# DHT11 / LED 真实硬件验证计划

类型：待执行的硬件验证计划。执行时逐项保存实测结果与未执行原因；当前试验及教师确认状态见 [真实性看板](project-truth-status.md)，软件编译和主机模拟不替代实物验收。

来源沿革见[不可辨识组与来源沿革](hardware-validation-plan.md#不可辨识组与来源沿革)；保留其中的知识 ID、来源 ID 和试验对应关系，旧审计配置不作为当前接线依据。首轮已确定选型、固件与待确认状态以[真实性看板](project-truth-status.md)、[固件说明](../firmware/esp32_dht11/README.md)及本次运行锁定的实验包为准。

首套DHT11器材到货时先按[内部技术目标与执行清单](experiments/dht11-arrival-checklist.md)完成基础链路，再按本计划扩展独立对照；清单通过不自动代表本计划全部试验通过。

## 1. 验证目标

建立“来源文件 → 项目配置 → 实际物理状态 → 原始设备记录 → 标准 Evidence UUID → 规则异常 → 候选与 unknown → 修复记录 → 教师确认”的可追溯链。

首先验证可观察到什么，再验证能区分哪些故障。DHT11 失败日志没有足够辨识度时，合格输出应保留 unknown / need_verification。LED 必须区分命令状态、引脚电压、回路电流和实际发光。扩大候选集或增加排序权重不能代替测量。

资料修订与发布遵循 [实验包规则](development-guidelines.md#package-content)。表中次数和观察时长是先导建议，不是官方标准或课堂判据。

## 3. 记录格式与证据层级

每次实际运行独立保存至 `hardware-validation/<experiment_type>/<run_id>/`，使用外部附件与现有反馈/审核能力，不创建占位结果。

每次实际运行至少记录：

| 字段组 | 必需信息 |
| --- | --- |
| 身份与版本 | run_id、experiment_type、设备标识、板卡/器件编号、包版本 ID/hash、固件/源码 hash、操作者、开始/结束时间 |
| 条件 | 接线图/照片版本、实测供电、仪表型号/编号/校准或核查状态、环境条件、实际采样周期 |
| 真值 | baseline / controlled_fault / recovery、单一改变项、注入与恢复时刻、操作者记录、已知/未知根因及依据 |
| 设备记录 | 原始 HTTP JSON（脱敏）、串口日志、bootId、sequenceNo、requestId、设备时间、服务端接收时间、timeQuality |
| 诊断记录 | 日志/读数/心跳 ID、diagnosis_id、持久化 Evidence UUID 列表及 normalized_value、规则命中、候选、unknown/缺证据/动作 |
| 外部观测 | 接线照片、电压/波形文件、人工发光记录或光学测量；文件 SHA-256、采集时刻、测点和观察者 |
| 结果与审核 | 实际修复动作、修复后新的诊断 ID、是否恢复、未解释现象、教师签署与日期 |

没有实测的字段填写 null/未执行，不填 0，不生成示例 UUID 冒充数据库记录。观察者姓名、确认时间和教师结论只在实际发生后登记。

光学、万用表和逻辑分析仪文件先作外部附件；未落库关联本次诊断时，AI 不得引用它们的伪造 ID。教师可据附件审核，新增结构化输入需另行评审。

真实硬件试验仍可能使用测试实验包，诊断会继承 is_test_data=true。这不是模拟数据伪装成实测：在实验记录中另记实际采集来源与“受控故障注入”，保留现有测试标记，不为进入正式统计而清除它。受控故障案例也不能称为历史学生案例。

## 4. 先验证接入，再开始故障试验

1. 在测试环境绑定明确包版本，从真实设备发送正常心跳、读数和失败日志，逐项核对协议 Schema。
2. DHT11 验证 `DHT11_READ_FAILED`→`sensor.read_failed` 后仍有 `component_id=dht11`；核对真实报文、服务端归一化与持久化来源，不以协议样例通过代替实物链路。映射不符时保留原报文并记录问题，不伪造组件值让测试通过。
3. LED 分别核对 `gpio_command_level`、`gpio_actual_level`、`led_physically_on` 到对应 `observation.*` 的来源、组件、接口和命令关联。旧 `level` 只能保留为来源未确认的旧观测，不自动补成引脚电压或实际发光。
4. 逐项核对 raw_payload、normalized_value、occurred_at、来源记录 ID 和 Evidence UUID。重发同 requestId 不应重复计数。
5. 分别发送缺观测、旧观测、未知错误码、缺组件、失效时间等测试输入，确认它们不会被当成真实正常或根因确定。此项合成协议测试与硬件试验分开归档。
6. 核对基础健康规则与当前包的运行预期共同生效：离线、心跳过期、必需观测及有效字段分别检查。DHT11 有效读数不等于测量精度合格；LED 已按命令目标比较，但实际响应窗口与观测来源仍待确认。周期、时限或关联缺失时保留 `unknown`，不以旧兼容规则或人为补值凑出正常结果。

## 5. 单次试验的通用流程

使用“基线 A → 单因素改变 B → 恢复 A”的顺序。建议先做每个可安全执行条件 3 次独立重复，每次重新记录基线与恢复；这是先导设计，用于发现波动，不足以宣称统计准确率。正常基线建议至少收集 30 个有效采样周期，实际时长由已确认采样周期计算。LED 每次建议记录 10 个完整亮灭周期，课程可调整。

1. 保存接线、参数和固件版本，确认基线观测满足课程判据；基线本身异常时停止本轮。
2. 断电完成需改线的操作，只改一个变量。记录改变项而不提前把系统输出写成故障真值。
3. 在批准条件下通电，连续记录本地串口、服务端数据及外部测量，并保留所有成功/失败序列。
4. 在预先定义的时点触发诊断，保存其输入时间窗和所有 Evidence UUID。
5. 按记录恢复唯一变量，重新采样并启动新的诊断上下文，保存修复后的独立结果。
6. 确认恢复后已有新的相关采样，再点击“用最新数据重新检查”并保存结果；该操作不控制采样，“仍未解决”只继续原指导。判据见 [重新检查与恢复](development-guidelines.md#recheck)。
7. 同样结果不能区分多个根因时，记录不可辨识集合与下一测量，不强行指定 Top-1 为真实根因。

## 6. DHT11 试验设计

| 试验 ID | 单一条件与前提 | 必采证据 | 要回答的问题 / 合格边界 |
| --- | --- | --- | --- |
| D-00 | 经确认接线、器件、驱动和采样周期的正常基线 | 温湿度逐次值、采样成功/失败时刻、供电、DATA 波形样本、协议记录 | 系统能收到新读数；读数有效、通信成功、精度合格是不同判据 |
| D-01 | 断电断开 DATA，再按审核步骤上电 | VDD-GND、主机脚与传感器端波形、错误码、在线、读数新鲜度 | 失败表现是否与 D-02/03 相同；只凭失败应 unknown |
| D-02 | 实物接线不变，只改为经教师确认可用于此试验的错误配置 | 固件 diff/hash、配置 GPIO、正确脚/配置脚波形 | 引脚错误是否有可区别证据；不扫描或随意驱动其他引脚 |
| D-03 | 传感器未供电的受控条件 | 电源实测、DATA 电压、网络心跳、失败序列 | 教师先评估 DATA 上拉造成反向供电的可能性；无法实现单因素隔离就标未执行 |
| D-04 | 同配置下已知正常件与来源明确异常件 A/B/A 对照 | 每件编号、原始异常依据、接线不变证明、结果 | 支持器件相关性；不人为损坏器件，没有故障件即保持 pending |
| D-05 | 核对实际驱动、启动等待与当前已确定的 3 秒项目采样周期；仅在批准条件内比较配置 | 固件/SDK 版本、每次真实触发时刻、总线时序、错误阶段 | 实际周期是否符合选定器件资料与配置；最低请求间隔、采样周期、缓存返回和真正总线采样分别记录 |
| D-06 | 受控、可恢复的间歇 DATA 连接；避免随机摇线造成多变量 | 每次断接时刻、完整成功/失败序列 | 累计五次和连续五次是否混淆；成功是否应重置连续数 |
| D-07 | 不破坏硬件，比较真实读数上传与暂停读数上传 | 心跳仍在、最后有效值时间、上报策略 | 缺测是否被当正常；旧值是否被当当前值 |
| D-08 | 按固件流程观察上电后的第一次和第二次有效帧 | priming 日志、两次触发 uptime、`previous_conversion` 元数据、`occurredAt` | 第一次未知前序转换不发布为测量；第二次读数绑定前一次触发时刻 |

精度试验是独立子任务：待教师确定参考仪器、条件、稳定时间及误差判据后执行。单次室内读到“看起来正常”的温湿度不构成精度验证；不按网络经验编造房间范围。

## 7. LED 试验设计

| 试验 ID | 单一条件与前提 | 必采证据 | 要回答的问题 / 合格边界 |
| --- | --- | --- | --- |
| L-01 | 正常 HIGH/LOW 完整周期，使用已确认电路 | 命令时刻/目标值、API 返回、GPIO 模式、pad 电压、同步目视或光学记录 | 两个相位分别验收；正常 LOW 不应解释为坏件 |
| L-02 | 仅改变输出模式配置，其他不变 | 程序目标变量、寄存器/输入使能信息、外部电压 | 上报 level 是否只是变量；gpio_get_level=0 是否因未使能输入 |
| L-03 | 仅改变程序 GPIO 配置为批准的测试引脚 | 构建配置、真实线、两脚测量、光学观测 | 配置错和断路是否仅凭日志不可区分 |
| L-04 | 在同一已知电路上分别命令 HIGH 与 LOW | 原理图、两态电压/光学记录 | 有效电平是什么；不预设所有板卡高电平点亮 |
| L-05 | 极性核对；反接带电测试只在器件额定与教师审批满足后做 | 极性依据、接线照片、回路状态、光学记录 | 不能证明安全则只做断电检查，保留测试缺口 |
| L-06 | 断电打开经确认的 LED 回流支路，再恢复 | 通断检查、命令/level、pad 电压、发光观测 | HIGH 与灯不亮并存时，系统必须说明光学证据来源与根因不确定 |
| L-07 | 已知正常/异常 LED 的 A/B/A 对照 | 器件编号与异常依据、同回路、测量和发光记录 | 不根据一次更换成功直接排除重新插线的影响；必要时重复对照 |
| L-08 | 不改硬件，模拟暂停上报/旧值回传并单独归档为协议试验 | 当前命令、采样时间、接收时间、真实光学状态 | 过时 1 不能证明本次已亮；缺观测不得当正常 |

发光观测可先由人工执行：固定观察条件，记录操作者、时刻、命令相位，保存可对应 run_id 的照片/视频。它是人工观察，不是设备自动检测。后续若增加光敏/电流检测，需独立验证传感器、环境干扰、阈值与接入字段；本阶段不要求购买或增加器件。

不得用短路、移除限流后直驱、过压或破坏器件制造故障。阻值、电流与电压从实际型号资料及教师确认计算，计划中不提供未经依据的统一数值。

## 8. 两实验共用的离线与恢复测试

| ID | 条件 | 对照证据 | 允许结论 |
| --- | --- | --- | --- |
| C-01 | 保持设备运行，仅在可控测试网络中中断服务器连接 | 供电、本地串口、缓存状态与服务端时间线；记录何时因缓存满暂停采样 | 服务器不可达不等于设备断电；当前 DHT11 单批缓存不保证离线期间连续采样 |
| C-02 | 按批准流程关闭设备电源并恢复 | 电源记录、bootId 变化、本地/服务器时间线 | 本轮受控断电有外部真值；仅服务器超时仍不能用于其他案例确认断电 |

| ID | 条件 | 对照证据 | 合格边界 |
| --- | --- | --- | --- |
| C-04 | 配好上传身份后断网生成一批，再恢复连接 | 冻结文件及载荷哈希、原会话/requestId/bootId/sequenceNo、HTTP 回执与数据库记录 | 先保存后发送；原批次不因重连或换会话而改写；单批缓存占用时暂停新采样 |
| C-05 | 分别验证未初始化、挂载失败、短写、读回不一致与改名失败 | 文件前后哈希、串口状态、网络抓取、服务端记录 | 不自动格式化；保存未成功就不发送，保留已有批次。每种故障独立记录，未注入的不算通过 |

| C-08 | 单批缓存阻塞采样后解除阻塞 | 暂停时段、恢复后两次有效帧、priming 日志及转换/读取时刻 | 恢复先重新 priming，不能把暂停前转换当作新的恢复证据 |

## 9. 评价方法与停止条件

先形成按真实条件分组的观察表，所有数据保留 run 级来源。报告至少包含：

- 有效试验数、未执行数及原因；同一接线重复采样不能当多个独立故障样本。
- 证据完整度：原始记录、标准 Evidence、外部真值是否都能定位到 run 和版本。
- 异常检测：正常/异常/缺测分别统计误报、漏报；当前包未覆盖的类型单列，不排除后美化分数。
- 根因可辨识性：同证据对应多少真实条件；unknown 是否恰当地保留。不可辨识组不以“必须正确 Top-1”作为验收要求。
- 不当确定结论：无光学证据声称灯亮、无真值声称器件损坏、引用不存在 Evidence、把测试确认当教师经验；目标为零，出现即阻止正式知识发布。
- 排查有效性：下一动作是否来自批准步骤，是否提供此前没有的区分性证据，是否实际执行并恢复。
- 版本与时间一致性：不混包、不混设备、不混修复前后样本，不把派生统计当独立证据。

发现异常发热、超出已确认电气条件、接线身份不明、基线失效或仪表结果冲突，应停止对应硬件轮次并记录。此处是针对具体试验的执行边界，不是已经完成的安全认证。

AI 初始关闭，先验证确定性链路。若后续启用，沿用同一证据和候选集检查 unknown 与引用正确性；AI 不能看注入真值后再声称从遥测诊断出来。进行原因区分评估时，可由另一位实验人员保存注入标签，诊断端只接收约定输入；这不是多智能体。

## 10. 从实测记录到正式实验知识

1. 为每个 knowledge_id 追加对应硬件 run、文件哈希和适用版本，保留原 source_ref；不可用实测覆盖厂商文档的原始含义。
2. 可复现且限定范围的配置更新为 hardware_verified；课程目标和教学流程只有真实教师确认后才记 teacher_confirmed。
3. 不可辨识故障继续 rootCauseStatus=unknown；解决后仍不确定根因的运行可以保留实验记录，但不能凑成 confirmed 正式案例。
4. 由真实事件创建 KnowledgeCaseDraft，绑定当前诊断 Evidence UUID、实际操作和恢复结果。资料手册中的通用事实留在事实清单/概念，不自动变成 real_case。
5. 教师核对真实根因、修复动作、适用硬件、时间、来源和测试性质；通过现有审核流程才产生正式 KnowledgeCase。AI 仅可整理表达。
6. 按 [实验包规则](development-guidelines.md#package-content) 修订、校验和审核新版本，保留历史快照；更新真实性看板时链接本次实测记录。

## 不可辨识组与来源沿革

旧审计中的D-A组为DATA断开、错误GPIO、未供电、部分器件异常：可能同样在线、失败码/累计数相同、无新温湿度；重复相同失败不增加辨识度。按D-01至D-04分别保留接线、两端波形、供电、构建/配置及正常件A/B/A记录。D-B组为网络隔离、ESP32断电、停止上传，可能都无新遥测；按C-01/C-02先恢复可观测性，不借历史失败判传感器损坏。

旧LED矩阵假设level来自程序目标变量；L-02至L-07的输出模式/GPIO错误、有效电平差异、反接、回路开路、器件异常都可能仍报告HIGH而未证明发光；须核变量/寄存器/pad语义、实际电压、回路与同步光学观察。均为待实测假设，不是故障结果或课程安全许可。

历史来源标识S1为Aosong DHT11资料，S2为Espressif GPIO资料；D/L事实ID只属当时审计定位，不能当Evidence UUID。旧配置不覆盖当前选型，实际版本/hash以固件sources.json及本次包为准；完整旧事实/来源/试验对应表通过[删除索引](archive/README.md)找回。
