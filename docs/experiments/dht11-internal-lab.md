# ESP32 + DHT11 内部实验操作指南

内容版次：2026-09-29 / v3。适用：DHT11资料包2.0.10、固件0.2.4、设备协议V1。状态：资料草稿，软件可检查部分与实物待执行部分分别标注。硬件选型已确定，尚未采购；没有真实实验结果或教师审核结论。

## 1. 范围与使用路径

面向首次使用本项目、能操作终端和编辑配置文件的维护者。前置知识是区分供电/地/信号、文件路径与串口，能阅读JSON字段；不要求先理解全部平台实现。

| 任务 | 预期能完成什么 | 留下的证据 | 现在能否做 |
| --- | --- | --- | --- |
| 准备 | 核对型号、来源、依赖及构建步骤 | 范围卡、来源定位、构建日志与产物hash | 可以 |
| 本地采集 | 接线、烧录、区分首次预热与实际读数 | 到货照片、配置、原始串口日志 | 需要实物 |
| 平台接入 | 确认身份、会话及固定包，核对上传回执和入库记录 | requestId、设备/会话/包版本、对应记录 | 需要已准备的测试环境与实物 |
| 异常理解 | 区分采样、传输和证据不足，按新数据重新检查 | 前后记录、诊断ID、未决问题 | 软件合成练习可先做，实物效果待验证 |

本实验不自行设定课堂合格分数、精度阈值、故障原因概率或连续运行合格时长。把配置正确、传输成功、硬件正常、精度合格分开记录。

单人可以兼任维护、记录和软件自审职责，记录实际操作者及依据；没有教师材料就保持缺失，不填写虚构教师署名。正式知识发布与运行包发布沿用项目流程。

快速路径：无硬件时完成第2、3节的资料和离线构建；到货后执行第4节；平台身份准备完成后执行第5节；异常按第7节分流，结果填第8节。

### 项目内部技术目标（2026-09-29确定）

本轮只评价首个ESP32+DHT11内部实验能否留下可信的完整链路；这是一套项目自定的功能验收目标，不是教师课程判据、温湿度精度认证或正式案例发布条件。到货后的逐项勾选和证据位置见[到货执行清单](dht11-arrival-checklist.md)。

| 门槛 | 完成时必须能证明什么 | 当前状态 |
| --- | --- | --- |
| T0 软件就绪 | 锁定版本的固件和LittleFS初始化镜像构建成功；镜像尺寸、分区和内容吻合；包/协议/宿主检查通过 | 本机已通过，见[构建复核](../../output/audits/dht11-arrival-prep-20260929/report.md)及[完整门禁](../../output/audits/littlefs-offline-20260929/report.md) |
| T1 板上本地采集 | 实物身份与接线可核对；烧录后串口留有启动版本、首次有效帧priming、后续有效温湿度或明确失败日志；配置的3秒周期与实际触发时刻可核对 | 待硬件 |
| T2 平台接入 | 独立测试环境中，固定测试包与真实硬件会话匹配；原始批次经授权入库，requestId、设备、会话、心跳和读数/失败日志能互相对应 | 待硬件与测试环境 |
| T3 可解释的异常与恢复 | 至少完成一次断电改线的单因素DATA断开—恢复对照；保存足够完整的失败序列以核对当前窗口累计阈值5，命中后只给有限候选/unknown；恢复后有新采样和新诊断，不把旧失败或学生反馈当恢复证明 | 待硬件 |
| T4 缓存与重连 | 在隔离测试网络中验证一批先持久化、断网保留、重连后按原身份投递及回执幂等；记录缓存满时暂停采样与恢复后重新priming | 待硬件与测试环境 |

T1—T4按顺序推进；每项有原始记录、配置/包/固件身份、操作前后时间和实际结果才可标通过。首轮只做功能与证据链验证，不设未经测量支持的准确率、连续运行时长或课堂分数。更细的单因素与掉电试验沿用[硬件验证计划](../hardware-validation-plan.md)；未执行项保持未执行。

### 2.2 断电接线

先拔掉开发板USB及其他电源。按原厂手册PDF第2页图1确定器件观察方向和脚号；下面是**按脚号的电气连接图，不是器件左右方向或面包板插孔图**。拿不准正反面时不凭线色或网上其他模块图片猜脚号；三针模块不套用四针裸件表。

| DHT11脚号 | 名称 | 本项目连接 |
| --- | --- | --- |
| 1 | VDD | 开发板3V3 |
| 2 | DATA | 开发板IO4/GPIO4；同时经4.7kΩ接3V3 |
| 3 | NC | 不连接 |
| 4 | GND | 开发板GND |

```text
ESP32 3V3 ───────────── DHT11 pin 1 VDD
     │
     └── [4.7 kΩ] ──┬── DHT11 pin 2 DATA
ESP32 IO4 ──────────┘
ESP32 GND ───────────── DHT11 pin 4 GND
                        DHT11 pin 3 NC：不接
```

GPIO4是引脚功能名称，不是排针从某一侧数第4针。检查面包板电源轨是否分段，所有GND是否相通，上拉是否接到3V3。首轮采用短连线，20cm以内只是项目布线建议；厂商资料要求3.3V供电时尽量短，并给出短于5m时4.7kΩ的典型电路建议，不把该长度当本项目实测能力。依据[S1][S2]。

**本步记录：**断电接线照片、每根线的两端、板卡/器件标识。预期是接线与表一致；这不证明通电后的电压或器件正常。不一致先修正并重新拍照，不带电插拔传感器作故障演示。

## 3. 无硬件准备与离线构建

下面命令从仓库根目录运行。`pio`指已安装的PlatformIO命令；若不在PATH，用它的实际可执行路径替换。框架和库锁定以[platformio.ini](../../firmware/esp32_dht11/platformio.ini)为准：Espressif32 7.0.1、Arduino框架、ArduinoJson 7.4.2；Arduino内核版本以解析后的包清单为准，不把平台包编号当内核版本。

```bash
pio --version
pio run -d firmware/esp32_dht11
pio run -d firmware/esp32_dht11 -t buildfs
```

前提：已有PlatformIO运行环境；缺锁定依赖时才执行`pio pkg install -d firmware/esp32_dht11`，首次安装可能需要访问软件包源。当前离线取得的`tool-mklittlefs@1.203.210628`已能被本机PlatformIO识别。预期：两个构建目标成功，产生`.pio/build/esp32dev/firmware.bin`和`littlefs.bin`。`buildfs`只生成文件，不写设备。失败按卡A处理。

本轮审计使用的PlatformIO Core 6.1.19位于`/private/tmp/xinjian-remediation-pio/`，这是临时环境，不作为到货时的长期依赖。到货前先确认自己的持久环境能运行`pio --version`并识别上述锁定平台与LittleFS工具；若CLI或依赖不可用，先准备对应环境再按本节构建，不将旧产物直接充作新版本。

首次无平台身份的构建应确认`include/secrets.h`不存在；此时固件可做串口采集，但不会向平台发送。`data/README.txt`是初始化镜像唯一预期文件；`secrets.h`不进入LittleFS镜像。当前`esp32dev`默认4MB分区表中名为`spiffs`的数据分区位于`0x290000`、大小`0x160000`，项目构建器明确选择LittleFS格式；名称并不表示镜像采用SPIFFS格式。若到货板卡闪存布局、构建平台或分区配置变化，重新核对实际`partitions.bin`与镜像尺寸后再烧录。

保存工具版本、完整构建日志、源码提交或工作区指纹，以及两个文件的SHA-256。macOS可用：

```bash
shasum -a 256 firmware/esp32_dht11/.pio/build/esp32dev/firmware.bin
shasum -a 256 firmware/esp32_dht11/.pio/build/esp32dev/littlefs.bin
```

每次构建记录当次哈希，不把历史镜像哈希当固定预期。本轮相同源文件下的LittleFS镜像哈希已有变化，但按实际分区尺寸解包后内容相同；验收同时核对大小、文件列表和README内容。配置真实上传身份后需重新构建并烧录`firmware.bin`，另记新哈希；只改固件身份配置无需重新上传文件系统，不能借此覆盖未发送批次。

可用项目Python环境运行：

```bash
python scripts/test_firmware_host.py
PYTHONPATH=backend python scripts/check_firmware_protocol.py
PYTHONPATH=backend python -m app.cli.verify_experiment_packages
PYTHONPATH=backend python -m app.cli.preview_package_context --strict --expectations backend/evaluation/package_context_expectations.json
```

这些命令不发布包、不接入实物或调用真实Provider。Python需满足后端依赖；主机测试还需C++编译器和已安装的ArduinoJson。缺工具应记录为受阻，不写成测试通过。完整验收另见[评测入口](../evaluation.md)。

## 4. 到货后的首次本地运行

### 4.1 确认串口和烧录

先完成第2节核对，使用USB数据线连接开发板。执行`pio device list`，通过插拔前后差异确认实际设备端口；不要复制别人电脑上的端口名。以下尖括号内容必须替换成实际端口：

```text
pio run -d firmware/esp32_dht11 -t upload --upload-port <实际串口>
pio device monitor -d firmware/esp32_dht11 --port <实际串口> --baud 115200
```

烧录时关闭占用同一端口的监视器。预期是烧录工具报告成功，串口启动日志出现固件版本、测试标记与GPIO。只看到烧录成功不等于传感器采样成功。保存两份日志；失败转卡B。需要手动进入下载模式时按所购板卡对应的DevKitC指南操作，不把其他板卡的按键流程当通用步骤。

### 4.2 首次文件系统初始化

**仅对已确认没有需保留记录的新设备执行。** 固件配置了上传身份后需要LittleFS持久缓存；普通程序烧录不等于已初始化文件系统。项目明确使用LittleFS，初始化镜像仅含说明文件，不含请求、凭据或测量数据。

核对第3节生成的是`littlefs.bin`，设备身份和端口正确，再执行：

```text
pio run -d firmware/esp32_dht11 -t uploadfs --upload-port <实际串口>
```

这会替换文件系统内容。已有或身份不明设备、有待发送批次、存储故障时，不能用此命令试错或清队列，应先保存现场并由维护者处理。项目保留`LittleFS.begin(false)`，启动失败不会自动格式化。

首次初始化时把端口、设备标识、分区表和当次镜像SHA-256写入记录。`uploadfs`完成仅证明烧写命令报告成功；配置上传身份并重新烧录固件后，还需观察板上LittleFS挂载及缓存读写。不要为了消除挂载错误反复执行`uploadfs`。

镜像构建已纳入软件检查；真实烧写、挂载和断电恢复仍待到货验证。若初始化后仍提示`storage unavailable`，记录分区/构建版本、日志并转卡E，不反复覆盖存储。[S3][S4]

### 4.3 先观察串口，再接平台

首次本地采集使用未配置上传身份的固件（默认不创建`secrets.h`），串口可预览记录。预期过程来自当前源码，实际发生时间仍要记录：

- 上电等待后发起读取；首次有效帧只作priming，会提示`first valid frame primed`，不发布未知前序转换的温湿度。
- 后续读取持续有效时出现temperature/humidity记录；它们表示前一次转换，不能把收到包的时刻直接当测量时刻。
- 读取失败出现`DHT11_READ_FAILED`；没有有效读数就不填“正常温湿度”。
- `heartbeat: firmware alive`只是串口运行标记，不是平台已收到心跳。请求批次中的heartbeat才是待上传记录。

保留连续原始日志而不是只截图成功的一行。没有读数转卡C/D；看到数值只证明当前程序输出，精度需独立仪器与方法核验。默认`XJ_IS_TEST_DATA=1`表示内部测试用途，即便接真实硬件也保留该标记，并在实验记录另写数据来自实物还是合成。

## 5. 平台接入与记录核对

### 5.1 平台准备交接

平台尚未准备好时，可以完成串口阶段。上传阶段需要以下真实对象，不能在固件随意编几个ID代替：

| 材料 | 核对方法/入口 |
| --- | --- |
| 后端可达地址 | 按[部署说明](../deployment.md)确认选定测试环境；开发板访问电脑的地址，不能使用开发板自身的localhost |
| 设备身份与令牌 | 新内部实验通过初始化CLI建立独立设备身份；已有设备使用核对后的凭据，不能被新前缀接管；ID是device_key，不是数据库UUID |
| 任务、设备授权与学生账号 | 维护者准备授权班级/任务/设备关系；学生登录后在`GET /api/v1/student/assignments`核对可用任务与设备 |
| 已发布测试包版本 | 包管理接口位于`/api/v1/experiments`，经validate/import及有权管理员的状态流程；核对版本/hash与测试标记 |
| 固定包的活动会话 | 学生通过`POST /api/v1/student/experiment-sessions`开始授权任务，或使用已核对的活动会话；保存服务端返回的会话ID与包版本 |

**内部实验准备入口：**现已提供`app.cli.prepare_internal_experiment`的plan/apply/status，按[内部测试准备说明](internal-lab-preparation.md)建立测试班级、任务、账号和设备绑定。它要求明确的测试数据库、已认证测试管理员与固定的已发布测试包；不自动审批包、不直接创建活动会话。学生随后经现有接口开始会话。`seed_demo`仍是旧合成演示入口，不绑定当前DHT11包；不要用它替代上述流程或改写旧会话。

包管理请求使用严格的`documents`（十个工件文件名到解析后对象的映射）及`is_test_data: true`，不是上传一个目录字符串。精确请求体以目标环境`/docs`为准。发布权限、状态流转及教学审核边界见[包设计](../experiment-package-design.md)。本指南和离线验证不会自动执行发布。单人可操作自己有权管理的测试环境，系统教师角色不等于取得真实教师确认。

### 5.2 固件上传配置

复制[secrets.example.h](../../firmware/esp32_dht11/include/secrets.example.h)为同目录`secrets.h`并填写本地值；存在该文件时先检查，不覆盖原凭据：

| 配置 | 应填内容 |
| --- | --- |
| XJ_WIFI_SSID / XJ_WIFI_PASSWORD | 实验网络 |
| XJ_API_BASE_URL | 完整批次入口，含`/api/v1/device/ingest` |
| XJ_DEVICE_ID / XJ_DEVICE_TOKEN | 上一步核对的device_key和令牌 |
| XJ_EXPERIMENT_SESSION_ID | 服务端的有效活动会话ID |
| XJ_CA_CERT | HTTPS主机对应的可信CA PEM；不要把认证失败当作可以跳过校验 |
| XJ_ALLOW_INSECURE_HTTP | 默认0；只有明确选定的隔离本地HTTP测试环境才设为1 |

不把凭据写入报告、截图或Git。重新编译并烧录，让配置进入固件；保留这次不同于串口阶段的固件hash。普通固件`upload`不应被当作文件系统初始化，亦不需要因填入凭据而再次执行`uploadfs`。配好上传身份后，存储不可用或有未确认批次时会暂停新采样。修改设备/会话前先处理原有批次，不靠重启、改请求ID或格式化规避未决状态。[S3][S4][S5]

### 5.3 核对到达，不只看“在线”

1. 串口找到requestId、bootId、sequenceNo及记录类型；将脱敏原始日志归档。
2. 核对对应请求的服务器回执及平台同一设备/会话的记录。requestId一致、各记录accepted说明接口接收，不证明传感器精度。当前固件不会把所有服务器回执原文打印出来，必要时用后端授权记录核对，不能要求不存在的串口行。
3. 分别核对心跳、温度、湿度或失败日志；串口预览和服务器记录不能相互冒充。
4. 检查时间质量：未取得可信设备时间时服务器会回退，不能把接收时间解释为独立测得的采样时间。
5. 没有新记录转卡E；有记录但状态未知转卡F。[S3][S5]

## 6. 重新检查与恢复判断

先确认新数据已到达当前会话，再在学生界面触发“重新检查”。该动作分析已上传记录，不命令ESP32重新采样。“仍未解决”继续原指导，也不等于新一次传感器失败。

保存新旧诊断ID、数据窗口、证据记录和实际操作。只有满足版本化正常/恢复判据才能称恢复；目前DHT11新鲜度等实测参数仍待确认，数据到达后也可能保持unknown。不要为了让页面变绿补填未经验证的阈值。窗口累计5次只是现有规则配置，不是连续5次，更不是某个器件已损坏。[S6][S7]

无硬件练习使用隔离测试环境和明确的合成输入，操作方法见[演示手册](../demo-runbook.md)及[评测入口](../evaluation.md)。合成输出不填入实物结果栏，不拿课堂验收标准评价软件夹具。

## 7. 六类排查卡

### 卡A：编译或镜像构建失败

- **先留证据：**命令、工具版本、首个错误及其上下文，区分依赖下载失败、缺本地工具和代码编译错误。
- **检查顺序：**仓库目录与环境名→锁定依赖是否取得→错误指向的文件/工具→原命令重试验证。
- **区分作用：**镜像工具下载失败不说明接线错误；buildfs成功不说明实物已挂载。
- **复查/停止：**只有同一环境构建成功才前进；版本冲突或来源不明时保存日志交维护者，不随意升级全套依赖。[S4]

### 卡B：无法烧录或没有串口输出

- **先留证据：**实际端口、插拔前后设备列表、烧录日志、监视器波特率及占用情况。
- **检查顺序：**数据线/USB连接→目标串口→关闭串口占用→按板卡指南核对下载模式→烧录完成后重新打开115200监视器并观察启动。
- **区分作用：**设备识别问题与程序输出问题分开；烧录成功不保证传感器响应。
- **复查/停止：**保存启动版本/GPIO信息；板卡型号、接口或电源不明时暂停，单独核对实物，不通过更改传感器连线解决USB问题。[S2][S3]

### 卡C：有心跳或运行标记，但没有温湿度

- **先留证据：**是串口alive、请求中的heartbeat，还是平台心跳；是否出现primed、读取失败或存储阻塞日志。
- **检查顺序：**首次有效帧→下一次有效读取→有无读取失败→有无pending/storage暂停。
- **区分作用：**首次priming不发布读数符合设计；有心跳不证明传感器正常；暂停采样时不能推导“连续读取失败”。
- **复查/停止：**记录下一个采样事件及其类型，不预填成功；持续读取失败转卡D，存储/上传阻塞转卡E。[S1][S3]

### 卡D：DHT11_READ_FAILED

- **先留证据：**错误阶段timeout/checksum/range/protocol、固件版本、配置、断电接线照片、失败前后日志。
- **检查顺序：**核对所选型号/修订→断电核对3V3/GND/DATA与上拉→核对GPIO4、所选手册数据格式及3秒周期。每次只改变一个有依据的因素并记录；独立电压测量与器件对照按硬件计划执行。
- **区分作用：**日志证明读取或解码未通过；range/protocol也可能提示版本不匹配，不能据此确认损坏。累计达阈值只触发异常。
- **复查/停止：**保留修正后新数据并重新检查；不能安全确认供电/脚号时停止上电。没有已知正常备件时如实记录“未做器件对照”，不假定已排除其他原因。实际教学动作遵循当前故障树提示。[S1][S3][S7]

### 卡E：串口有记录，平台没有新记录

- **先留证据：**是否配置上传身份、网络状态、requestId、存储提示、服务器授权状态/错误响应，避免复制令牌。
- **检查顺序：**是否仅串口预览→完整入口可达性→设备与会话对应关系→LittleFS状态→原待发送请求及重试次数→服务器授权记录。
- **区分作用：**缺配置不发送；离线可保留一批，未确认前暂停新采样。重试预算耗尽、会话改变、存储损坏均不是“传感器坏了”。
- **复查/停止：**确认原请求的接收/未决状态；自动重试仍复用同一批次。预算耗尽或队列损坏时保存现场，当前没有供用户直接调用的队列解锁工具，不把反复重启、格式化或更换会话当恢复步骤。新设备无历史数据的初始化仅按4.2节执行。[S3][S5]

### 卡F：记录已经到达，诊断仍为unknown

- **先留证据：**当前设备/会话、固定包版本、诊断ID、时间窗口、缺失证据项及数据时间质量。
- **检查顺序：**身份和包是否对应→所需观测是否齐全→新数据是否在检查窗口→周期/新鲜度判据是否已定义→用新数据显式重新检查。
- **区分作用：**无规则命中不等于正常；读取失败不能区分根因；未知是证据边界，不是必须消除的页面错误。
- **复查/停止：**记录哪些缺口已补、哪些仍待实测；参数未核验时保留unknown。涉及专业判据整理材料待后续确认，不填写虚构教师结论。[S6][S7]
