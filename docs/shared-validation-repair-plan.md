职责保持分层：API负责解析身份和映射错误；共享服务负责规则；领域服务负责资源状态、锁和事务；图节点在最终写入前调用；前端负责按结果更新页面，不能替代后端授权。共用的是相同含义，不把不同业务的权限、409或恢复规则硬合成一条。

## 2. R1：在真正生效的位置检查当前权限

### 身份、资格、资源状态分开负责

- API把已解析身份传成服务器构造的 `ActorContext`，包含操作者ID、认证模式、需要时的登录会话引用。它是身份线索，不是可长期复用的授权结果；不接受客户端自行提供的“已授权”标志。
- `auth.py` 统一重新读取登录会话、有效期、撤销状态、账号及当前角色/权限；有些现有函数依赖FastAPI Request，抽出不依赖HTTP的核心，再让依赖层复用。只传一个旧ORM User对象不再足以执行受保护写入。
- `data_scope.py` 统一资源所属学生/会话/班级、当前授课关系与能力边界。保留不同业务角色，不能将“能看”推成“能审核”。停用班级占用仍可按管理规则释放，不新增一刀切禁止历史管理的条件。
- 域服务检查版本、状态与动作合法性。授权失败统一领域异常，路由映射401/403；并发版本或状态冲突映射409。图装饰器、恢复异常包装必须识别并保留授权失败，不能变成503。

所需能力由服务器的操作类型确定，资源从持久化归属解析，不能让客户端挑选较低权限或另一班级来完成校验。失败后不得出现新的成功审核、状态或回执写入；必要的拒绝审计须使用固定原因并避免保存无权正文。

### 校验时点与并发契约

入站预检 → 等待资源锁 → 读取最新授权及资源 → 执行短事务内的状态/审计/回执写入 → 当前响应按权限投影。长操作分段处理，在网络/Provider等待结束后再次进入同一受保护写入边界。

诊断审核的 `review_workflow` 与 `persist_result/reject_result/_persist_teacher_review` 是本轮重点：图的中间提交会释放先前锁，最终节点必须重新核权，不能认为路由查过一次就有效。工单、模板等现有 `recheck_access=None` 属于容易遗漏的入口；将受保护的公开写入口改为必需身份参数并在内部校验，未提供身份明确拒绝。内部构造辅助函数不作为公共写入替代入口。

只重查一次仍有“检查后、提交前撤权”的窗口。实施先绘制现有 actor→device、生命周期锁、workflow锁及授权依据行的锁顺序；为最终短事务锁定支撑本次授权的账号/会话/关系行，撤销这些关系的更新或删除须与之互斥。按这一顺序统一调用方，不能各自插锁。采用如下可验证语义：撤权先提交则后续动作拒绝；动作先取得保护并完成提交则保留合法历史，随后撤权阻止新动作。不声称撤权能追溯取消已经提交的结果。

锁顺序表、PostgreSQL两种交错执行及超时/死锁测试是实施前置条件；不能用SQLite或一次SELECT证明以上事务语义。不得持数据库锁等待外部模型。不同教师、设备或工单应保持可独立推进，不引入全局大锁。

### 恢复兼容

- `ActorContext`及明文令牌不写入Checkpoint。新的人工审核恢复需要新请求的当前身份；旧Checkpoint仅有 `reviewer_user_id` 时不能据此授权新写入。
- 已经完成的业务审核与待对齐Checkpoint必须区分：恢复已提交结果不得再执行审核、重复审计或改写历史；是否允许当前用户读取由读取授权检查。
- 内部CLI沿用已明确的本地管理员模式并重验数据库资格；不能为兼容加入通用 `skip_auth`。设备演示身份仅在既有演示入口有效，不能获得教师审核能力。

## 3. R2/R3：每个页面使用同一份合格建议

### 共用资格结果，保留各自展示

在 `current_advice.py` 内形成 `AdviceAssessment`：`usable`、固定原因码、已验证的说明与来源引用。规则说明渲染、AI结构/动作白名单校验、当前策略检查、来源状态检查分别复用原有模块；资格组合只在这里维护。依赖方向为投影器→底层校验器，不能让 `current_advice` 与 `ai_diagnosis` 相互调用产生循环。

检查内容包括：诊断/工作流/包归属、冻结 `context_delivery.explanation_call_id` 与相应推理阶段、调用成功、当前上下文策略、输出结构及允许动作、来源当前可用性、版本和测试范围。各消费者只负责把合格结果转成自己的响应格式。

工作流来源按冻结调用ID绑定，不能用“最新一次成功调用”替换。独立解释API可以按它自身明确的调用身份校验；没有足够绑定的旧记录作为历史查看或确定性降级，不猜一个新绑定。未绑定数据库的记录不能跳过来源检查而成为当前建议。

学生仪表盘的 `device_state_explanation` 与 `ai_explanation` 使用同一资格评估；前者的构造器只接收已验证投影，不接收原始 `output_json`。工作流、检查/反馈回执的当前展示、教师当前预览亦接入；历史审计保留原值并明确历史性质。模型摘要不能覆盖后端固定事实，规则生成的状态、限制和动作范围保持权威。

合格的教师编辑结果仍按其最终快照投影，不能在收敛实现时用原AI调用替换教师编辑；来源失效后的历史审核标记沿用既有降级契约，不伪称教师重新审核了回退结果。

来源停用、绑定缺失或策略过期时，不调用模型补救，不修改旧调用/回执/Checkpoint；返回确定性说明或教学暂停状态，具体沿用现有适用来源契约。即使AI配置关闭，也不能直接展示未检验的旧内容。

### 实验身份只从冻结事实解析

`context_from_diagnosis` 校验诊断与冻结快照的一致性，匹配器不再把 `sensor_type` 或旧模板标识拼成候选实验集合。冲突、缺失、未知都不能变成“适用所有实验”。已明确身份的旧全局案例仍可用，身份不明的记录保留历史而不参与当前增强。案例自由文字条件 `text_only` 不能豁免实验身份门槛。

全局与包路径、图运行与离线预检调用同一个匹配器；包内案例还须通过装载器现有包身份检查。保持规则诊断与确定性指导可用，不能把“无合格案例”变成整条诊断失败。

## 4. R4/R5：来源生命周期与测试标记

### 删除采用整次检查、整次拒绝

本轮选择明确且保守的处理：合成运行被诊断/审核/冻结工作流引用，或无法证明未被使用时，清理返回409和固定原因，**整次运行不删任何记录**。不级联删除诊断来让清理成功，不自动设置保留期限。不涉及正式数据清理。

清理服务负责验证设备身份、运行归属与测试标记，统一枚举日志、读数、心跳来源；按实际 `source_type + source_ref` 及历史冻结引用格式查找，不能只查某一种字符串形式或只查最新诊断。无引用且无在途使用的合成运行维持现有清理结果与空集合重放语义。

“先查无引用再删除”不能独立于引用创建：原始数据装载/冻结与持久化引用、清理需要共同的设备/来源保护。长工作流必须在释放保护、调用模型前固定可查询的来源使用记录；最终写入前重验来源仍在。对当前表或快照无法证明安全的旧在途流程，拒绝清理，不猜测或增加绕过开关。实施先检查能否复用现有工作流冻结记录和 `DiagnosisEvidence`；本方案不预先新增表。若现有记录无法提供并发保护，需要先补充可审查的持久化设计与追加迁移，再开放该删除分支。

允许清理、引用拒绝、引用与清理并发、失败回滚必须分别测试；特别检查“查询已无引用、另一事务随后创建引用”的反例。

### 测试标记单向传播

拟定 `derive_test_flag(explicit, source_flags)`：任一有效来源为测试数据，派生记录就是测试数据，调用方的false不能覆盖true。纯函数只接受已核对来源；来源身份无法确定时由域服务拒绝或标为受限，不能把缺值默认为正式。

课堂消息的来源至少包含请求标记、当前作者和目标班级。逐项检查工单、诊断、案例和包的来源清单，不盲目把所有bool表达式替换。派生对象的“包含测试来源”使用any语义；统计上的“全部是测试”如确有必要须使用独立字段含义，不能复用为正式性判据。导出保留逐条标记，混合数据不能进入纯正式统计。

只修正新写入规则。历史false记录先做只读范围清单；没有来源证据不批量改成true或false。确证历史需修正时另列变更方案与审计，不夹在本次普通代码回归中执行。

## 5. R6：统一错误事实、操作策略和页面失效动作

### 集中分类，不用所有状态码共用一个动作

`resilience.ts` 统一识别HTTP状态、无响应和超时；实际收到HTTP响应时优先采用响应，不让 `navigator.onLine` 覆盖已确认的401/403。`commandOutcome.ts` 维护“操作类型＋结果＋既往是否存在未知提交”的处理表，输出下一动作；各API和Store消费结果，不再分别写状态码列表。

| 结果 | 身份/页面动作 | 命令处理 |
| --- | --- | --- |
| 401 | 原登录代次失效，清除其可见内容和凭据，重新认证 | 停止重发；当前明确拒绝的尝试退出活动队列 |
| 403 | 清除被拒对象/范围的投影，递增请求代次，停止相关操作；不能把单对象403扩大为其他合法范围全撤权 | 显示权限变化，不当普通网络重试；重新授权后查询原回执 |
| 400/404/422 | 按具体端点的拒绝契约提示修正/重新读取 | 禁止自动换ID或自动提交；释放已确定未执行的当前命令 |
| 409 | 刷新相应对象/回执，保持明确冲突提示 | **按操作表处理**：反馈维持既有原请求恢复语义；会话/工单已知版本冲突不自动重试；身份复用冲突不能丢掉原命令 |
| 超时、无响应、可疑5xx | 已授权旧数据按现有规则仅只读且标过期 | 保留同ID/同载荷的未决命令，查询或显式恢复；不另起身份制造重复副作用 |
| 429 | 提示限额与允许的重试时机 | 按服务契约判断本次未准入；不把其他历史未知尝试一并判为失败 |

收到401/403只说明本次尝试被拒绝，**不能证明此前超时的那次未提交**。将可执行的待重试载荷和最小恢复线索分开：权限失效时清除不再有权展示的正文和重试载荷；既往未知操作的request_id、操作类型和账户/资源范围以最小方式保存或依赖已有服务端回执恢复，不跨账号展示、不保存令牌。重新认证并确认当前授权后，只读查询状态再决定。若某命令尚无可靠的原回执查询能力，在实施该分支前补齐它或明确保留受控恢复流程，不能靠清本地记录绕过。

同一套Store失效处理用于GET和动作POST，覆盖工单动作、解决报告、审核以及分区读取。等待中的旧请求成功或失败都必须经过账户、资源与请求代次检查，不能把刚清空的内容写回。401一般针对该登录代次，403按错误作用域处理；作用域无法准确判断时先隐藏该受保护视图并重新读取授权，不能继续显示未经确认的旧内容。

操作表逐项登记：`beginExperiment`、`finishExperiment`、`actOnTeacherIntervention`、`reportTeacherProblemResolved`、`reviewDiagnosisWorkflow`、`sendFeedback/recoverFeedback`、`submitCheck`、`releaseManagedSession`。已有反馈409测试作为不得破坏的契约。

## 6. R7/R8：工具输出与运行探针

- 密钥扫描只返回路径、行号、规则ID和固定提示，不打印匹配文本、整行、截断片段或未清洗异常。本机、verify、CI调用同一入口。若shell管道不能可靠区分“未命中”和“扫描失败”，内部改用标准库扫描器，保留脚本入口与非零失败语义；不可读文件、Git失败也不能报通过。用假令牌分别断言stdout/stderr/CI捕获内容不含秘密；中文、空格或换行文件名不得破坏记录边界。
- Compose健康检查改用现有 `/health/ready`，继续复用已有数据库检测；存活接口保留原职责。部署文档只链接同一个就绪契约，不另写一份判断。
- 验收初次就绪、断库unhealthy、恢复healthy。`depends_on: service_healthy`主要约束启动顺序，运行中unhealthy不会自动停止前端，`restart: unless-stopped`也不会仅因unhealthy自动重启容器；本修复不宣称新增自动故障恢复。
