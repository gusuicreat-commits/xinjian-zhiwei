# 芯鉴知微：产品背景与需求（PRD）

修订日期：2026-10-07。用途：后续开发理解产品目标、确定功能优先级和评估方案的背景依据。

本次根据用户对核心价值的明确说明重写产品定位：**利用设备采集到的、学生不容易直接观察或理解的内部运行信息，通过规则和 AI 辅助分析，帮助学生理解实验异常、缩小排查范围，并用新证据验证处理效果。**

本文定义产品意图与目标需求，不是上线公告或验收报告。下文功能要求均不自动表示已经实现；当前实现和外部验收分别以[实现状态](implementation-status.md)、[真实性看板](project-truth-status.md)为准。持续开发约束统一维护在[开发准则](development-guidelines.md)，本文不另建一套执行规则。本次核对基于 `38a3556` 及已有未提交工作区；没有运行硬件、模型或课堂验收。

## 1. 产品背景：学生看到的现象与设备运行过程之间存在信息差

嵌入式实验中，学生通常先看到外部现象，例如传感器没有读数、LED 没亮、数据异常或页面迟迟不更新。造成这些现象的环节可能位于采集、程序配置、设备通信、数据上传或平台处理等不同位置。

器材和软件内部已有的状态、错误事件与时序记录，学生可能无法直接获得，也可能无法理解或把它们与外部现象联系起来。教师需要反复询问操作、查看日志、核对版本，才能判断应该从哪里开始排查。只展示一条“读取失败”或给出通用检查清单，不能充分利用设备运行信息。

平台要解决的问题是：**让本来难以观察的运行过程有据可查，让这些证据能够帮助学生和教师作出更有依据的下一步判断。**

“内部信息”指通过固件、驱动、协议、已授权的软件记录或独立测量实际取得的可观测信息。信息可能是错误日志、运行配置、时间序列或状态记录，不限于硬件寄存器。没有采集的状态依然未知；AI 不会直接感知器材内部，也不能把预训练知识当成本次设备的测量结果。

## 2. 产品定位与核心价值

### 2.1 一句话定位

**面向高校嵌入式与物联网实验的设备运行证据辅助诊断平台。**

平台连接实验设备、课程资料、学生操作和教师经验，将实际运行证据组织为异常说明、有限候选、排查指导及验证记录。

### 2.2 价值如何产生

```text
设备或软件暴露运行信息
  → 平台确认来源、版本、时刻与实验归属
  → 结合实验预期识别异常
  → 规则与 AI 在证据范围内辅助分析
  → 学生理解依据并执行适用的排查动作
  → 收集新证据、重新检查或请求教师协助
```

| 环节 | 产品应带来的价值 | 前提 |
| --- | --- | --- |
| 采集与观察 | 获得学生不容易看到的运行信息 | 有真实采集生产方及明确含义 |
| 证据组织 | 把日志、读数、版本和操作关联到同一次实验 | 归属、时效、单位和来源可信且可追溯 |
| 辅助分析 | 将内部信息与表面异常联系起来，缩小合理排查范围 | 当前证据具有区分能力；不足时保留未知 |
| 指导与验证 | 让学生知道为什么检查这一项、如何观察结果 | 动作适用并符合课程与器材要求 |
| 教师复核 | 还原问题过程，补充确认并沉淀可复用经验 | 教师拥有对应权限，正式知识经过审核 |

AI 的主要目标是提高已有证据的利用质量，包括辅助关联多条信息、在允许的候选中排序，以及组织受约束的说明。聊天自然度、解释长度和工具调用次数不能单独代表这个目标已经实现。哪些判断由规则完成、哪些部分由模型辅助，以[模型规范内核](development-guidelines.md#model-core)为准。

### 2.3 固定实验与 AI 的关系

实验步骤可以固定，设备运行状态和故障表现仍可能不同。固定步骤不消除内部信息差，也不能据此否定 AI 辅助分析的价值。

能由明确规则完成的比较、状态计算和分支继续由程序执行；需要模型理解的复杂材料或候选关联，在现有合同范围内单独验证收益。是否增加自主查询循环，取决于证据获取需求。Pi、LangGraph、RAG 等技术选择不作为产品成功条件，本 PRD 不构成接入新框架、放开工具或修改架构的实施授权。

## 3. 用户与使用目标

| 用户 | 主要困境 | 希望得到的结果 |
| --- | --- | --- |
| 学生 | 只能看到外部现象，不知道设备内部哪个环节异常；难以理解日志 | 看懂当前异常、判断依据和未知项，知道下一项有效检查，并能查看新证据是否支持恢复 |
| 教师 | 难以同时观察多组设备，学生描述不完整，排查过程容易丢失 | 查看授权实验的证据与处理过程，识别需介入的问题，确认诊断与案例适用范围 |
| 实验内容维护者 | 实验要求、设备采集和诊断逻辑可能脱节 | 为每个实验明确可观测信息、来源、规则、允许动作及验证依据，并进行版本管理 |
| 系统维护者 | 设备数据、业务状态和模型结果需要稳定协作 | 能定位接入、处理或调用故障，核对审计与资源消耗，并区分软件故障和实验异常 |

## 4. 核心使用场景

以下为目标体验示例，内部信号存在与否必须按实际采集能力核对，示例不新增当前协议字段或诊断规则。

### 场景 A：表面相同，内部证据不同

学生反馈“温湿度没有显示”。平台先核对本次实验的实际记录：是否收到有效读数、是否有驱动失败事件、数据是否过期、是否属于当前会话，以及是否存在可核验的运行配置。

若有明确有效读数及对应时间记录，可据此区分“已有采集证据”与“没有有效采集证据”；若只有缺失数据，仍不能直接判断为断电、设备损坏或网络中断。诊断显示相关依据、证据能支持的范围和适用的下一步。

### 场景 B：命令已经发出，但物理效果未知

学生反馈“LED 没亮”。平台分别展示程序命令、已取得的电平观测以及实际发光证据的来源与状态。只有 HIGH 命令而没有独立电气或光学观测时，保留物理效果未知。后续依课程允许动作补充证据，避免把程序意图等同于实际效果。

### 场景 C：内部信息不足以区分原因

DHT11 连续读取失败，但没有实际配置、接线或独立测量依据。系统说明已经发现的异常，同时保留根因未确定；提供适用的待验证动作或教师求助入口。不能因某种故障常见，就把它写成本次已确认原因。

### 场景 D：处理后用新证据验证

学生完成检查后，平台关联操作时间和新上传记录，按照适用恢复判据重新检查。学生报告“已经解决”、教师结案和硬件恢复分别记录；没有新证据或缺少判据时，显示验证仍未完成。当前重新检查只分析已有上传数据，不自动控制设备采样。

## 5. 可观测信息与证据需求

### 5.1 每类信息应回答的问题

| 信息类别 | 能帮助回答的问题 | 不应直接推导的结论 |
| --- | --- | --- |
| 心跳、启动标识、运行时间与接收时刻 | 数据何时到达、是否来自同次运行、能否关联前后事件 | 无心跳必然断电；出现新启动标识就已知重启原因 |
| 错误事件、驱动结果与日志 | 哪个软件环节报告了什么异常 | 一个错误码证明唯一物理根因 |
| 有效读数及其时间序列 | 是否取得有效样本、变化或恢复是否有新数据支持 | 有一个数值就证明传感器精度或整个实验合格 |
| 实际运行配置及构建身份 | 设备实际报告的配置是否与实验要求一致 | 实验包期望值就是设备当前实际值 |
| 采集与上传过程记录 | 在记录覆盖充分时定位流程停在哪个环节 | 平台没有收到数据就确定上传失败的原因 |
| 独立测量、接线观察与学生反馈 | 补充软件遥测不能证明的物理状态 | 学生描述自动成为独立实测或教师确认 |

这些是需求分类，不是当前设备能力清单。现有设备接入以[设备协议](device-protocol.md)及实际固件为准，字段可传输不表示固件已生产或物理真实性已验证。

### 5.2 新增观测能力的完整交付

每个计划用于诊断的内部信号，需要在对应模块设计中明确以下内容：

- **生产方与测量位置**：谁产生该信息，反映变量、寄存器、驱动返回还是独立物理测量。
- **含义与适用范围**：单位、合法值、适用硬件和固件版本，什么时候该信息不可用。
- **来源与关联**：设备、实验会话、时间质量、版本，以及关联的操作或样本。
- **诊断用途**：支持或排除哪些候选，需要与什么其他证据一起使用。
- **缺失与冲突**：没有上报、过期、互相矛盾时如何表达，不能用默认值掩盖。
- **验证与成本**：真实对照记录、采集开销、对采样时序与存储的影响，以及受权展示方式。

具体字段、协议、规则和验证程序沿用对应契约维护，本文不定义另一份 Schema。

## 6. 功能需求与优先级

P0 表示实现产品核心闭环所需的目标能力；P1 表示在该闭环可信之后扩展的辅助能力。优先级不代表当前完成状态。

| 编号 | 优先级 | 产品需求 | 可检查的交付结果 |
| --- | --- | --- | --- |
| FR-01 | P0 | 为目标实验建立真实可观测信息清单 | 每个诊断输入可找到实际生产方、含义、适用版本及验证材料；缺失能力显式登记 |
| FR-02 | P0 | 采集和关联设备运行证据 | 数据归属、时间质量、测试身份和版本可追溯；迟到或重复记录不混入其他学生实验 |
| FR-03 | P0 | 将实际信息与实验预期对照 | 明确区分要求、设备报告、学生自述和独立测量；缺少实际值不能显示比较通过 |
| FR-04 | P0 | 基于证据识别异常并辅助分析 | 每个异常和候选有对应依据及适用范围；AI 遵守已有候选、引用和输出合同 |
| FR-05 | P0 | 展示学生能理解的诊断证据 | 页面说明现象、相关内部信息、支持的判断、未知项和下一动作，并可追到来源 |
| FR-06 | P0 | 连续记录排查与重新验证 | 操作、反馈、新数据和诊断轮次可关联；旧数据或重复反馈不伪装成新验证 |
| FR-07 | P0 | 支持教师介入与复核 | 教师在授权范围看到证据和过程，能记录确认依据、处理结论与仍未知事项 |
| FR-08 | P0 | 维护与实验相匹配的资料和知识 | 规则、候选、动作、案例和来源随实验版本管理；正式知识经过已有审核流程 |
| FR-09 | P0 | 让 AI 增强具有可控失败路径 | 模型不可用、超时或结果不合规时保留确定性诊断、证据和求助能力 |
| FR-10 | P1 | 辅助理解学生自由描述和复杂材料 | 对提取的信息保留原始出处与待确认状态，经独立评测证明有增益后再进入正式流程 |

FR-05 是目标体验。当前模型自由文字已有严格限制，概念解释也有待建设项；不能将该需求解释为允许绕过输出合同。具体扩展另行设计和验收。

## 7. 学生与教师的目标体验

### 学生诊断视图

一次诊断应让学生能够回答：

1. **现在发生了什么？** 当前现象与规则发现的异常。
2. **平台看到了什么？** 与本次问题有关的内部记录、发生时刻和来源类型。
3. **这些信息说明什么？** 已有证据支持的判断及其限度。
4. **还有什么不能确定？** 缺少、过期或冲突的证据。
5. **下一步做什么、为什么？** 当前适用的指导及其预期验证作用。
6. **做完以后发生了什么变化？** 新证据与处理前记录的对照，或仍未完成验证的原因。

默认展示少量相关证据和解释，保留查看详情的入口。不能仅堆积原始日志，也不能隐藏判断依据、只给一段模型结论。数据接收、设备运行、异常处理和恢复验证的状态分别表达。

### 教师复核视图

教师能够查看所属实验的问题、使用的包版本、关键证据、指导与反馈时间线及当前待核验点。教师确认应包含依据和适用范围；未经确认的学生反馈或模型判断继续保持原有来源性质。页面范围与私密信息投影遵守既有授权规则。

## 9. 如何验证核心价值

### 9.1 产品验收场景

| 场景 | 预期 |
| --- | --- |
| 外部现象相近，但存在可区分的内部证据 | 系统利用差异给出对应判断方向，能够指出具体证据 |
| 外部现象相近，内部记录也无法区分 | 保留候选或未知，不给确定根因 |
| 只知道实验期望，缺少实际配置 | 显示实际配置未取得，不报告配置一致或不一致 |
| 有设备命令，缺少物理效果观测 | 只报告命令事实，不断言器材已产生预期效果 |
| 新旧记录冲突、缺时刻或来源不适用 | 显式表达问题，避免沿用失效材料作为当前判断 |
| 学生处理后提供新证据 | 按对应判据更新验证状态，并保留前后来源 |
| 模型不可用或结论被拒绝 | 仍能查证据、使用确定性指导并求助教师 |
| 教师复核或知识来源失效 | 能追溯原依据，当前建议遵守既有复核与停用机制 |

### 9.2 分开测量“多看到了信息”与“AI 分析的增益”

设计效果评测时，区分两个问题：

- **可观测性的收益**：与只有表面现象或原有教学方式相比，新增设备证据是否帮助缩小范围、减少无效操作？
- **模型的额外收益**：使用相同内部证据、资料和界面时，规则诊断与规则加 AI 辅助相比，是否提高有效判断和理解质量？

模型对照不通过人为削弱规则基线制造优势。实物场景采用可复查的独立测量或教师确认作为依据，并保留无法确定的样本。单纯增加解释长度、模型调用次数或测试数量不计为诊断收益。

建议记录有依据判断的比例、无依据确定断言、正确保留未知的情况、学生找到有效下一步的时间、无效操作次数、教师复核工作量，以及响应时间和调用费用。样本量、课程判据、容许误差和目标数值应在正式试验前由对应负责人确认，本 PRD 不虚构准确率或效果目标。实施方法与报告分别沿用[测试与评测](evaluation.md)和[测试报告约定](test-reporting.md)。

## 10. 建设顺序与范围

1. **选定一个实验核实证据能力。** 列清外部现象、已有内部信号、缺失观测、来源与适用版本。
2. **建立真实对照。** 采集正常及单因素故障、处理后的记录，确认哪些信号能够区分原因。
3. **补齐确定性闭环。** 完善适用规则、故障树、指导、状态和验证判据，形成可信基线。
4. **评测 AI 的额外帮助。** 在同一证据条件下验证候选关联和受约束说明的作用。
5. **开展教师和课堂验收。** 检查学生是否理解依据、排查是否有效以及教师负担是否改善，再扩展实验范围。

以上为产品建设方向，不是本轮已执行计划。当前范围不包括自主修改硬件、自动确认物理根因、自动评分或未经审核发布知识；相关边界继续参见[开发准则](development-guidelines.md#model-core)。后续若证据分散且必须按发现继续取证，再独立评估查询机制，不把引入框架当作本路线的前置条件。

## 11. 后续开发如何使用本文

讨论新功能时，先说明它服务于哪类内部信息、哪项学生判断或哪段证据验证过程，并关联本 PRD 的需求编号。具体实施仍按[开发准则](development-guidelines.md)维护规则归属、契约、反例和验收；本文只维护产品背景与需求意图。
