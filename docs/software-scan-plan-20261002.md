| 代理到应用再到解析器 | 合法上限与超限、分块/慢请求、编码与解压展开 | 实际字节、耗时、取消与子进程回收、无半写、正常请求恢复；同一合法文件的直连/代理结果 |
| 当前实现到交付环境 | 锁定依赖、环境名、配置覆盖、迁移及不同平台 | 实际解析后的非秘密配置、构建身份、迁移与恢复结果、平台跳过范围；源码存在不代运行验收 |

并发取证用屏障、显式锁和独立连接控制顺序，避免用任意 `sleep` 猜测竞争。进程终止、断库、慢响应、坏文件只作用于明确的一次性资源；每个探针有总时限、资源上限与清理检查，不以拖垮主机证明风险。

## 执行顺序与验证方法

1. **建立独立预期。** 从开发准则和模块契约写下合法前提、成功效果、禁止副作用、失败后状态和显示含义，再查看实现。发现契约冲突先登记待决，不能用当前代码反向定义正确答案。
2. **完成清单与静态追踪。** 将所有实际入口映射到 S01—S17 和[规则表](development-guidelines.md#rule-map)。核对直接调用、异常分支、旧兼容、批量和读取投影。没有测试的入口不直接判失败，但必须安排证据或标出缺口。
3. **执行已有软件基线。** 按[完整本机门禁](evaluation.md#2-完整本机门禁)选择隔离环境，运行一次 `scripts/verify.sh`，不带 `--docker`。缺少单独平台、代理、崩溃等覆盖时登记补验项，不假定门禁包含所有专项。脚本中断后，把后续项标未执行并在原因明确后补齐必要阶段；不把分阶段通过描述成单次全绿。
4. **定向验证历史与相邻反例。** 31 项逐条核对当前保护和当前测试，扩查同规则入口。已有本次日志确实覆盖的用例直接引用；新增探针只解决尚未覆盖的问题，不重复累计测试数量。历史特征测试若断言错误行为，保留其历史意义，在本次目录另写正确预期。
5. **补真实交接证据。** 必需的PG竞态、进程终止恢复、Linux解析、真实Nginx传输和浏览器后端联调均按矩阵执行。SQLite不替代PG锁，Mock页面不替代真实后端，连接重建不替代进程崩溃。软件语义投影可用独立恶意输出夹具验证；真实模型因果和教学语义保持单独待验。
6. **验证测试有效性。** 对高风险共享授权、幂等/调用状态、当前建议与来源保护，优先复用已有有效反例。若测试可能绕过被测路径或只复述实现，在隔离副本或测试替身中暂时移除关键保护，证明断言会失败，并核对正常对照。只做能消除具体疑点的有限破坏测试，恢复后核对源码指纹。
7. **交叉审阅并收尾。** 对发现重新核对预期、复现层次、允许/禁止副作用、相邻入口和根因组；主审查者验证结论。清理本次不再需要的容器、schema、进程和临时文件，保留必要证据。若本轮仅扫描且源码不变，基线加补验完成后不机械重跑全套；后续修复按影响补测。

执行可由主 Agent 加最多两个独立审阅者协作，例如一人检查身份/状态，一人检查AI/资源；只在任务确实独立且有收益时委派。每项有明确输入、输出、版本和完成判据，数据库/容器/端口独立；共享事务设计、结论合并和文档由主 Agent 负责。换一个 Agent 不自动使预期独立，审查仍须基于业务规则与实际证据。

## 结果记录与缺陷归并

运行格式和日志边界沿用[报告约定](test-reporting.md)。本轮审计目录至少保留以下材料，允许在同一文件中合并简短记录，避免重复维护。

| 材料 | 最少内容 |
| --- | --- |
| `report.md` | 结论、检查范围、已确认缺陷、根因组、优先级和触发条件、未决与未验范围、命令及证据索引、清理结果 |
| `source-manifest.json` | 实际HEAD/工作区差异、被测文件指纹、非秘密依赖和配置版本、工具与环境；排除真实凭据 |
| `coverage.md` | S01—S17逐组展开的实际入口、规则、场景、所需证据层、测试/探针位置、本次结果和缺口；清单总数来自本次实际登记 |
| `history-map.md` | 原31项编号→当前规则/执行位置→回归/相邻入口→本次证据；历史复发、新入口遗漏、新根因分别标记 |
| 分组日志与复现附件 | 最小合成输入、操作顺序、独立预期、实际响应/副作用/显示、退出码及必要截图；失败基线与后续结果分开保留 |

覆盖执行状态采用 `not_run`、`passed`、`failed`、`blocked`、`not_applicable` 并附原因；这些是执行状态，不新增语义Rubric判定类别。Rubric继续使用符合/不符合，未审阅为 `judgement=null`。审查没有发现问题不等于行为验证通过，代码静态证据与运行证据分别注明。

每条发现必须有明确规则、触发前提、版本、最小复现、预期与实际、影响对象、代码位置及证据层次。无法复现的风险与已证实缺陷分开；不得仅凭大文件、宽泛异常、缺一个工具、潜在公网条件或历史PDF表述定性为Bug。

根因先按授权覆盖、状态时序、语义契约、验证盲区、资源边界、配置交付归纳，允许出现有证据的新组。同根因的多个入口可作为一条修复任务保留多个子证据，不把入口数当独立根因数；一个问题涉及多组时指定主组并交叉引用。报告分别列发现条目数、根因组数和受影响入口数，不预设本轮应发现多少项。

## 完成标准

- **覆盖可追溯。** S01—S17均有结论；实际入口清单与规则映射双向核对，没有无法解释的未分配入口。31项历史发现全部有本次去向；缺失历史附件不伪造通过，可用当前独立反例补证并注明。
- **关键时序有证据。** 适用的撤权/写入两种顺序、版本竞争、重复/冲突、断点恢复、来源失效、未知结果、资源耗尽与回收均有明确场景；关键组没有未说明的跳过。
- **检查真实副作用。** 关键拒绝验证响应、业务持久化与可见内容；幂等检查调用和计数；资源检查实际停止与恢复。合法对照和允许审计保留，不能通过封死正常功能来“通过”。
- **测试与版本绑定。** 日志对应实际源码、依赖和安全配置；测试真正执行且预期独立；失败、跳过、未执行分开；中途改动影响已验行为时补相应检查。
- **报告可审查。** 确认缺陷与风险、历史复发与新发现、根因与入口、软件与外部验收分别可查；必需取证缺失时可提交受阻报告，但不能标为完整软件验收。发现真实缺陷不妨碍扫描工作完成，受影响业务范围不得标为通过。
- **资源已清理。** 一次性数据库、容器、进程与测试副本均核对清理；无关工作区内容保留，必要复现和日志可追溯。

本轮目标是获得有证据的完整覆盖结论和可执行缺陷清单，不以缺陷数为零、测试数量增加或固定耗时作为完成条件。
