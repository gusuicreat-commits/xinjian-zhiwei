设计日期：2026-09-28；核对基线：`6eba821`。**状态：P0–P3已实施，P4保留后续阶段。** 用户随后明确授权按此方案实施；运行库未导入或发布新包。下文保留决策依据，当前合同已归入实验包、AI和评测文档。本文维护本次改造决策与实施顺序；持续规则仍见[开发准则](development-guidelines.md)，当前契约见[实验包设计](experiment-package-design.md)与[AI设计](ai-diagnosis-design.md)。

## 1. 目标、范围和依据

目标是让程序能回答：一条资料适用于什么条件、依据来自哪里、哪个阶段会使用它、本次实际提供了什么。保留“通用诊断引擎＋版本化实验包”，不增加通用RAG、向量库、文档浏览Agent或第二份手工AI知识库。

首期实施范围为P0–P3：补齐案例条件、建立来源关联、兼容新旧包格式、提供只读调用预检。P4单列概念解释的完整扩展设计，待首期完成及材料审阅就绪后推进；首期不因此开放教学原文外发。

## 2. 内容分工与唯一来源

```text
原始附件、源码、教师材料
  → 审阅后的配置／规则／案例／概念／步骤（现有十类工件）
  → 固定包版本＋当前任务快照
  → 程序筛选、按阶段投影、整单元预算与来源清单
  → 模型辅助输出＋独立校验
```

| 内容 | 唯一所有者与实际消费者 | 本次处理 |
| --- | --- | --- |
| 配置与正常/恢复要求 | hardware、rules、expected_behaviors各自现有字段；确定性引擎读取 | 登记权威字段及来源，不另存AI参数副本；包声明与实物核验分开。 |
| 候选和允许动作 | fault_tree；程序生成指导与允许动作 | 保持唯一动作入口。独立hints仍不覆盖它，本次不顺带统一两处文字。 |
| 经验案例 | cases或兼容全局案例；两路径共享匹配与投影 | 接通适用限制及有限结构化条件，保留审核四重门槛。 |
| 概念与实验步骤正文 | concepts、steps；明确bindings后用于教学快照 | P0–P3维持用途；P4只增加已审概念的受控解释，不外发整个步骤文档。 |
| 原始附件、私密审核材料 | 现有审阅资料/业务记录 | 保留来源定位，运行时不自动抓取URL、读取任意文件或外发全文。 |
| 测试输入与独立预期 | tests及评测夹具 | 只用于验证，期望答案不得进入builder或模型输入。 |

事实记忆引用配置及其确认状态，经验记忆引用受审案例，工作记忆来自本次业务记录/Checkpoint。三类记忆不要求复制三份资料包；当前任务的尝试、反馈和待办不写回静态包，也不自动晋升为经验。

## 3. P1：接通案例适用限制

### 3.1 数据合同

保留 `solution_record.confirmation_material.applicability_limits` 为限制正文的唯一来源；包文件对应已有 `solutionRecord` JSON。新增小型纯函数 `knowledge/applicability.py`（已建），包案例和数据库案例共用。只提取下表字段，不把整个解决记录、确认人、恢复诊断ID或学生材料交给模型。

| 内部投影字段（`case-applicability-v1`） | 含义及规则 |
| --- | --- |
| `limits_text` | 从已有字段原样提取的非空文本，沿用现有2000字符输入上限；外发前严格清洗，不能截句。 |
| `condition_status` | `text_only`或`matched`；表示尚只有人工文字，或所有已声明结构化条件通过。后者不认证自由文本语义或实际硬件。 |
| `checks` | P2才产生的有限结构化条件结果；来源是固定包/问题范围，不由模型填。 |

来源身份继续由案例ID、版本、来源hash及包身份承载，不在正文重复保存另一套版本。纯函数另返回固定省略原因，异常不带原始私密值。

消费路径为：包/全局来源 → 共用适用性处理 → `MatchedKnowledgeCase.applicability` → `AIKnowledgeReference.content.applicability` → 知识约束 → 推理/解释。独立知识验证使用通过资格检查的完整集合；预算只缩减模型参考集合，不能一并移除本地硬约束。

### 3.2 采用与缺失规则

| 输入情形 | 新请求处理 |
| --- | --- |
| 限制文字有效、未声明结构化条件 | 可作带条件的参考，标`text_only`；不能声称当前条件已满足，也不能凭历史经验确认本次根因。 |
| 已声明条件全部匹配 | 可进入原匹配排序，标`matched`；仍保留完整文字限制，匹配分不是根因概率。 |
| 条件不匹配／当前快照无法核实 | 整案例不进入本次新增强，分别记`applicability_mismatch/unknown`。 |
| 限制缺失、空白、类型错误 | 分别记`applicability_missing/invalid`并省略；不补“通用适用”。 |
| 清洗后案例连同限制超预算 | 整案例省略；不留结论而删条件。必需上下文不完整时取消本阶段增强。 |

资格过滤先于原有排序和top-k，避免不合格案例占满名额。包路径和全局路径保持原实验/错误类型、审核、测试范围、停用过滤及稳定排序。代码不判断自由文本限制是否在本次满足；提示明确其为条件性参考，语义采用情况需独立审阅。

新审批仍要求原有确认材料；旧案例有有效材料即可只读提取，无需批量回填。缺材料的旧案例仍可作为历史记录读取，但不再供新AI调用。这是明确的兼容收紧，可能增加确定性降级。无合格经验时沿用`ai_require_knowledge`和既有策略，不停掉诊断、反馈或求助。

学生解释继续保留后端限制声明；有`text_only`参考时由后端补充“参考案例的适用条件尚未自动核验”。具体经清洗条件随现有知识引用保存，不依靠模型自行提醒，也不把条件写成已验证事实。

### 3.3 隐私、版本、重放

服务层在来源仍完整且已授权时提取临时私有`sensitive_sources`或敏感值集合，仅供本次builder清洗；不放入公开MatchedKnowledgeCase、Checkpoint、日志或响应。随后才投影允许字段，避免删掉审核字段后漏掉正文中重复的秘密。注入文字始终是资料，不是指令。

P1使用`case-applicability-v1`和新上下文策略版本；推理、解释Prompt版本同步增加，输出结构未变时不冒称输出Schema升级。实际payload hash、条件投影版本和源hash共同参与缓存及审计。

同`workflow_run_id + call_stage`旧结果有提前重放路径，必须一并改造：若记录不能证明已执行新条件投影，继续作为当前建议时采用确定性结果；不补造历史清单、不修改原AI记录、不自动再次调用同阶段。检查完成后直接返回final_result、幂等检查回执、反馈返回及学生当前页也须共用只读的当前建议投影，不能只检查模型调用函数。持久化回执和已发生的业务效果不变；授权历史视图可展示标明旧策略的原快照，当前建议视图不把它表述为新策略通过。新显式检查才走新请求流程。来源在途变更、撤回和权限变化仍在调用返回及交付时重验。

## 4. P2：来源登记、有限条件与格式兼容

### 4.1 保留十文件，新增有版本的登记块

已新增包格式`1.1`，在`metadata.yaml`中增加严格的`content_registry`；不新增第十一份必需文件，不用自由dict扩充行为。表内是设计字段，当前`1.0`解析器尚不支持。

| 登记对象 | 最小字段与约束 |
| --- | --- |
| `sources[]` | `source_id`、来源种类、版本/修订、位置、页码/章节/代码定位、可取得状态、可空原附件hash。版本或附件未知明确为空及待补，不伪造。 |
| `units[]` | `unit_id`、工件路径、实体种类、实体ID或受限字段选择器、陈述性质、`source_refs`、`derived_from`。只定位已有正文，不另存一段摘要；性质区分来源陈述、项目配置、实测结论和待验证建议。 |
| 单元`applicability` | 仅概念/步骤登记所需的`limits_text`与可选有限条件，作为这两类说明的条件来源；案例直接读取3.1的唯一来源，禁止再填一份；规则/硬件的可执行含义仍归原字段。P4外发概念必须有经审的必要限制。 |
| `source_refs[]` | 来源ID、支持的字段/主张定位及原文位置。引用完整性可由代码检查，原文是否支持主张需人工审阅。 |
| `derived_from[]` | 原全局案例或外部包单元的ID、版本、hash、`snapshot/adapted`关系；未知来历明确缺失，不按文字相似度认定同源。 |
| `value_owners[]` | 参数的唯一权威字段定位，以及可确定比较的重复字段位置/单位。禁止表达式、脚本、模板执行与任意路径访问。 |

实体选择器仅允许现有十工件、已声明ID和后端注册的字段；拒绝缺失、重复、循环及越界引用。内部依赖通过本包unit_id关联，外部来源不在运行时自动读取。维护者预检时显式提供可信来源快照才能计算并比对派生hash；不符则失败，不可取得则标`unverifiable`，只能验证格式，不能声称来源链已核实或作为P4已核验依据。来源文件hash只证明内容身份，不证明材料真实或得到教师确认。

单元身份由服务器生成：`package_version_id + package_hash + unit_id + unit_hash`。unit_hash依据正文、必要条件及来源关联计算，连同包hash保存在生成报告/运行审计中，不写回被哈希的包正文，避免自引用。更改来源、条件或派生关系同样要求新包版本。

已有 `sourceRef/references` 为旧路径兼容保留；1.1登记块负责精确关联，冲突时报告待修订，不能悄悄覆盖。审核状态属于服务器审核记录，包作者不能填写一个`approved`就自行获得模型外发资格。

### 4.2 有限可判定条件

在已有`confirmation_material`中增加可选、严格解析的`applicability_conditions`：`version=1`、声明时至少1项且最多10项条件；首版字段只有`experiment_code`、`package_version`、`component_id`，操作只有`in`（单值也用列表，每项1–20个非空字符串）。拒绝空块、空值、同字段重复条件和未知字段，避免空集合被判为matched；未声明才是text_only。实验来自固定实验身份，包版本来自固定发布快照，组件来自单一明确的问题范围；全部条件按AND执行，值做精确匹配。

package_version或component_id条件必须同时声明对应experiment_code，避免跨实验同名。条件不填当前包hash作为自引用；实际调用身份仍通过包hash验证。未绑定包、组件范围歧义或字段缺失产生unknown，不用当前设备绑定或最新配置补全历史。

更复杂的实物型号、固件语义、测量值和安全前提仍写在限制正文，不从文字自动推断为可执行条件。后续只有建立可信字段来源和反例，才扩白名单。结构化条件只服务采用范围，不修改异常阈值或硬件恢复判据。

### 4.3 写作模板与参数一致性

每个案例围绕一个诊断主题整理“现象—依据—适用范围—已确认结果—限制”；来源长附件另存。概念说明同时区分来源陈述、当前配置和待确认事项。DHT11先作为编写样板，LED作为跨实验对照，仍保留测试、draft、unknown，不制造教师签署。

首期登记已有参数的权威位置，并对明确声明的重复结构化值做单位与相等检查。自然语言中的数字是否与事实一致不能靠关键词扫描证明，仍需审阅。涉及参数的展示句子以后可由受限的服务器模板生成；本期不引入通用模板语言，也不批量改写全部文案。

### 4.4 旧包兼容

按metadata.schema_version分派1.0/1.1解析、校验和序列化；保留1.0的默认值及规范化行为，不能用新模型的默认字段重写旧包。旧库加载直接以原保存文档核验hash；新增登记只属于新版本。Manifest的文件哈希算法与十文件集合不变。1.0的来源登记状态记为未提供，不能反推历史来历；P1可读取其已有文字限制，新结构化条件要求1.1，不能在1.0任意JSON中偷加后静默生效。全局案例的新条件由版本化审批Schema写入，旧记录不回填。

新引擎兼容版本为`2.2.0`，1.1包声明`>=2.2,<3.0`；当前两包已采用该合同。启用新字段还须明确格式能力校验，不能只凭版本字符串跳过。工作区DHT11/LED发生内容变化时分别递增包版本并更新清单；具体新版本在实施基线冻结，运行库旧包不自动导入或迁移。

P1–P3复用现有JSON列，不计划新增数据库表/列。新全局案例的条件仍保存于solution_record，现有源hash已覆盖；1.1包的元数据和来源登记由包hash覆盖。部署新解析器先于使用新包；回退旧程序只能服务其支持的旧包，新包明确拒绝，不尝试丢字段读取。

## 5. P3：生成调用预检，连接资料编写与实际输入

已新增只读CLI `app.cli.preview_package_context`，接受包目录、明确标为合成的场景文件、预算配置白名单及输出路径。先把matcher资格筛选、适用性检查和投影整理为运行/预览共用的纯函数，返回合格单元及受控筛选轨迹；不从现有top-k结果倒猜遗漏原因，也不复制第二套筛选逻辑。复用阶段builder、Prompt构造和估算器；不发布包、不连接Provider、不改业务库。离线身份使用明确合成标识，不伪造真实库版本ID；报告标`offline_fixture`，线上权限为`not_evaluated`。

场景提供固定包身份、错误类型、候选、问题范围、当前证据、允许动作和阶段；预期结果另存，由评测器读取。草稿案例如实报告无资格，不为预览临时改成已审核。需要已审路径的回归用独立明确标测试的夹具，不修改两包的真实状态。

生成JSON/Markdown到`output/package-context-preview/`（已建）。每份报告至少含：

- 源码身份、包/单元hash、场景与预算配置指纹、投影/Prompt版本；脱敏后的必要定位，不保存密钥。
- 每个阶段的候选资料、资格结果、实际选中单元、必要依赖、清洗后长度、完整Prompt的token估算、固定省略原因；内部受权报告可列ID，公共响应仍不泄露无权资料数量。
- 分开的`structure/source_traceability/stage_coverage`结果，不把文件合法、来源充分和模型可用合成一个“已就绪”。样例不全则覆盖待补。
- 真实Provider、语义、硬件状态固定为未运行；预算数值不写成永久内容标准。

报告生成本身退出0只表示分析完成，可包含“无合格案例/预计降级”；解析或执行错误退出1，必需场景/预算材料缺失退出2。独立评测增加严格模式，期望不符退出1；预期就是降级的反例可以通过。完整门禁调用严格模式，不用“报告生成成功”替代断言成功。

默认沿用项目现有预算，不因材料多而自动加限额。预检需分别验证推理和解释：同一案例在两阶段的投影不同，不能只量一次原文长度。

## 6. 生命周期与P4概念解释扩展

### 6.1 写入、召回、更新、遗忘

写入时登记来源与必要条件；召回时按固定范围检查资格，再按阶段选择；更新通过新版本，同时核对关联规则、说明、样例和缓存。全局案例撤回只触发明确关联包的影响候选，不自动撤销包；改名副本通过derived_from定位，历史无关联仍标覆盖未知。包撤回、来源不可用、交付重验和过期缓存清理复用现有治理；原证据、指导快照、Checkpoint及备份不会因删除源文档而自动删除。

### 6.2 P4必须同时解决输入、输出和展示

只允许与当前固定指导的树/原因/组件/等级显式绑定、经审阅的少量概念，进入**解释阶段**。步骤正文继续作为学生参考；引用概念不能成为Evidence UUID、确认案例或新增允许动作。该能力采用独立默认关闭开关，仍受总AI开关控制，不新增一次模型调用、不绕过ai_require_knowledge。

审核复用现有`AuditEvent`，新增专用材料审核动作：操作者须有`knowledge.review.approve`及所列来源的当前读取权限，不能由查看班级或发布包权限推导；确认一份冻结清单，事件绑定版本ID、包hash、单元ID/hash、用途和支持依据。普通包approved/published事件、作者署名和软件预检均不能替代该记录。按包父记录锁顺序串行，等待后重验权限和版本；审核与审计同事务。幂等身份为`版本ID＋操作者＋request_id`，同载荷返回原事件、异载荷409；所有入口持同一父记录锁并使用严格事件Schema。首版撤销该外发资格沿用明确整包revoke；细粒度单元撤回留待独立设计。无此审核记录不外发。

P4的`guidance_ref`由后端从当前指导身份及允许动作定位生成，概念引用ID由包hash和unit_id生成；不要求模型发明身份。内部保存全量身份对应关系，外发只给稳定、不含用户身份的引用；映射属于本次封存输入，重放不得用新动作顺序重新解释旧索引。

| P4合同（拟定） | 完整路径与限制 |
| --- | --- |
| 输入 `teaching_references[]` | 独立于knowledge案例数组，最多3个当前绑定概念；只含本地生成引用ID、已审正文、必要条件、状态和允许动作关联。单元清洗后上限起点1000字符且共享总预算，按bindings原次序去重；超限整条省略。 |
| 输出 `teaching_explanations[]` | 新增可选数组，最多3项；每项`guidance_ref/concept_ids/text`，text起点上限300字符。引用必须属于本次已提供集合，guidance_ref只能指向现有指导/允许动作；步骤、异常、候选及计数合同不变。 |
| 本地校验和展示 | 检查类型、引用、绑定及长度；无效教学项丢弃并保留既有解释/原文。显示在当前指导旁，标“AI辅助理解”，保留来源、条件及资料状态。自由文字正确性需独立语义验收，关键词扫描不充当安全证明。 |
| 审计和兼容 | 输入、输出、缓存、前端类型与渲染同步版本化；概念提供/引用在manifest独立记录，包来源继续由MemoryUse跟踪；不塞入case_ids。旧输出缺数组默认空，不补历史参考或再调用。 |

这些容量是首版工程约束，不是效果最优值，须用预检与独立样本核对。软件接通后只有取得真实、已审内容和模型对照证据，才评估是否启用；当前两包草稿不因此获得正式经验或概念审核资格。

以下是必须覆盖的场景组，不是预先声称的测试数量。预期由项目规则和审阅材料独立给出，测试不得从被测选择器反推期望。

| 编号 | 代码必须断言的结果 |

| PKC-01 | 限制只存在原审核JSON时，包/全局路径在实际Mock推理与解释请求中都完整携带；确认人、恢复ID、私密材料不外发。 |
| PKC-02 | 缺失、空白、类型错、未知结构字段分别拒用/拒解析；不生成“通用适用”，其他合法案例可补入top-k。 |

| PKC-04 | 审核、测试性质、实验/错误类型和权限过滤不因新字段放宽；无权限资料不出现在公开遗漏统计中。 |

| PKC-06 | 仅改变限制使源/输入指纹变化；缓存、原call-stage快捷重放、Checkpoint恢复、完成工作流/检查/反馈返回和迟到结果均重验，不额外收费调用、不改持久化原回执。 |

| PKC-08 | 来源/单元ID缺失或重复、循环、越界路径及可核验来源的hash不符被检出；来源不可取得明确未核验，内部引用不形成包hash自引用。 |
