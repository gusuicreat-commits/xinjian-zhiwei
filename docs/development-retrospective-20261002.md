# AI 辅助开发缺陷复盘

日期：2026-10-02。本文面向后续开发者，解释项目在主要教学流程成形后仍反复发现缺陷的原因，以及 AI 辅助开发可能放大这些问题的机制。持续生效的要求统一维护在[开发准则](development-guidelines.md#defect-prevention)；本文保留复盘依据，不另维护一套业务规则。本轮如何检查见[全项目软件扫描方案](implementation-status.md#软件限制)。

核心判断是：功能已经成形，但跨模块、跨时间的约束没有完整覆盖。局部功能正确，不保证多个入口、并发操作和恢复流程组合后仍然正确。让 AI 阅读更多要求有帮助，真正减少复发还需要把要求落实为共享执行位置、完整入口清单和独立反例。

## 事实范围与归因边界

本次复盘采用 2026 年 9 月底至 10 月初三批审查，共 7＋9＋15 条历史发现。第三批由 Agent 审查的 8 条和综合核对新增的 7 条组成。条目之间存在共同原因和相邻入口，31 不是独立根因数量，也不是当前待修缺陷数量。各轮范围不同，发现数量不能直接说明质量变差。

还要区分两类对象：用 AI 编写软件的开发过程，以及软件内部调用模型的运行过程。报告证明了具体缺陷及其触发机制，没有逐项重建最初生成过程，也没有人工开发对照。因此，下文对工程缺口的归纳有项目证据；对 AI 如何放大缺口的说明属于机制分析，不能表述为全部缺陷都由 AI 造成。

## 同一规则没有覆盖全部入口

工单补了锁后撤权检查，诊断审核、记忆治理仍可能遗漏；诊断返回时检查建议是否有效，仪表盘读取旧记录时却可能再次展示。局部实现各自维护授权、来源或状态判断，规则就会随入口分化。

这反映了完成单位偏向某个接口或文件，验收没有完整追踪同一规则的所有调用方。共享函数已经存在，也不能证明其他入口都调用了它。HTTP、服务直接调用、图节点、CLI、旧接口、重放、批量操作，以及列表、统计、导出和缓存，都需要按真实可达路径核对。

AI 的任务上下文如果只包含几个文件，可能生成局部成立的修复，却没有发现其他入口。这是影响范围不完整的风险。OWASP 授权指南要求每个请求正确执行权限检查，并建议采用全局一致的机制，避免逐处补检查造成遗漏。[官方依据](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 状态正确不等于状态变化过程正确

有权限成功、无权限失败，两条测试都通过，仍然可能出现“有权限进入 → 等待锁 → 撤权 → 继续写入”。旧草稿覆盖已发布内容也有相同结构：读取时允许编辑，使用旧快照时已经不允许。

这是检查与使用之间状态发生变化的问题。MITRE 将其定义为 TOCTOU 竞态缺陷；校验与后续操作需要在正确的锁和事务边界内形成保护。[官方依据](https://cwe.mitre.org/data/definitions/367.html)

模型调用恢复则涉及外部副作用：Provider 已收到请求，本地尚未保存结果就退出，恢复后再次发送。没有收到成功结果，不能推出没有执行；预算预留、调用日志和重试次数也不自动保证幂等。AWS 的工程文档说明，安全重试需要明确请求身份，并处理副作用与记录的一致性。[官方依据](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

顺序阅读代码容易忽略这些交错过程。需要主动画出等待、撤权、提交、响应丢失和恢复的时间线，并测试关键事件的两种先后顺序。外部系统没有相应保证时，不能承诺跨系统恰好执行一次。

## 数据格式通过了但含义发生变化

| 真实含义 | 历史错误解释 |
| --- | --- |
| 模型建议核验 | 已确定缺少证据 |
| HTTP 明确拒绝 | 操作结果未知，需要继续等待 |
| 清除浏览器登录信息 | 服务端凭证已经失效 |
| 进程能响应 | 数据库可用，业务已就绪 |
| 引用和结构合法 | 自由文字中的因果结论也可信 |

这些错误可能通过类型检查，返回合法 JSON，并在页面上正常渲染。缺口在于字段、错误码和状态的业务含义，没有在生产方与消费方之间始终保持一致。

如果没有明确契约，AI 可能用常见写法补齐项目特有的含义。GitHub 官方提醒，生成代码可能看似有效，却不符合开发者意图，需要核对实际需求。[官方依据](https://docs.github.com/en/copilot/responsible-use/agents)

本项目尤其需要保住证据等级：观察、规则异常、候选、待核验、教师确认分别表达；后端、缓存、历史投影和页面不能通过文案或默认值把弱依据升级为事实。

## 测试与实现可能共享错误假设

七项审查中，已有完整软件门禁通过，独立构造的反例仍然发现问题。这证明已有用例没有覆盖相应约束，不能仅用测试数量评估保护是否完整。

一种可能的 AI 开发风险是：实现假设“进入服务就已经授权”，测试也使用始终有权限的夹具；实现和测试相互吻合，真正的业务约束没有进入测试。这是机制分析，现有记录不足以证明每份历史测试都这样产生。

独立预期应来自已确认的业务规则。例如，明确拒绝后没有成功业务写入；旧来源停用后不能作为当前建议；旧请求恢复不产生第二次物理调用。测试需要观察响应、数据库、审计、外部请求和实际页面，而不只检查 helper 返回值。合成环境的拒绝审计等允许副作用与禁止业务副作用分别断言。

GitHub 的 AI 代码审查指南要求核对架构和意图，检查遗漏场景、虚构 API、忽略约束，以及是否通过删除或跳过测试处理失败。[官方依据](https://docs.github.com/en/copilot/tutorials/review-ai-generated-code)

## 局部资源限制保护不了整条处理链

原文件大小受限，不表示解压后的内存和 CPU 消耗受限；后端允许的文件，不一定能通过代理；单次网络读取超时，不表示完整调用存在总截止时间；输出 Token 配置，也不等于客户端接收字节数上限。

这些限制分布在代理、框架、解析器、传输客户端和业务层。每层都有保护仍可能存在交接空隙。OWASP 文件上传指南明确要求考虑解压后大小与处理风险。[官方依据](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

AI 可以快速生成正常输入可用的实现；若任务只以正常功能完成为验收条件，容量、故障和取消过程容易遗漏。资源预算需要在处理之前或处理过程中生效，并验证超限后真实停止、回收资源，随后正常请求仍能成功。实际容量目标尚未确定时，不能从有限合成测试推导生产容量。

## 完成说明需要对应交付证据

本地修复、软件测试通过、Git 提交、远端同步、业务库迁移、服务部署、真实模型效果和硬件课堂验收是不同事实。完整的文字说明或大量通过数字不能代替各自的证据。

配置的多个默认来源、旧接口兼容和不同运行平台也会导致差异。开发者需要核对交付源码、依赖、迁移、配置与目标环境；报告明确本次执行、跳过、受阻和未执行的范围。

## 后续开发怎样使用这份复盘

常见的 AI 辅助开发风险包括上下文遗漏、用默认模式填补需求、实现与测试共享假设、局部补丁积累、语义与意图不一致，以及虚构 API 或依赖。最后一类属于通用审查重点，本次 31 条记录不能证明项目已经发生该类问题。

后续开发采用[开发准则中的缺陷预防要求](development-guidelines.md#defect-prevention)：记录规则归属和所有入口，明确时间顺序与禁止副作用，以独立预期验证真实交接，再按交付层次报告。对纯文档、样式等低影响改动保持相称检查，不机械新增测试或流程。

NIST SSDF 的 RV.3 要求分析共同原因、寻找类似漏洞，并调整开发过程来减少复发。更换模型或追加一次自审可以提供帮助，完成证据仍要由可检查的实现和独立验证提供。[官方依据](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf)
