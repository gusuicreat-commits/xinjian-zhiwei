# 受控上下文建设实施方案

设计日期：2026-09-28。状态：**P0–P3软件已实施，最终门禁结果见实施报告；P4真实效果待验收**。用户确认后于同日实施；未启用运行环境AI或迁移业务库。本文维护建设顺序、改动位置和验收依据；持续规则仍以[开发准则](development-guidelines.md)为准，当前实现见[AI 设计](ai-diagnosis-design.md)。

目标：让系统能说明“本次需要什么材料、哪些材料合格、实际提供了什么、缺口在哪里”，并保证预算处理不破坏材料条件。本期沿用固定工作流和结构化知识匹配；不建设通用文档切块、Embedding、向量库、模型重排或自主检索循环。

## 2. 本期范围与完成定义

本期软件交付包含三个产物：共用的上下文准备逻辑、每次实际AI阶段的来源/省略清单、独立的上下文评测报告。优先复用现有模块；新增模块限于内部Schema、准备函数和评测适配器。暂不增加数据库表、HTTP端点、学生页面或第三方运行依赖。

软件完成必须能用实际路径证明：不适用材料进不去；选中的关键材料不会被悄悄截断；材料不足时明确省略或走确定性降级；审计准确区分匹配、实际提供和输出引用；新老缓存/恢复不串版本。软件完成不等于真实模型效果、实物或课堂验收完成。

以下不属于首期：给模型新增概念卡/教学步骤原文、将 `memory_context` 整包外发、自由查询改写、自动生成事实、自动发布经验、通用聊天、额外模型调用、扩大留存或副本删除范围。以后若需要，分别设计外发契约和验收，不借本方案自动启用。

## 3. 内容建设与信息缺口

先以DHT11为样板，LED用于检验同一逻辑能否跨实验适用；不新增DHT11专用代码分支。内容维护者按既有[资料包流程](development-guidelines.md#package-content)整理原始来源、事实清单、正常流程和排查卡，使用现有来源字段及审阅材料，不向严格包Schema临时塞字段。（B1、B4、B9）

| 所需信息 | 读取方式 | 缺少时的处理 |
| --- | --- | --- |
| 固定配置/课程约束 | 当前绑定包版本，按已有ID和字段读取 | 标明未提供/待确认；不使用模型常识填参数 |
| 本次观测、规则结果、候选关联 | 当前诊断已落库证据及确定性结果 | 沿现有unknown/待核验路径；不把资料当本次观测 |
| 可复用经验 | 当前包或兼容路径中的合格案例 | 记录无合格参考；沿用 `ai_require_knowledge` 与已有降级策略 |
| 当前进度/反馈 | 本会话、本问题的业务记录和工作流 | 区分学生自述与已验证结果；不跨学生拼接历史 |
| 教学原理/实验环节 | 现有概念和步骤的明确绑定 | 首期继续用于已有展示，不因此加入Provider输入 |

缺口按阶段记录，不能凭空推断全库没有资料：

- `no_eligible_reference`：本次授权、版本和测试范围内没有合格匹配结果；线上不泄露无权资料的存在或数量。
- `policy_omitted` / `budget_omitted`：已经可用，但被明确策略或预算排除；记录阶段与原因。
- `scope_unavailable` / `source_changed`：来源当前不可用或在途变化，不能继续作为新建议交付。
- `context_incomplete`：无法在输入约束内完整保留本阶段必需内容，停止该次增强并走现有确定性路径。
- “源未收录”“源存在但未审核”“合格源未匹配”“提供正确但解释错误”是离线诊断分类，须由完整的授权评测语料和独立预期判定；不能仅从一次空召回自动推导。

这些是内部上下文状态，不新增硬件故障类型；没有对应公开契约时不直接透出内部代码。资料建设与软件可以并行，尚无真人材料的场景只标合成，不填写虚构确认人、时间或根因。

## 4. 最小实现结构

保留原图节点和两类AI职责。改造集中在现有调用前的准备边界：

```text
当前授权与固定版本 → 读取本次证据/候选及合格案例
                 → 按阶段投影、完整性检查、隐私清洗、预算选择
                 → 封存实际payload与内部manifest
                 → 原有调用治理、推理/解释
                 → 原有输出校验、来源和权限重验、持久化/交付
```

新增 `backend/app/ai/context_contract.py` 和 `context_builder.py`（已实施）：前者只定义内部类型，后者组织纯投影/打包逻辑，不查询数据库、不调用Provider、不写历史。服务层负责授权、锁、读取与来源快照，使用现有matcher/memory/governance；推理和解释保留各自的输入适配器，不能合并成一个无限制字典。（B2、B3、B5）

拟定内部返回值 `PreparedContext` 包含：本阶段已清洗payload、被完整保留的来源引用、`ContextManifestV1`。推理仍返回现有 `AIReasoningResult`，解释仍使用 `AIDiagnosisInput` / `AIStructuredExplanation`；manifest不作为模型输入。

本地校验必需与外发必需分开，不能为“补完整”增加外发字段：

| 阶段 | 现有输入中要完整保持的约束 | 本地负责的事项与合法空值 |
| --- | --- | --- |
| 原因排序 | `_reasoning_prompt` 现有 `error_type`、`candidate_causes` 及关联 `evidence_registry`、`allowed_verification_actions`；已提供的 `experiment_context/knowledge_constraints` 保持完整单元 | 原因排序当前没有单独外发 `evidence_conflict` 字段；完整证据冲突由本地检查并强制约束输出，不能新增字段或整包State。候选/证据为空走既有unknown逻辑，不补引用。 |
| 学生解释 | 当前 `rule_matches/fault_tree_guidance/allowed_evidence` 及既有 `workflow_state` 白名单中的推理状态、冲突和允许动作约束 | 仅使用当前已允许字段；规则摘要、限制和动作仍由后端合同约束。缺独立实测保持unknown。 |
| 两阶段共同 | 已提供参考的来源身份和条件、固定版本、测试性质，以及各自原有字段白名单 | 权限和停用检查保留在本地。显式空动作列表是合法约束，不等于截断丢失；未配置资料按既有缺省规则处理，不能凭空变成必填内容。 |

实施时把该矩阵细化为两组内部校验器，对“原本就为空”和“构建过程中丢失”分别断言。不得依据模型声称“信息够了”决定完整性。

| manifest字段组（拟定） | 含义与保存边界 |
| --- | --- |
| `contract_version`、`stage`、`policy_version` | 上下文合同、推理/解释阶段和选择策略；版本名称实施时冻结，不冒充已存在 |
| `prepared_source_refs` | 准备提交的来源种类、ID、版本、内容hash；复用MemorySource身份，包案例与全局案例分开 |
| `provider_attempted`、`submitted_source_refs`、`cache_origin` | 持久化时按实际分支填充；无Provider尝试则submitted为空，缓存命中记录缓存派生来源。客户端调用不证明服务商已接收或模型实际利用。 |
| `selected_ids`、`omission_counts` | 当前阶段的证据/案例标识及省略原因计数；不记录无权材料标识，不复制原文 |
| `required_complete`、`reason_codes` | 能由代码验证的本阶段结构/引用/必要信息是否完整；不表示语义充分或根因确认 |
| `payload_sha256`、`prompt_hash` | 清洗和选择后的准确payload与实际Prompt指纹；不得用原文hash冒充外发内容hash |
| `budget` | 实际字数、项数、沿现有算法的Token估算和采用上限；估算不冒充服务商真实Token或费用 |

优先把清单写进现有 `AICallRecord.input_snapshot.context_manifest`，保持已有键。调用未发生也沿用既有跳过/降级审计入口，不增加一次“记录清单”的模型调用。AI关闭、普通GET和纯确定性请求不为本方案额外写AI记录。历史无清单标识为旧版未知，不用今天的来源补造过去的清单。

清单容量跟随本阶段既有Schema和材料上限：只列实际选中身份，省略对象按固定原因汇总计数，不保存全量被拒列表。服务层交给builder的是受权快照；纯函数不能自行获取额外对象或把无权内容写进错误信息。

## 5. 选择和预算的具体规则

1. **先限定资格，再排序。** 复用固定包/兼容全局分支、审核四重门槛、实验/错误类型、权限与测试限制；保留当前确定性排序，暂不引入新的打分算法。当前案例没有独立必填的型号适用字段，不能宣称已有通用型号过滤：只比较既有明确结构化约束，不从症状文字猜型号；任务确需型号而无法核对时保持未知并按必需信息缺口处理。调试信息不能扩大查询权限。（B1、B2）
2. **按完整关联单元组织材料。** 候选与其证据ID、原因标题和支持信息一起处理；知识默认以一条当前允许投影的案例为单位，包含其适用条件。不得只保留结论而删除条件/反例。模型当前拿不到的字段不因“补上下文”被加入。（B1、B3）
3. **清洗与压缩分开。** 敏感值识别仍覆盖原始授权输入，不能先删字段导致其秘密在另一字段漏检。新增严格路径能报告“需要截断”，而非先截断再声称完整；脱敏可能使文本变长，长度按清洗后结果计算。用于判断或限制的文本超长时，不让代码猜哪半句重要：可选案例整条省略，必需内容走 `context_incomplete`。来源ID/版本等必需身份与秘密冲突时拒绝增强，不用脱敏占位符伪造新身份。原有日志摘要按既有白名单处理，不能混为证据原文。结构化对象只能完成选择后整体序列化，不截JSON字符串。（B1、B3）
4. **先校验全部可信输入中的冲突，再限制数量。** 已有冲突、unknown和允许动作约束属于必需内容。先为图内上游第51条证据等边界建立反例；需要调整时，在服务层从完整授权证据临时读取后选择，不能仅修下游builder而假设上游没丢资料，也不扩大Checkpoint或改规则判据。如果某候选必须依赖的证据单元不能完整放入，本阶段不生成基于残缺关联的排序。不能把真实证据合成新UUID。（B1、B3）
5. **使用已有容量和预算。** 起点为现有配置：案例默认5条、知识正文默认1000字符、输入Token估算默认4000；它们是配置基线，不是研究证明的最优值。先去掉重复引用及低优先级可选案例，保持稳定顺序，再用现有估算器校验实际Prompt（含Schema）；必需内容仍超限就降级，不自动加预算、不调用模型压缩。（B3、B5）
6. **只去掉同一次请求中的相同身份副本。** 同来源、同版本、同hash可去重；同一句话来自不同观测不能直接合并，已有设备重传规则继续独立负责去重。多轮可以复用同一依据，使用前重验；不按session已读列表永久排除。（B1、B5、B9）

“完整关联单元”的首期实现采用明确字段组合和整体省略，不尝试自动识别自由文本里的全部条件。若一条合法案例本身过长，应在后续资料修订中人工整理短且完整的版本，走审核和新版本发布；本次软件不得改写旧包来凑预算。

独立知识校验继续检查可信完整材料中的硬约束，不能通过“模型没看到这条案例”绕过限制；模型输出的案例引用则限定于本阶段实际提供集合。可信校验集合与模型输入集合分开命名和测试，避免删除可选参考时一并删除安全约束。

## 6. 来源、缓存与恢复

- `matched`保留匹配集合；准备集合放manifest，只有实际调用尝试时才将提交payload的来源记为`provided`，不承诺服务商已接收/模型已利用；`cited`再按有效输出引用登记。预算拒绝、治理拒绝和缓存命中不生成本阶段新provided关系，缓存沿用derived来源。被预算排除的案例不能仍被记为已提供。沿用现有MemoryUse唯一键和业务事务，不另建来源账本。
- 选择时捕获原来源快照，清洗/打包后封存payload；Prompt构建后不再静默改内容。Provider返回、缓存命中、恢复与最终交付继续重验来源、权限和包状态，变更时丢弃迟到结果，实际调用仍记账。
- Prompt使用实际payload计算hash；缓存额外纳入上下文合同/选择策略版本，防止只变选择语义但误用旧缓存。输入投影变化须同步推进相应Prompt版本，输出Schema没变不能冒称输出Schema升级。
- 原 `(workflow_run_id, call_stage)` 幂等身份不变。旧完成阶段不因升级再调用模型；旧记录按现行来源和输出合同重验，通过才可重放，但不能回填manifest或计为新策略效果。若已知旧输入损坏或不能通过现行验证，返回确定性结果并保留历史。未执行阶段用新准备逻辑，恢复后仍以原固定证据和包版本为输入，不偷换最新观测。
- 不改Checkpoint存储、不批量重写历史。新manifest使用已有JSON容器；旧读者须能忽略附加键。实施时同步AI/API/数据库文档对审计含义和兼容边界的说明，公共响应Schema无变化也要核对序列化路径。
- 回退保留记忆治理和停用检查；必要时用现有AI关闭开关保留确定性服务。经反例确认不安全的截断路径不作为生产回退模式；旧实现仅用于冻结的隔离对照。（B1、B5）

| P2 接入和追踪 | `reasoning.py`、`context_sanitizer.py`、`services/ai_diagnosis.py`；`ai_call_records` JSON、MemoryUse | 实际Mock请求、审计、来源用途、缓存与幂等相符；新旧入口/恢复均受完整性与停用保护 | B1、B3、B5 |
| P3 分层评测 | `app/evaluation`、`backend/evaluation`及受影响测试；见下一节 | 必需代码断言通过；真实输出材料可供人工审阅；未运行语义/模型/硬件项目明确留空 | B1、B7 |
| P4 内容与真实效果 | 资料维护者、教师、硬件负责人分别提供来源与确认；已有受权模型环境中做冻结输入对照 | 不把合成资料升格；按独立样本比较实际输出、遗漏、耗时、调用与费用。未完成则仅交付软件行为，不宣称诊断效果提升 | B1、B4、B6 |

P0–P3的主要工作集中后端；新UI、库迁移和外部检索都不是前置依赖。资料整理可与P0–P3并行，不能绕过审核发布。没有真实来源也能验证拒用草稿、unknown和软件边界；不能据此验证真实诊断准确率。每阶段完成后按实际结果估算剩余工作量，不在缺样本/教师安排时承诺固定交付天数。

主要代价是完整案例可能超过现有预算，导致更多确定性降级。P0先统计哪些现有合法样本受影响，P3逐项解释变化；不能为了提高AI调用成功数删掉限制条件或悄悄增大预算。P4所需的真实资料、教师审阅和模型环境分别记录就绪状态，缺项不阻断独立软件建设，也不算已完成效果验收。

## 8. 评测数据、场景与门槛

新增 `backend/evaluation/context_inputs.json`、`context_expectations.json`，以及 `app/evaluation/context_runner.py`、`app/cli/run_context_evaluation.py`（已实施）。输入包含合成/脱敏来源、身份范围、固定版本、证据、阶段及预算；期望单独保存合格来源ID、禁止来源ID、必须保留的字段/关联、可接受省略及预期降级。期望只能由评测器读取，禁止传给builder或Provider。

样本先按会话/问题/来源版本分组划分调试集与保留验收集；同一案例的改写和派生样本不能跨两组。验收材料若用于调参，就转为回归材料并补充独立验收集。合成资料仅用于软件边界，真实语义材料另记来源和审阅人。结构化资格期望来自业务规则，事实/语义预期来自独立手册或核验材料，不由matcher或模型输出反推。（B1、B7）

| 场景ID | 必须检验的结果（每个确切判断拆成独立断言） |
| --- | --- |
| CTX-01 | 正常合格案例被选中；引用、版本、hash与实际提供内容对应 |
| CTX-02 | 未审核、未确认、未锁事实或质检未通过分别排除；空召回不等于搜索失败 |
| CTX-03 | 错实验、错版本、跨班、测试混正式分别不能提供；已有可比较型号约束不匹配时拒用，必需型号无法核对时保持未知；不泄露被拒对象 |
| CTX-04 | 长JSON保持可解析；尾部否定、单位、适用条件完整保留或整单元省略 |
| CTX-05 | 冲突证据在数量边界外时仍不能被隐藏；缺必要关联时停止增强 |
| CTX-06 | 可选内容超限整单元退出；必需内容超限返回确定性降级，无Provider调用 |
| CTX-07 | 相同来源副本不重复提供；跨轮必要依据仍可复用；不合并不同实测事件 |

| CTX-11 | 隐私清洗覆盖两类AI输入；清洗后变长仍受限、身份冲突不伪造版本；注入文本不能改变外发字段和动作集合 |
| CTX-12 | 规则计数、候选、动作、升级保持既有职责；方案关闭AI、只读GET时无新增调用/写入 |
| CTX-13 | 评测器对“无源/不合格/漏选/预算省略”按独立夹具分开归因，不泄露期望 |

| CTX-15 | 仅有DHT11失败或LED命令时，历史案例不增加本次实测证据、不更改其unknown状态；自由解释是否暗示已确认另作语义审阅 |

语义条目只在现有 `semantic_rubrics.json` 增补需要的定义：理由是否受材料支持、条件与冲突是否表达完整、是否保留本次未知、是否回答当前问题；尽量复用既有SEM/COT条目，避免同一要求重复计数。人工基于实际模型输出与独立材料逐项判“符合/不符合”；未审阅保持 `not_run/null`，不做关键词语义判定或模型总分。

报告拟用 `context-evaluation-v1`：分别记录 `code_checks_passed`、各阶段选择/省略原因、语义审阅状态、版本与源码/输入指纹、实际调用/耗时/费用。可记录独立期望几项、匹配几项、最终提供几项；无合格材料不进入召回分母，已知错误版本和越权不能被覆盖率抵消。输出到 `output/context-evaluation/` 的JSON+Markdown，复用现有报告封装但确保不丢语义状态；新增CLI拟定退出0仅代表代码检查完成且通过，1为代码失败，2为环境/必需软件材料未完成，并在报告显式表达语义等范围是否未完成。现有synthetic/workflow CLI的退出码含义保持不变。

验收门槛：所有适用必需代码断言通过；至少对截断和错误来源保护做隔离破坏反例，证明测试会失败；冻结的正常路径不存在未解释的退步；必需语义项未审完不能宣称语义通过。不得预设“准确率提高20%”或用平均分抵消越权、错版本与无依据结论。真实模型对照固定模型/输入/包/预算，只改变上下文策略，预先规定重复方式并保留全部运行，不挑最好结果。

验证顺序为受影响单测→实际服务与隔离PostgreSQL→固定工作流/缓存/恢复回归→必要的浏览器交付复核；跨整条链路的变更执行[完整门禁](evaluation.md#2-完整本机门禁)。命令以届时已实现CLI和测试指南为准，本方案不把尚不存在的命令写成现在可执行的操作。

## 9. 后续可选的资料检索试验

仅当“合格资料已经存在，却因不同表达或跨文档定位而持续漏取”有独立样本证据时进入。优先服务教师资料整理，其次为受限实验原理问答；与诊断事实判定分开设计。（B4、B8）

离线比较现有结构匹配、关键词/全文检索、可选Hybrid Search。只有前一步暴露具体不足才增加下一层，重排也须单独证明价值。型号、错误码、权限、包版本、停用和测试边界仍做硬约束；返回原文位置和条件，不能把相似案例升级为当前根因。

进入产品前须另行明确：资料导入/OCR/原文定位、索引与来源版本一致性、撤回传播、外发许可、缓存、容量和成本，以及在冻结验收集上的净收益。GraphRAG、Agentic RAG、自动Wiki回写均不包含在这条试验的默认授权中；文档篇数、MB/GB大小或第三方榜单不单独构成选型门槛。
