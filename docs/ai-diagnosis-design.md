## 架构选择与实现入口

LangGraph 编排固定诊断流程，不负责自主规划。AI 默认关闭；不可用或校验失败时沿用规则、
故障树和已匹配知识生成确定性结果。Provider 使用现有轻量客户端，不叠加多智能体封装。

当前结构化案例规模有限，字段匹配能直接说明匹配原因；故障类型和候选又必须分别来自规则和
故障树。因此诊断不使用 RAG、Embedding 或向量召回。历史 pgvector 迁移和旧字段只作兼容；
未来扩展须先有独立需求、召回评测和架构决策，不因保留旧表就恢复旧链路。

2026-09-28形成[上下文完整性合同](ai-diagnosis-design.md#上下文完整性与后续取舍)：优先改善现有材料的完整打包、来源清单与分层评测，暂不增加通用RAG架构。该方案的P0–P3已接入，采用整单元预算选择与内部来源清单；实际验收见实施报告，P4真实效果待验收。

[资料包与上下文合同](experiment-package-design.md#格式11来源登记与案例条件)的P0–P3已实施：接通案例适用限制，增加来源登记和调用预检；P4概念解释保留后续阶段，教学原文仍不外发。

## 固定流程与状态

```text
context_builder → rule_engine → fault_tree_analyzer → knowledge_context
                → ai_reasoning → knowledge_validation
                    ├─ rejected → teacher_review
                    └─ accepted → ai_explanation
```

| 节点 | 输入与产出 |
| --- | --- |
| `context_builder` | 由固定输入构建 `DiagnosisContext`，读取设备、日志、读数和实验预期 |
| `rule_engine` | 输出唯一的错误类型、规则 ID、观测值和证据；包化规则取固定版本，旧请求保留文件定义路径 |
| `fault_tree_analyzer` | 分析命中规则对应的候选，计算支持分、分级提示及教师介入建议 |
| `knowledge_context` | 提供已审核实验约束、正常条件、故障映射和确认案例；案例须匹配当前错误类型 |
| `ai_reasoning` | 在已有候选中排序，返回支持等级和关联证据；失败或越界时确定性降级 |
| `knowledge_validation` | 不调用模型，检查规范、引用、候选、错误类型和允许动作 |
| `ai_explanation` | 将已约束结果组织为学生解释 |
| `feedback_handler` | interrupt 等待 `resolved/unresolved/request_teacher_help`，使用原 thread 恢复 |
| `escalation_handler` | 依据异常证据轮次、持续时间、提示等级及反馈确定升级与教师介入 |

`route_after_explanation` 在无异常时直接持久化，首次异常后进入升级判断，反馈后的再次解释
回到等待反馈。升级后按教师条件、未解决反馈、剩余问题和结束条件分支到审核、知识供给、
继续等待或持久化。教师 approve/edit 后保存，reject 后终结；工单结案不是这条审核边。
`teacher_review/persist_result/reject_result` 都是流程基础设施。

`DiagnosisState` 保存上下文、规则证据、候选、知识、推理、反馈、缺失证据、包版本、输入指纹、
流程身份及节点指标。原始输入快照在业务库，checkpoint 只保存经投影的有界状态；外发清洗另行执行。
`state_revision` 是审计修订，不是并发锁。流程、诊断结果、问题和会话的 ID 分别使用，不可互换。

## 模型输入与输出契约

推理输入为设备事实、规则结果、故障树候选、知识上下文和历史失败信息；解释输入另含知识校验结果。
推理、解释和润色各自建立字段白名单，再由公共清洗器处理敏感值与嵌套文本。设备标识匿名化，相关
日志限量，读数/心跳投影为摘要，知识按完整案例单元选择，超量时整单元省略；学生身份、密钥、Wi-Fi、联系方式和教师私密备注
不进入 Prompt。必需引用与敏感值冲突时取消增强，不改写证据 ID；AI 关闭不依赖外发投影成功。
精确字段及长度以代码为准，不在本文维护第二份 Schema。

| 输出 | 当前约束 |
| --- | --- |
| `AIReasoningResult` | `conclusion`、候选排序、关联证据、简短理由、限制、待核验信息和下一动作 |
| 排序项 | `cause_id/cause/support_level/used_evidence_ids/reason`；最多 20 个候选，每项最多 30 个有效相关引用 |
| `unknown` | 排序为空；无有效关联证据时仍保留当前允许动作 |
| `AIStructuredExplanation` | `error_type/evidence/possible_causes/steps/hint_level/need_teacher_help/summary/limitations` |

`error_type` 与规则一致；原因属于故障树；证据使用本次已落库 UUID，并与具体候选相关；案例 ID
来自本次匹配结果。降级先判断完整证据的冲突，再按固定顺序截取。支持等级不是统计概率，合法引用
也不证明因果。只有 DHT11 累计读取失败而无接线/独立测量依据时，不能推断某个 GPIO 根因。
HTTP 响应使用 snake_case，实验包 camelCase 不另构成 HTTP 契约。

最终 `steps` 逐字选择工作流允许动作，显式空列表保持为空；没有该字段的旧调用只能选择
已持久化故障树指导的 hints，不能从任意知识正文补步骤。`hint_level/need_teacher_help` 取确定性升级结果。
`summary/limitations` 由后端解释契约生成，自由文字不直接升格为事实。当前契约
`explanation-boundary-v6` 列出规则异常和 unknown 状态，保留证据冲突。模型自由理由和
missing_evidence不进入当前展示或下阶段输入；仅将本次允许的下一动作呈现为未执行指导，
不把动作改写为已经缺失的观察。没有合格指导时提示教师帮助。解释模型补写的限制不直接采纳。

响应、持久化解释和回放使用同一契约。缓存纳入实际 Prompt 哈希并重新校验；旧 v1 审计不改写，
缺当前契约或校验失败时返回 `rules_only`，不再次付费调用，不作为新建议展示。输出投影本身不回填历史；调用恢复的0038另保存有界Provider结果，不保存完整原始私有输入。
新推理Provider合同v2.14将 `reason/summary` 固定为服务器生成占位文字，`limitations/missing_evidence`只能为空；服务端用已验证状态生成实际说明，严格新响应拒绝任意补写。解释Schema的摘要/限制明确为后端合同常量，后端继续执行交付投影。历史记录仍经兼容解析和安全投影，不改写或收费重生。候选选择和引用的语义关系、教师编辑、完整因果与电气安全仍需独立审阅，代码通过和模板保护不能代替。

## 知识来源、版本与案例沉淀

案例定义见 [`KnowledgeCaseDefinition`](../backend/app/schemas/knowledge_case.py)。产品简写
experiment/causes/steps 对应 `experiment_type/possible_causes/solution_steps`，不另建知识模型。

包化诊断从 PostgreSQL 锁定包快照读取 `knowledge/cases.yaml`，推理后再从可信快照重载并核验 ID。
旧 `backend/knowledge/cases/` 和 `knowledge_cases` 表服务未包化请求。两条路径均要求
`approved + confirmed + facts_locked + quality_check_passed`，并过滤实验、错误类型、测试身份和版本；
先精确匹配 error_type，再校验 experiment_type，最后按显式证据加分，不做语义召回或 LLM 重排。
匹配结果保留规范、步骤、教师经验和来源版本；没有匹配仍可返回规则与故障树结果。

AI 只读取固定版本产生的投影，不执行包代码、不拼接其他实验或版本。包结构、导入校验、审核发布和
旧空关联的兼容边界统一见[实验包设计](experiment-package-design.md)。

案例沉淀流程为：

1. 保存诊断事实、证据、规则/树版本；学生提交 resolved 后产生 `KnowledgeCaseDraft`，根因仍 unknown。
2. 模板绑定事实快照；AI 只润色 `title/symptomDescription/teachingNote/solutionSummary`，每项保留 `sourceIds`。
3. 质量检查失败留在 draft，通过进入 pending_review。
4. 审核人提供根因确认材料和真实解决动作；候选外根因先修订。审批成功才产生符合四重门槛的正式案例。

草稿以原状态和版本条件更新；审批与正式案例插入同事务、来源草稿唯一。润色在锁外调用模型，返回后
重验权限和版本，迟到结果不覆盖审核。学生报告解决不能独自确认硬件根因，全局案例发布也不改写旧包。

## 反馈、降级与审计

- 反馈绑定目标问题、会话和原请求身份后恢复原 checkpoint；未解决继续原输入，新数据由显式检查冻结。
  刷新与回执查询不运行图。身份重验、完成回执和新检查状态投影见[API 契约](api-design.md)。
- 三个模型入口共用持久化预算预留，重试和失败按实际尝试记账；估算预检不代表服务商账单硬上限。
  退避及额度锁等待后，在新预留或成功结果重放前重验当前教学范围、来源及运行时操作者；身份回调不进入Checkpoint或操作指纹。进程额度锁限时获取，PG治理短事务使用事务内锁/语句时限，超时回滚并返回明确降级原因；已经完成的历史调用可在原发送时限之后安全重放，不重复外发。
  未配置、超时、限流、预算或结构校验失败时降级；知识校验拒绝的流程转教师。
- `ai_call_records` 保存触发原因、模型、Prompt/Schema 版本、耗时、Token、案例 ID、校验及降级原因。
  `call_stage` 区分首次及各反馈轮次的推理/解释；输入快照是受限投影，不保存密钥或完整敏感 Prompt。
- 旧 `chunk_id/knowledge_references` 容器中的新值为结构化 case_id，不表示 RAG Chunk。
  checkpoint 保存可恢复状态，业务流程表保存可查询审计；二者都不替代原始数据和诊断事实。
- 语义审阅按 Rubric 逐项“符合/不符合”，关键词仅作线索，不用分数或模型裁判替代依据。
  正式条目及执行状态见[评测要求对应表](evaluation-requirements.md)。

## CoT 分步证据核对

用户确认实施后，第一版已接入 `ai/reasoning.py`，当前Prompt版本为 `evidence-reasoning-v2.14`（显式冲突输入及错误类型输出契约修复；原分步核对从v2.6引入）。在原有一次推理调用内，模型按下面的顺序核对材料，只返回现有 JSON 字段中的简洁结果，不输出完整思维过程。

| 顺序 | 要做什么 | 谁负责把关 |
| --- | --- | --- |
| 1 | 分清设备报告、规则结论与待验证原因，沿用已计算的数值和状态 | 规则与代码确定异常，不交给 AI 改判 |
| 2 | 逐个检查已有候选的证据支持什么、不能证明什么 | 候选、引用和关联集合由代码校验；理由语义另行审阅 |
| 3 | 保留冲突；没有区分依据就给 unknown，排序结果为空 | 代码检查 unknown/候选一致性及冲突约束 |
| 4 | 从现有允许动作中选择下一步，空集合返回 null | 动作逐字匹配，建议不能冒充已执行 |
| 5 | 用已有 reason、summary、limitations 等字段表达简洁依据与限制 | 既有独立知识校验与后端解释契约 |

例如：只有 DHT11 读取失败记录，缺少实际接线和代码引脚对照时，提示要求保留“原因尚不能确定”，不能凭相同症状认定接线或 GPIO 配置错误。这个语义要求已写入提示，但还需要真实模型与独立材料验证效果；Mock 返回 unknown 只证明软件能正确处理该结果。

### 运行与兼容

- 保持原图、Schema、Provider、thinking 设置、外发字段、预算和重试上限。AI 默认仍关闭；在已有授权启用 AI 的环境中，新推理请求使用新提示，不新增模型调用阶段。
- 确切事项继续由代码检查；模型自查不替代断言。`reason/summary` 是待审阅文字，不是设备证据或内部思维过程的真实性证明。
- 候选结果仍按支持等级、再按 cause_id 排序；同等级不能声称已可靠区分先后。最终学生摘要和限制仍由后端控制，不整段展示模型分析草稿。
- 推理失败沿用确定性降级；独立知识校验拒绝仍转教师。继续旧指导沿用旧快照，新数据须显式重新检查，不自动控制硬件。
- 新审计记录 Prompt 版本及哈希。旧版本已完成调用按当前结构/引用约束重验并沿用原记录，不重新付费调用，也不改写为 v2.6；旧结果不能计入新提示效果比较。解释缓存继续沿用现有输入指纹和重验机制。
- 本轮没有新增 Schema 版本字段或内部思维链存储。回退时成对恢复原提示正文与版本；保留历史审计，不改写已发布实验包。

### 检查与尚未验收的部分

新增软件检查验证真实服务路径下的一次 Mock 调用、请求字段与审计哈希、越界动作拒绝及旧版本重放；既有回归继续覆盖原因/证据越界、冲突、缺测、注入、隐私、解释与反馈流程。执行证据见[实施报告](../output/audits/cot-implementation-latest/report.md)，这些检查不证明真实模型推理质量。

6 项语义条目已纳入 `backend/evaluation/semantic_rubrics.json`（COT-SEM-01 至 06），分别审阅理由有据、未知保留、冲突限制、建议未冒充执行、解释与结论一致、表达清楚尊重。由现有合成评测报告逐项列出 `not_run/null`；没有用关键词或模型打分冒充语义审阅。条目正文只在目录中维护，映射见[评测要求对应表](evaluation-requirements.md)。

历史v2.5/v2.6对照尚无此处要求的独立证据；2026-10-03已进行同实质规则、不同顺序的合成CoT对照，未显示该小样本增益。实际材料见设计效果报告，不能把删除实质规则的对照归因为CoT。调试与验收样本隔离；不得只挑最好结果或用旧审计冒充新运行。thinking 是另一变量，本次未开启。只有证据支持改善且原有边界无退步，才能声称效果提升。

## 记忆生命周期方案（2026-09-27）

**目标：记住可追溯的事实和已审核经验；知识出错时，能停用、查影响、修正并处理副本。** 用户已授权按本方案实施；能力与验收状态见[实现状态](implementation-status.md)，本节的目标不自动代表已完成。沿用[知识生命周期规则](development-guidelines.md#business-rules)，不改变规则判异常、故障树给候选、AI受约束解释的分工。

### 1. 三类记忆：事实、经验、工作

保留现有业务库和固定工作流，在其上补充来源关系与生命周期管理，不另建一份重复的“万能记忆库”。本期不引入学生画像、跨学生经验自动迁移、向量库或自主学习。

| 记忆类别 | 存什么 | 在本项目中的例子与边界 |
| --- | --- | --- |
| 事实记忆 | 在明确范围和版本内已经确认、相对稳定的信息 | 经核验的设备型号、指定固件的引脚配置、已审核实验要求；配置值不等于实际接线，当前测试草稿中的待确认项不能冒充实物事实 |
| 经验记忆 | 经验证、能在相同条件下复用的排查教训 | 某类已确认案例的适用条件、有效检查、失败尝试和局限；相同症状不等于相同根因，案例步骤不能扩充故障树允许动作 |
| 工作记忆 | 当前任务继续执行所需的最小上下文 | 当前会话/问题、固定包版本、证据引用、已尝试动作、反馈、未知项和待办；只服务本任务，恢复前重验权限、知识和包状态 |

**原始证据和历史记录是三类记忆的来源，不自动等于事实记忆；缓存、导出和备份是副本，不是第四种认知记忆。** 例如“一次读数失败”属于本次观测，不能沉淀成“这个传感器一直有问题”。三类是逻辑职责，不要求各建一套数据库：事实沿用已确认资料与版本记录，经验沿用正式案例及包快照，工作状态沿用业务表和Checkpoint。尚未审核的草稿留在候选区，不进入正式经验召回。

| 类型 | 写入与最小信息 | 召回 | 更新与遗忘 |
| --- | --- | --- | --- |
| 事实 | 记录对象、属性/值、信息性质（配置/实测/课程要求）、来源证据、确认人、适用版本和有效范围 | 按对象、版本和权限精确读取；冲突材料保留并标记待核验，不让AI选一个当真 | 信息变化生成新版本或失效记录；普通替代保留旧版本适用范围，错误事实停用并追踪影响；删除遵循证据保留要求 |
| 经验 | 记录触发条件、已验证结论、操作与结果、反例/不适用条件、来源案例、审核及版本 | 沿用实验/错误类型等结构化匹配；返回适用依据和局限，不直接套用历史根因 | 新反例进入复核，不靠使用次数自动提升可信度；修订重新审核，错误版本停用；低频本身不是删除理由 |
| 工作 | 记录任务身份、固定版本、当前状态、证据ID、动作/反馈及其时刻、待办和修订号 | 按会话/问题/工作流身份精确恢复，只取本次相关片段；不混入其他学生或其他任务 | 用新事件更新当前投影，状态与计数由代码计算；任务结束停止作为活动上下文，按恢复及审计策略保留，再清理临时副本 |

事实记忆用于解释和核对已有约束；诊断仍执行版本化规则、故障树和代码判据，不能从自由文字记忆临时生成新阈值。工作记忆中的“尝试过”需区分学生自述、系统记录和独立验证；一次尝试无效不能自动排除某个根因。

三类之间的流转拟定为：**适用的事实＋已审核经验＋本次新证据→工作记忆→受约束诊断；任务结束后，有价值的结果→候选事实/经验草稿→独立核验与审核→长期记忆。** 任务完成、AI总结或同一结论重复出现都不能跳过审核。工作摘要仅帮助恢复，保留来源ID、版本、未决问题和冲突；原始记录才是回查依据，摘要不能成为新的证据。

### 2. 写入、召回、更新、遗忘

| 环节 | 拟定流程 | 谁作决定 |
| --- | --- | --- |
| 写入 | 事实先落库并关联证据；解决反馈形成草稿；核验根因、适用条件和修复后观测后审核发布 | 代码校验身份、关联、版本、必填项和重复请求；教师确认专业事实。AI只辅助表达 |
| 召回 | 先检查当前权限、实验/会话范围、测试身份、固定版本和可用状态，再做现有结构化匹配；只传入本次必要材料 | 代码决定能否使用；AI不能把无权、未审核或停用内容选回来 |
| 更新 | 新事实追加记录，修订经验形成新版本并重新审核；记录替代关系与原因，不覆盖旧事实或已发布快照 | 教师审核内容；代码保证版本冲突检测、事务和来源唯一 |
| 遗忘 | 先区分停止使用、归档保存、物理删除；停用立即影响后续使用，删除另按保留策略和引用关系执行 | 业务负责人确定保留和删除范围；代码执行范围校验与逐项验证 |

召回不仅是读案例：缓存命中、Checkpoint恢复、旧指导继续、历史结果重新展示都可能带回旧内容，因此都接入同一套可用性检查。交给模型前及交付结果前再次核对；查不到必要状态时暂停相关增强/指导并转教师，不猜测可用。历史审计使用单独的受权视图，不能直接当作当前建议。

只使用当前问题的有关历史，例如“已经尝试过哪一步”；次数、时间、阈值和状态仍由代码计算。学生自由文字是待核实陈述，不作为系统指令。知识ID、Evidence UUID和工作流ID保持不同语义；不存储完整内部思维链。

### 3. 出错后怎样闭环

```text
发现问题 → 定位来源和版本 → 停用明确对象 → 查找依赖与受影响记录
         → 教师复核影响 → 审核修订版本 → 显式采用新版本
         → 按策略清理副本，并验证不能重新带回旧内容
```

1. **登记与停用。** 记录问题材料、报告人、审核人、原因和精确版本。普通更新可以保留旧任务版本；事实错误或安全问题由有权限的人员执行撤回/撤销。疑似问题尚不能直接定为错误，必要的预防性停用也要明确对象和负责人。
2. **案例和包分别处置。** 全局案例撤回只作用于全局路径；列出包含它的实验包，由有包管理权限的人明确选择需要撤销的版本。不能静默改写包，也不能宣称案例撤回就已全部停用。案例已撤回但相关包待处置时，整体状态为“部分完成”。
3. **反查影响。** 从来源版本查到包、诊断、工作流、指导、调用和缓存；分别标注“仅收录/提供给模型/被输出引用/已交付”。这些都不是“已造成误诊”。教师逐项判断无需处理、需要补充核验或需要更正指导，留下依据。
4. **控制后续使用。** 被撤销包的任务停止相关教学建议，保留采集与历史；不能继续引用同包的故障树动作来冒充安全降级。学生看到“该指导已停用，请联系教师”；教师可看受权历史、停用原因和待复核对象。旧回执和诊断事实不改写，当前响应另附可用状态并屏蔽失效建议。
5. **修订后显式采用。** 新版重新走审核发布；旧任务不自动换包、不自动重诊断。教师按现有会话流程安排后续任务，学生显式检查新数据。修订版本与原版本、复核结果互相可追溯。

已发出的页面、下载文件和离线副本无法保证实时收回；在下一次服务端交互时核验，已登记的导出列入处置清单。教师处置页区分“待告知、已告知、已复核”，不能把生成清单当作已联系学生。

### 4. 最小实现结构与并发边界

拟在现有服务中补充以下能力；这里列逻辑职责，不冻结表名和HTTP Schema。实施时同步数据库、API契约及迁移设计，不新增独立记忆服务。

| 能力 | 最小记录与约束 |
| --- | --- |
| 来源关系 | 来源类型、稳定ID、内容版本/哈希、目标类型/ID、使用方式、业务范围、测试标记、时间；包内案例用“包版本ID＋包哈希＋案例ID”定位，不能只凭case_id跨包串联 |
| 治理事件 | 操作者、原因、精确目标清单、预期状态/修订、请求身份、实际结果；内容版本与停用修订分开，撤回状态改变也使旧校验失效 |
| 影响复核 | 治理事件、受影响对象、关联依据、复核人、结论和后续动作；同一事件/对象幂等，未知关联明确标为待核实 |
| 副本处理任务 | 目标存储与对象、处理方式、前置条件、状态、尝试及验证结果；与治理事件同事务登记待执行任务，再由可重试任务处理 |

来源关系与业务结果同事务保存；Checkpoint等外部存储通过任务登记和后续核对补齐。旧记录只根据已有明确ID、版本和快照补关系，不凭相似文字或时间猜来源；追溯报告同时给出已覆盖、关联缺失和未核实范围。

所有使用入口复用同一服务判定可用性。停用提交后不依赖缓存清理完成才能生效；最终交付检查与停用操作通过同一范围的锁/修订校验排序，不能“检查后无条件交付”。权限也在等待锁后重验。网络上已经发出的响应不能追回，按已交付历史列入影响范围。

模型在锁外运行；回来后如果权限、包状态或治理修订变化，丢弃不再适用的输出，按实际尝试记费用，不自动补一次模型调用。异步任务失败可重试，不能撤销已完成的停用。各对象独立报告结果，不假定业务库与Checkpoint跨存储原子提交。

### 5. 遗忘必须覆盖副本

| 存储位置 | 停用后 | 获准物理删除时 |
| --- | --- | --- |
| 原始证据、诊断、反馈与确认材料 | 保留历史，加关联的停用/更正说明 | 先核查活跃任务、审核和证据引用；受保护记录不进入删除批次 |
| 正式案例、实验包固定快照 | 案例撤回、包显式撤销；不改正文 | 有历史依赖时保留或归档；不能靠外键级联抹掉整条诊断链 |
| 指导快照、AI调用投影、Checkpoint | 保留受权审计；恢复和展示时拦截失效内容 | 分别定位嵌入的正文；只删源案例或只删workflow业务行都不算清理完成 |
| AI缓存及以后新增的检索索引 | 禁止命中相关内容；异步失效/清理 | 删除派生项并核对；TTL只管理这类可重建数据，不决定证据寿命 |
| 导出、备份、外部服务副本 | 登记可控制范围与未确认副本 | 自管导出逐项处理；备份按到期策略管理，外部服务需取得实际处理依据，不能声称全都已删除 |

物理删除另走“清单预览→负责人确定范围→阻止新引用并等待在途任务结束→重新核验→分存储处理→验证”的流程。保留时长按数据类别由负责人确定，本方案不虚设统一天数；当前 `retention_dry_run.py` 只统计超龄数量，不能直接作为安全删除清单。

删除计划固定对象、版本和范围；执行前发现新增引用或状态变化则跳过并报告，不能扩大到新对象。逐项记录待处理、完成、失败和验证情况；部分失败不显示全部完成。需保留的审计只存最小必要标识和处理结果，不复制被删除正文；无法继续提供的历史明确标为已清理，不补造证据。

备份恢复前，在隔离环境重放独立保存的停用/删除记录，再检查业务库与Checkpoint，完成后才允许提供服务。删除记录本身纳入受控保留与备份，避免随旧库恢复一起丢失；旧备份尚未到期或外部副本未确认时，只能报告“在线范围已清理”，不能报告“所有副本已删除”。

### 6. 验收与分期

以下是验收条件；实际执行证据见[实现状态](implementation-status.md)。确定性结果必须以实际服务路径、数据库与Checkpoint结果作代码断言，不能让模型自行判定通过。

| 场景 | 必须验证的结果 |
| --- | --- |
| 未审核、跨班级/任务/实验、测试与正式数据混用 | 均不能进入本次召回；无关历史不进入模型输入 |
| 工作总结、学生自述或一次观测被申请沉淀 | 未经核验与审核不得进入正式事实/经验记忆；配置、实测与待验证陈述保持区分 |
| 同ID不同包/版本、重复写入与并发审核 | 不串来源；只有合法版本成功；重复请求不重复生成事实/案例 |
| 案例撤回但包未撤销；普通替代与安全撤销 | 分别符合其作用范围；未处理包明确列出；普通替代不改旧任务 |
| 撤销发生在缓存命中、图恢复或模型返回期间 | 已停用内容不能作为新指导交付；停用排序与权限复查可复现；不额外调用模型 |
| 反查历史存在缺失关系、曾供模型但未引用 | 覆盖缺口明确；不把可能受影响误报为已误诊或未受影响 |
| 清理期间新增引用、进程中断、重复任务 | 新引用被阻止或使对象退出批次；可恢复重试，部分失败如实报告 |
| 从停用/删除前的备份恢复 | 业务记录、Checkpoint和缓存均不能重新启用已停用内容；删除范围复验 |

专业内容是否正确、是否足以更正原建议，由教师依据独立材料逐项审阅；代码断言不能证明电气安全。页面还需核验停用提示、历史标签和权限，不能只看后台任务完成。

建议分两步实施：**先做来源追踪、停用与恢复/交付检查、影响复核；再做保留策略和跨存储删除。** 第一阶段允许保留受控历史，不承诺物理删除；第二阶段须明确各类保留期、删除负责人和实际备份/外部副本范围。Hybrid Search如另行立项，应接入同一可用性检查和来源关系，本方案不以它为前提。

### 7. 本次实施决策（2026-09-28）

三类记忆与四个生命周期环节共用一套服务：事实通过固定包版本写入和更新，经验沿用草稿审批和案例匹配，工作记忆从当前任务业务记录生成有界投影。新增投影不额外调用模型、不自动加入Provider输入、不自动晋升草稿。配置事实明确标记为配置，未经实物确认不输出实测断言。

新增来源使用账本、停用事件、影响复核和清理计划；只保存关系及必要治理信息，不复制原始实验数据。来源身份包含版本与内容哈希，包内案例与全局案例分开。旧记录采用显式引用核对；无法确认的覆盖缺口保持未知。通过现有撤回/撤销服务登记事件，包撤销仍须独立显式操作。

工作流响应附三类记忆投影；教师通过受权接口查询影响和提交复核。治理角色不自动取得学生历史权限，影响列表逐条按原班级授权，并分页返回。副本清理先生成固定计划，再按原计划执行：已有TTL可授权清理过期解释缓存；证据、调用审计、包快照、Checkpoint和备份的保留期尚未确定，预览返回明确阻止原因，不开放绕过保留策略的通用删除。待负责人给出这些策略后再扩展执行器，不用假定天数填补业务决策。

数据库追加迁移，旧诊断不回填或重写；来源记录与业务写入同事务。读路径只核验、不创建记忆、不运行模型。回退代码前保留治理表及停用状态；有治理记录时拒绝破坏性降级。验证覆盖真实调用路径、跨范围、停用/返回时序、精确版本、幂等、清理范围及空库/历史迁移。

本版实现以配置事实为事实记忆的首个可核验来源；尚无独立实测事实录入器，不把待硬件确认材料包装成事实。经验写入和修订沿用新草稿/新版包的审核，不建立自动学习。已实现关系可区分匹配、提供给模型、输出引用和缓存派生；没有学生接收确认时，交付状态保持未知。旧来源缺失、改名副本和未登记导出不在完整覆盖承诺内。

停用缓存由受权接口或维护命令处理，登记后即使尚未清理，使用入口仍拦截；没有新增后台调度器。恢复工具导出/重放停用登记，须由维护者提供独立保存的最新可信文件。留存未定的业务历史、Checkpoint、备份及外部副本仅列阻止原因，不物理删除。这些边界与测试证据必须随交付说明。

## 案例条件与当前建议读取（2026-09-28）

包与全局经验案例共用`knowledge/applicability.py`、matcher及`knowledge/projection.py`。限制正文只从确认材料提取，匹配后进入`AIKnowledgeReference.content.applicability`和推理约束。代码只比较已声明实验/包版本/组件条件；`text_only`由后端输出合同提示尚未核验。异常、证据、候选、动作仍由原确定性链控制，条件匹配不确认实物或根因。

完整受权来源中的敏感值在投影前暂存私有属性；包括确认人、恢复诊断ID及审核秘密的重复值，清洗覆盖Provider正文、标题和Checkpoint引用。私有来源本身不写Checkpoint、公开响应或审计清单。案例及全部条件整条入选或省略，预算不影响独立本地硬约束集合。

当前策略`whole-unit-applicability-v1`、投影`case-applicability-v1`、推理Prompt`evidence-reasoning-v2.14`、解释默认Prompt`phase9.5-v3`；推理输出error_type改为必填（无异常回退仍可为null），每次Provider Schema约束为本次规则值；输入显式传递evidence_conflict。服务端输出合同为`explanation-boundary-v6`。实际payload/Prompt/来源指纹参与缓存，清单记录投影版本。旧阶段结果及唯一约束竞争重放都重验策略、当前来源和权限，不补造历史清单或收费重调。

新工作流结果及等待反馈/教师审核快照冻结`context_delivery.explanation_call_id`，并校验对应推理阶段。读取不能用诊断上后来更新的latest调用替旧正文证明；缺冻结身份或旧策略AI结果只读降级到原确定性核心。检查幂等、反馈后读取、学生当前页共用投影；原final_result、调用审计及业务回执不修改。明确历史复核接口保留原文，标历史用途和策略状态。

资料来源登记、包格式兼容见[实验包设计](experiment-package-design.md)，只读预检见[测试指南](evaluation.md#package-context-preview)。P4概念解释未实施：concepts/steps全文仍不进Provider，不新增调用或自由RAG。

## 当前输出与调用恢复边界（2026-10-02）

`provider-allowlist-v4` 拒绝含私密信息的动态键，值继续最小化清洗。`reasoning-facts-v2` 使用受控理由和摘要，仅从已校验的下一动作产生`verification_requests`；自由missing_evidence及历史reason/rationale/evidence别名不能绕过共同投影。原模型响应仅保留清洗后的调用审计。页面不回退展示旧自由字段。

`reported_evidence` 独立展示当前诊断的来源记录，即使排序为unknown仍可见；来源类型和状态同时显示，不能将文本自动当作类型化配置比对或硬件真值。当前读取重新加载该诊断的证据，并从绑定的有效解释或配对推理记录恢复动作许可；预算跳过解释不抹掉合法推理指导。源/权限不合格仍降级，历史和已授权教师编辑保留。

调用治理新增持久逻辑操作，具体状态与失败恢复合同见[调用恢复合同](ai-diagnosis-design.md#调用恢复合同)，数据字段见[数据库设计](database-design.md)。本地恶意输出与故障注入只能验证程序合同，不能证明真实模型的语义质量。

## 真实 API 修复后的表达与等待合同（2026-10-03）

推理 v2.12 的 Provider 专用 Schema 只保留当前五个排序字段，外发候选标题统一为 cause；新响应严格验证，历史 confidence/evidence/rationale 仅在历史兼容模型中解释。CoT 五步和图结构保留。推理 limitations 依据实际 unknown、冲突及可信案例条件生成；旧推理重放同样投影，原审计不回写，模型原文不作为当前条件。

案例整理 Prompt 为 knowledge-case-polish-v4。四个文字字段逐字选择当前锁定材料/固定状态说明组成的字段专属 expression_choices；Schema 枚举及本地共同校验，不再接受任意自由改写。symptom/teacherNotes 不可从旁路改变。生成、直接写入、提交审核及审批均复核已有润色内容；旧无据草稿保留原文但不能继续发布，需重新整理。教师独立提供的根因确认和修复步骤仍沿审核合同。该保守限制降低自由润色能力，不能称为已解决任意自然语言的语义保真。

润色交付拒绝复用 `GovernedAIInvocation.audit_delivery_denial()` 和现有 `AuditEvent`：行动 `ai.delivery_denied` 关联原 `ai_operation`，仅存阶段、尝试序号及固定错误码，正文与费用不复制。Provider 后撤权、已取得原响应后的复核拒绝、最终写入拒绝均先回滚草稿，再串行查重记录；同一操作最多一条，原用量仍按实际尝试保留。发送前拒绝不伪造 Provider 后事件，审计存储失败仍拒绝交付并记录固定运行日志。推理/解释原有无输出拒绝 `AICallRecord` 保留。方案与验收入口见[交付审计合同](ai-diagnosis-design.md#调用恢复合同)。

无效但结果已知的模型输出可按 `ai_max_retries` 在同一操作内重试，每次保存已发生用量；默认 `1` 表示最多两次物理尝试，显式 `0` 表示最多一次。撤权、来源失效和结果未知不按输出无效重试；恢复不重置上限，成功响应重放不重复外发或增加用量。测试显式覆盖 `0/1`，不依赖本机 `.env`。

前端对检查、反馈、直接解释、诊断审核与案例整理 POST 采用75秒有限等待，普通请求8秒；Nginx API读取期限90秒。覆盖默认每阶段30秒、两阶段及本地余量。自定义更长阶段或断网仍可能进入原身份恢复；不自动重发，不把超时视为未执行。

修复方案、设计回归矩阵与执行结果见 [本轮审计目录](../output/audits/real-api-repair-20261003/plan.md)。CoT独立增益、上下文效果、概念解释P4及真实课堂状态分别保留原验收边界。

## 调用恢复合同

`ai/governance.py` 与 `ai/clients.py` 分别拥有逻辑操作和单次传输；`AIOperation` 唯一键固定业务动作，输入指纹及 Provider/模型/Prompt/Schema/验证器版本用于冲突核对，不能改指纹就重发原阶段。每次物理尝试使用原 `AIUsageReservation` 账本。`prepared → dispatching → succeeded / failed_known / outcome_unknown`：发送前短事务提交 dispatching、尝试号及预留，等待 Provider 不持业务锁；结果保存后推进 checkpoint，业务已保存而 checkpoint 未推进只能补进度。

成功只重放并重验当前权限/来源/版本；failed_known 仅在政策、剩余次数、时间及预算允许时重试，每次重新准入。dispatching/结果未知、发送后超时/截断/保存失败不能自动重发或退款，不假定 Provider 支持幂等查询或跨系统恰好一次；未知旧预留不猜归属或费用。并发只有一个发送者，不能租约过期后直接补发，恢复不重置截止时间/预算。回退优先关闭增强，保留操作、预留和审计，不恢复不识别发送状态的旧代码后继续外发。

总期限使用单调时钟覆盖连接/发送/读取/等待/解析及取消回收，限制编码前后字节；不以 Future 超时后放任后台下载，拒绝无法有界解压的编码。确定请求错误不盲重试；429 的秒数/HTTP日期 Retry-After 不截短提前重试；5xx 不等于确定未执行。响应/异常只留安全状态、固定原因、重试时点及未知标志，不记完整 Provider 错误体。Provider 输入Schema必填/允许值与本地业务一致，约束取清洗后的实际输入。

清洗必须覆盖授权原始源的秘密、动态键和值、短敏感串及嵌套知识；数值保持类型，不任意豁免id或改编号，必需身份与秘密冲突取消增强。失败/重试均按实际尝试计费、在途占额，同请求及多问题不重复扣；有限非负金额、零预算禁调用，记范围/时区/币种/价目版本，只有可靠最大成本预留可称费用硬上限。未知费用独立待核对。

`audit_delivery_denial` 的审计存储及清理回滚失败不能替换原交付拒绝；同操作仅一条 `ai.delivery_denied`，不补猜历史。回归由 `test_ai_operation*`、`test_ai_transport_lifecycle.py`、`test_ai_dispatch*`、`test_knowledge_case_drafting.py` 覆盖，软件通过不证明真实语义。

## 上下文完整性与后续取舍

`context_builder.py/context_contract.py` 只做纯投影，不查库/调用模型/改历史；服务层负责授权与冻结，推理/解释各自白名单。候选与关联证据、案例与全部前提整单元保留或省略，完整可信校验集合与实际外发集合分开。先看全量冲突再限数量，不能截JSON、丢第51条所需关联或只留结论；只在本次同来源/版本/hash内去重，不永久排除已读资料，同文独立观测不合并。

空召回只证明本次范围内没有合格匹配，不能推出全库未收录/未审核；来源身份与有限条件检查不认证硬件/自由文本前提。manifest只保存授权身份/版本/hash、实际payload及Prompt指纹、选择和省略计数，matched/prepared/provided/cited/derived分开，缓存无本阶段新provided；尝试不证明Provider收到或模型利用，旧记录缺清单保持未知。知识关系图不替代故障树，统计由代码/数据库承担；未来检索须独立需求和对照，不因旧表恢复RAG。

P4真实效果仍待两实验独立材料及语义审阅，材料入口见[评测要求](evaluation-requirements.md#p4-真实效果待验材料)。原型选型已结束：当时优先既有LangGraph，PydanticAI/Pi仅条件备选，没有换框架的收益证据；当前产品沿用确定性来源/任务服务，不建设Node桥接或第二套费用账本。
