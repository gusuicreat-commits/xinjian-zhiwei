# 芯鉴知微开发准则

- 文档核对：2026-09-27（规则沿用下述确认记录；实现和验证状态另见当前状态文档）
- 模型规范内核纳入日期：2026-09-17（第 19 节；不表示实现状态已重新验收）
- 业务方案确认日期：2026-09-19（第 20 节；用户授权逐步实施并要求以后遵守，目标规则不等于已实现）
- 适用范围：后端、前端、设备接入、实验包、诊断知识、数据库迁移、测试和部署
- 目标：让后续开发继续沿着“真实设备证据 + 确定性诊断 + 受约束 AI + 教师审核”的方向演进，不重新引入已经放弃的自由 Agent 或 MVP RAG 路线。

## 1. 本文的约束级别

本文是当前项目的开发准则。新增功能、重构和数据导入必须满足本文；如果业务需求确实需要突破某条约束，应先形成可审查的架构决策并同时修改代码、测试和本文，不能只在实现中静默改变边界。

真实性优先于演示完整度。缺少真实硬件数据、正式知识或人工审核时，系统应明确显示 `test_only`、`pending`、`unknown` 或 `blocked`，不得用合成数据伪装正式能力。

## 2. 当前技术基线

- 后端：Python 3.10+、FastAPI、SQLAlchemy、Alembic、PostgreSQL。
- 工作流：LangGraph 负责节点编排、状态保存、条件分支和恢复，不负责自由规划。
- 前端：Vue 3、TypeScript、Vite。
- AI：统一 Provider 客户端、严格结构化输出、审计、预算和确定性降级；默认关闭。
- 数据库迁移 Head：`20260927_0034`（代码版本，目标环境是否升级需单独验证）。历史初始迁移创建了 `vector` 扩展，因此标准 Compose 使用带 pgvector 扩展的 PostgreSQL 镜像；这不表示当前诊断链路使用向量检索。
- 当前仓库版本：`1.0.0`。版本号只是交付标识，不代表真实硬件或生产环境已经验收。

## 3. 架构总原则

当前诊断主链固定为：

```text
设备数据采集
  -> DiagnosisContext / DiagnosisState
  -> Rule Engine（确定异常类型和事实证据）
  -> Fault Tree（生成候选原因空间）
  -> Knowledge Context（推理前知识供给）
  -> AI Reasoning（受约束排序，可降级）
  -> Knowledge Validation（推理后校验）
  -> Explanation（学生可理解的建议）
  -> Feedback / Escalation / Teacher Review
```

每一层只承担自己的职责：

- 设备层报告发生了什么，不直接声明根因。
- 规则引擎判断确定性异常并产生证据。
- 故障树给出有限候选原因及支持分，不把分数表述为统计概率。
- 结构化知识在推理前提供实验约束、标准故障映射、排查步骤和已确认案例。
- AI 可以综合证据、重排候选原因、给出有界置信度并组织教学表达。
- 知识校验在推理后检查原因、证据和操作是否越界。
- 教师审核关键知识和需要人工处置的诊断。

禁止把 AI 设计为能够脱离设备证据“自动发现硬件故障”的万能判断器。

## 4. 模块边界

### 4.1 设备接入

设备接入代码必须保持以下性质：

- 所有写入经过设备身份认证、请求大小和速率限制。
- 批量上报使用 UUID `requestId` 和载荷哈希实现持久化幂等；相同 ID、不同载荷必须冲突失败。
- `bootId + sequenceNo` 用于设备内顺序判断；乱序历史可以保存，但不得回退当前状态。
- 原始设备时间和服务端接收时间分开保存；设备时间不可信时明确标记回退来源。
- 测试、模拟和重放数据必须贯穿 `is_test_data=true` 与 `test_run_id`。
- 设备不得直连 PostgreSQL，不得持有 AI Provider 密钥。

### 4.2 DiagnosisContext 与 DiagnosisState

`DiagnosisContext` 是一次确定性诊断使用的规范化输入；`DiagnosisState` 是整个工作流的可恢复状态。新增字段应满足：

- 有明确来源、类型和默认值；
- 可序列化并能兼容旧记录；
- 不在多个字段重复表达同一事实；
- 证据、知识、推理结果和学生反馈分区保存；
- 敏感或超长原文进入 AI 前经过清洗、截断和外发许可检查。

`state_revision` 当前是业务审计修订号，不是数据库 checkpoint 的乐观锁版本。不要依赖它解决并发覆盖；并发控制必须在存储或服务层显式实现。

### 4.3 确定性诊断

规则引擎只能基于规范化观察、事件、错误码和实验包规则做判断。每条命中必须能够追溯到真实落库证据或可复现的规则事实。

故障树必须从已声明的候选集合中工作。候选的 `score` 是规则支持强弱的排序分，不是经统计校准的故障概率。没有证据时不得通过缺失值、时间顺序或语言常识虚构支持关系。

重复读取同一诊断或重复调用指导接口不得自动提高提示等级。升级只能由新反馈、失败次数、持续时间或明确的教师动作触发。

### 4.4 推理前知识供给

Knowledge Context 应在 AI 推理前提供：

- 当前实验定义、硬件约束和正常工作条件；
- 当前 `error_type` 对应的标准故障映射；
- 已审核、事实锁定且适用版本匹配的教师确认案例；
- 允许的排查动作和教学提示。

知识匹配至少按实验、错误类型、发布/审核状态和测试数据边界过滤。实验包案例若 `errorType` 不匹配，不得进入当前推理上下文。

### 4.5 AI 推理

AI 允许做的事情：

- 对故障树已有候选原因排序；
- 组合多个真实证据说明支持关系；
- 在候选范围内给出有界置信度；
- 当证据不足时输出 `unknown`；
- 生成符合提示等级的学生语言。

AI 不允许做的事情：

- 覆盖规则引擎的 `error_type`；
- 引入故障树或知识约束外的新原因；
- 引用本次诊断不存在的证据 ID；
- 把规则支持分包装成统计概率；
- 生成未在允许动作集合中的危险操作；
- 把合成案例、未经审核案例或语言模型输出描述成真实教师经验。

AI Provider 不可用、输出不合规、超时、超预算或校验失败时，必须走确定性降级，不能让整个诊断链路失效。

### 4.6 推理后知识校验

Knowledge Validation 至少检查：

- `error_type` 是否仍等于规则结果；
- 原因是否属于故障树候选集合；
- 证据 ID 是否属于本次诊断持久化的 `diagnosis_evidence.id`；
- 建议步骤是否来自已匹配知识案例或允许动作；
- 输出是否违反实验包的安全边界和明确规范；
- 无法校验的结果是否降级为 `unknown` 或转教师处理。

当前校验覆盖身份、集合成员、动作白名单和基本一致性，不等于已经覆盖所有电气安全规范。涉及供电、电压、短接、焊接或器件替换的建议必须由正式实验包和教师审核提供。

## 5. 证据治理

### 5.1 证据必须真实落库

提供给 AI 的证据 ID 必须来自本次诊断已经写入的 `diagnosis_evidence` UUID。禁止临时生成 `device:status`、`log:xxx`、`history:failure_count` 等伪证据 ID。

允许的证据类型包括原始日志/读数/心跳的引用、规范化 Observation/Event、规则事实和人工反馈。原始载荷与规范化值应分开保存，既支持审计，也避免把清洗后的信息误当原始事实。

### 5.2 输出只能引用输入子集

AI 输出中的证据必须是允许证据集合的子集；原因必须是允许候选集合的子集。校验失败时记录安全错误分类，不保存 Provider 的完整敏感错误体。

### 5.3 测试数据传播

任何来源为测试数据时都要保守传播测试标记。使用测试实验包版本运行得到的诊断结果也必须是测试数据，即使输入遥测记录本身未标记。测试知识不能提升为正式知识，除非经过单独的真实数据验证和教师审核流程。

## 6. Experiment Package 准则

实验知识和代码必须分离。新增实验原则上通过 Experiment Package 完成，而不是在 Python 函数中写死实验名、GPIO、阈值、错误映射或步骤。

资料收集、内容制作、分层验证与修订统一遵守[第 20.26 节](#2026-资料包内容建设与变更管理br-package-content2026-09-21)；该节是用户确认的持续规则，不另建相互独立的制作口径。

每个包包含十个必需 YAML 工件：metadata、hardware、rules、fault_tree、concepts、cases、steps、hints、normal_cases、fault_cases。内容清单和哈希由装载器生成；证据映射、运行预期及测试预期存于对应工件中。具体目录和字段见 [Experiment Package 设计](experiment-package-design.md)。

包开发必须遵守：

- 严格 Schema 校验，未知字段默认拒绝；
- ID 在包内稳定且所有跨文件引用可解析；
- 阈值有单位、来源和适用硬件版本；
- 规则、故障树、案例和测试样本必须交叉验证；
- 内容哈希可复现；
- 实验包发布经过 `draft -> pending -> approved -> published`（`pending_review` 属于案例草稿，不能混用枚举）；
- 运行时锁定已发布的 PostgreSQL 快照和版本，不依赖可变工作区文件；
- 已发布版本通过服务/API 不可修改，只能创建新版本。

`metadata.compatibility.engine` 在导入、发布校验和运行装载时执行版本范围校验；当前诊断引擎契约版本为 `2.1.0`，与应用发行版本 `1.0.0` 分开。不兼容或无效范围拒绝使用。声明检查不代表硬件适用性、所有教学工件消费或真实效果已经验证。

当前 DHT11 和 LED 包是结构、运行时和测试用示例，案例明确标记为测试数据；它们未经过真实硬件与教师正式确认。包中的 concepts 和 steps 经显式关联作为新指导的教学参考保存展示；旧指导不回填，资料不外发给模型。工件存在不等于适用、已执行或已确认。

## 7. 知识库与案例沉淀

MVP 使用结构化数据库和实验包 YAML，不使用 Embedding、向量数据库检索或 RAG 主链。

`KnowledgeCase` 的核心语义包括实验、错误类型、症状、证据条件、候选原因、排查步骤、教师备注和审核状态。知识内容必须与执行代码分离。

案例沉淀流程固定为：

```text
实验事实与诊断过程保存
  -> 学生反馈或教师确认结果
  -> 模板生成案例草稿
  -> AI 仅优化表达
  -> 质量检查
  -> 教师审核
  -> 发布并进入可匹配知识
```

AI 不得创建未经验证的事实、篡改锁定事实或自行发布案例。来源授权、适用硬件、版本、审核人和变更历史必须可追溯。

## 8. LangGraph 工作流准则

当前节点职责：

1. `context_builder`：构建并持久化诊断上下文。
2. `rule_engine`：确定异常类型和事实证据。
3. `fault_tree_analyzer`：生成有限候选原因。
4. `knowledge_context`：推理前加载可信结构化知识。
5. `ai_reasoning`：受约束排序或确定性降级。
6. `knowledge_validation`：推理后验证证据、原因和步骤。
7. `ai_explanation`：生成结构化教学建议。
8. `escalation_handler`：根据失败次数、持续时间和证据质量升级。
9. `feedback_handler`：处理已解决、未解决和请求教师帮助。
10. `teacher_review`：在需要时暂停等待有权限教师处理。

LangGraph 不得引入多智能体、自主工具选择或自由规划。节点输入输出必须有明确 Schema，条件边必须能被测试覆盖。

当前 `unresolved` 反馈沿已保存状态继续指导，不会重新采集设备数据。另有第20.22节定义的显式重新检查命令，它固定新输入、请求身份和时间范围；该能力不能被描述成反馈自动刷新或硬件主动采样。实际条件边见 [AI诊断设计](ai-diagnosis-design.md)。

## 9. 兼容性边界

为保证旧数据库和 API 记录可读，以下历史字段或结构暂时保留：

- `needs_rag`、`retrieval_query`、`retrieved_chunks`；新工作流必须令 `needs_rag=false`，检索容器只承载结构化案例引用。
- `embedding` 或向量相关数据库表/迁移；当前运行时不写入、不检索、不作为诊断依赖。
- `phase9.5-v1` 等旧提示词/缓存版本名；它们是审计标识，不代表当前架构阶段。
- 旧实验定义和旧结构化知识表；它们用于兼容已有功能，新实验应优先走 Experiment Package。
- `hybrid_retrieval` 兼容入口保持 fail-closed，不能重新接回主链。

删除兼容字段前必须先完成数据迁移、API 版本策略、前端迁移和回滚验证。不要为了“目录干净”直接改写历史 Alembic 迁移。

## 10. 数据库与迁移

- 迁移只允许向前追加；已经进入仓库和环境的迁移不得改写。
- 迁移必须在空数据库升级、现有数据库升级和 `alembic check` 三种场景验证。
- 新表或字段要定义所有权、生命周期、测试标记、删除策略和索引依据。
- 发布工件、审核记录、AI 审计和诊断证据不可通过普通更新路径静默覆盖。
- 当前实验包发布不可变主要由服务/API 路径保证，数据库尚无完整不可变触发器；新增写路径必须复用同一守卫。
- 删除生产数据、重置数据库或覆盖备份不属于普通开发步骤，必须显式确认范围并提供恢复方案。

## 11. API 与前端

- FastAPI OpenAPI 是字段级接口事实来源；文档只描述稳定语义。
- 新接口必须定义认证、授权、幂等、分页、错误码、测试数据边界和审计行为。
- 教师数据按授课班级和设备绑定范围隔离；私人备注不得进入学生响应。
- 前端必须区分“服务在线”“诊断可用”“真实资料已就绪”和“生产可交付”。
- 不再显示 RAG 命中、向量召回等当前不存在的主功能；兼容字段只可用于历史记录解释。
- 原始证据、规则结论、AI 排序和教师结论应在 UI 中保持可区分，不能合并成不可追溯的一段话。

## 12. 安全与隐私

- 密钥、设备令牌、密码、证书、生产连接串和真实个人数据不得提交 Git。
- 只提交 `.env.example`；真实配置由环境或密钥管理系统注入。
- AI 外发采用字段白名单，默认不发送真实姓名、令牌、完整原始文件、无关日志和私人教师备注。
- 日志与审计不得记录明文密码、令牌、完整 Provider 错误体或超出需要的学生个人信息。
- 知识来源必须记录授权、许可证、适用范围和审核状态。
- 危险硬件操作必须来自正式审核知识，并清晰提示断电、安全防护或教师介入条件。

## 13. 标准开发流程

每次变更至少完成以下步骤：

1. 先确认真实代码、Schema、迁移和测试，不以旧文档猜测现状。
2. 明确变更属于设备事实、规则、故障树、知识、AI、教学还是处置层。
3. 优先扩展现有模块和 Experiment Package，避免平行实现第二套诊断链路。
4. 先定义输入输出与失败路径，再实现正常路径。
5. 同步更新测试数据边界、审计信息和权限判断。
6. 增加最小必要测试，覆盖成功、拒绝、降级和兼容路径。
7. 更新对应核心文档和实现状态；不新增一次性“阶段总结”文档。
8. 运行与风险相称的验证；准备提交前运行完整门禁。

### 文档维护与事实核对

- 先区分持续规则、当前实现、待评审方案、操作说明、历史证据与原始来源；文档类别、用途和入口统一见 [文档索引](README.md)。原始来源不因实现更新而重写，历史结果不提升为当前验收。
- 第19、20、21节是已确认的持续约束。代码和测试说明现在做了什么，不授予偏离规则的许可；发现不一致时分别记录要求与实现缺口，不能通过降低文档要求掩盖问题。
- 可由源码确定的环境名、枚举、接口、版本、路径、容量和命令须核对唯一来源。修改契约或检查脚本时保留“错误输入会被拒绝”的反例，不以脚本输出通过或文档写已完成作为验证。
- 每条规则保留唯一维护位置，其他文档引用它；当前状态只汇总能力/缺口及最近执行证据，不持续堆叠旧轮次。无独立价值的占位或重复文档可删除；仍有依据的旧材料归档，修正所有当前入口链接。
- 本轮只调整文档时检查链接/锚点、命令来源、版本门禁、差异及代码未变，不借用旧全量通过数宣称本轮又执行了全套测试。

### 新增实验的顺序

1. 获取已确认的硬件资料、实验目标、单位、接线和安全限制。
2. 复制最小示例包并更换稳定 ID，不复制未经确认的阈值结论。
3. 完成十类工件及交叉引用。
4. 添加正常、典型异常、证据不足和禁止性陈述样本。
5. 运行严格包校验和通用引擎测试。
6. 以测试版本导入，完成教师审核后再发布正式版本。
7. 用真实设备真值样本评估，不以合成通过替代硬件验收。

## 14. 测试与完成标准

提交前首选执行：

## 18. 项目真实性治理与负责人摘要

维护 [项目真实性看板](project-truth-status.md)，区分 verified（必须注明是来源事实还是代码行为）、pending_hardware、pending_teacher（含 pending_course_confirmation）和 issue。未知内容只标记与追踪，不允许 AI 或代码自动补全事实。真实硬件验证、教师审核和软件测试是不同门槛，不能互相替代。

证据 ≠ 异常 ≠ 根因。读取失败日志是证据，规则判定 SENSOR_READ_FAILED 是异常，DATA 断开只是待验证候选。原因排序与分数不能升级为真实根因；证据不足时保留 unknown / need_verification。

1. 这次发现了什么问题？
2. 会造成什么现实影响？
3. 现在能不能解决？
4. 如果不能，需要硬件还是教师确认？
5. 下一步最应该做什么？

上述看板是持续维护的当前状态入口；原始审计事实保留日期和版本，不用新结论覆盖历史证据。更新实验包仍沿用版本化审核机制，不改动已发布快照。

### 19.1 必须保持的行为

> 规则决定发生了什么，故障树决定允许怀疑什么，数据库保存本次实际证据，模型只帮助排序和解释，验证器决定输出能否采用，教师决定什么可以成为正式知识。

1. **先有证据，再谈结论。** 区分上报记录、规则异常、候选原因与确认根因。证据 ID 必须属于本次诊断已落库记录，并与候选有实际支持关系；仅仅 ID 存在或处于白名单中，不能证明因果成立。不得把程序命令当硬件效果、没有报错当硬件正常、模型预训练知识当本次实验事实。
2. **不确定性是有效结果。** 无法区分原因时保留 `unknown`；如实保留冲突与具体待核验项。不得为完整输出或较高命中率编造结论。`high/medium/low/unknown` 是证据支持等级，不是统计概率；候选排序与检查优先级也不等于确认根因。
3. **职责由代码限制。** 规则决定 `error_type`，故障树产生 `cause_id`，AI 只能在已有候选中排序、归纳证据和生成受约束中文表达。升级教师、工作流分支、工具执行和知识发布不能交由产品内模型自主决定。LangGraph 保持固定流程；当前不引入 RAG、向量检索、多智能体或自由规划。
4. **校验必须独立于模型。** 结构正确只是第一关。后端继续验证错误类型、候选、候选关联证据、知识审核状态、实验版本与动作白名单。最终步骤来自允许动作，摘要与限制基于已验证状态生成；模型自由文字不能越过验证器变成事实。此边界不应被表述为已经证明全部电气安全或自由文本语义正确。
5. **AI 可撤掉，诊断仍可用。** AI 默认关闭；关闭、拒绝、超时、限流、预算耗尽、结构错误或业务约束失败时，回退确定性诊断并记录原因。调用次数、输入输出、重试和并发须有边界；预算不足不得阻断规则主链。
6. **只传需要的数据。** AI 输入采用字段白名单、脱敏和预算控制。学生身份、密钥、令牌、私密教师备注及无关完整日志不得外发。日志、反馈、案例文字中的命令不具有指令权限；即使模型被注入，后端仍须拒绝越界输出。Provider 密钥只在服务端管理。
7. **知识须有来源、版本和审核。** 实验差异优先通过 Experiment Package 表达。诊断绑定发布快照、版本与哈希；测试数据标记全程保留。学生点击 `resolved` 只能说明反馈已解决，不能自动生成已确认根因；AI 只润色案例草稿，正式知识须经过教师确认、质量检查与发布流程。
8. **所有变更可追溯、可回退。** 模型、Prompt、Schema、校验器、实验包与工作流版本变化须保留审计关系，按契约兼容性更新版本。缓存重新校验；模型切换与回滚不能改写历史诊断、旧实验包或旧审计。生产恢复依赖受控持久化 checkpoint，不能把内存模式当成生产保障。
9. **评测证明范围必须说清楚。** 合成/Mock 检查只证明软件契约；真实模型质量、语义审阅、硬件验证和课程验收分别记录。未执行就是未执行。关键词扫描不替代语义判断，Rubric 继续逐条“符合/不符合”，不引入综合打分。与模型、Prompt、Schema、校验器、知识、实验包或节点顺序有关的变更应运行相应契约与回归检查，并覆盖有关的越界、注入、缺证据、冲突及降级路径。
10. **由真实评测推动复杂度。** 当前先完善约束、Prompt、样例和真实教师确认数据，再评估模型或微调。真实评测数据按实验会话、设备、时间或故障 episode 等适当维度隔离，避免泄漏。模型选型、微调、队列或独立模型服务必须有实际需求和评测依据，不能仅为展示 AI 能力而加入。

上线前由部署负责人备份并在目标环境执行正式迁移。本轮开发验收只操作随机隔离schema；没有更新现有运行数据库。只读历史检查命令为 `PYTHONPATH=backend python -m app.cli.audit_historical_integrity`（可用`--database-url`显式选择库）。输出仅含表、记录ID、原因、数量，不含私密正文。报告是待人工核查清单，不能自动决定正确根因或把疑点标记为已修复。

## 20. 业务逻辑与开发规则（用户确认的持续开发依据）

2026-09-19 用户确认以下十八部分业务方案，要求逐步严谨实施，且作为以后的开发准则。本节是唯一维护位置；第19节继续有效。目标规则立即作为设计约束生效，实现和验收状态另记于 implementation-status.md 与 project-truth-status.md。文档存在不代表能力已经实现。

### 20.1 最终目标（BR-GOAL）

开始实验→可信现象→规则异常与有限候选→允许的排查动作→新证据验证→教师介入→经确认审核的知识。学生知道下一步，教师能还原过程，诊断可还原证据及版本，新增入口复用规则。保留现有 FastAPI/PostgreSQL、固定 LangGraph、Vue/TypeScript 架构；首期不扩自主硬件控制、自动评分、多学校管理、RAG或自由Agent，不为统一规则拆微服务。

### 20.2 统一术语（BR-FACT）

实验会话是被授权主体的一次实验；观察是设备/人工的记录；异常是固定版本规则的不符合项；候选是待验证解释；诊断是固定证据快照；问题过程（episode）是同范围问题从发现到结束；工单是教师工作记录；恢复证据支持指定异常消失；根因确认有确认人、方法及来源；课程完成需教师批准的验收判据。

学生说解决、工单关闭、恢复读数、确认接线原因、课程合格分别记录。上报不等于独立实测，异常不等于根因，排序分不等于概率，最新诊断不代替全部历史。

### 20.3 身份、归属与权限（BR-AUTH）

分别回答谁操作、记录原属谁、现在是否允许。学生账号认证到人，设备凭据仅认证设备；正式学生操作需有效账号、任务资格、正确会话和允许状态。设备登录只兼容明确测试演示，不能取得正式学生数据。

历史固定学生/班级/任务/设备/版本，换人转班调岗不改归属；纠正需证据及专门审计。权限按操作能力、资源范围及状态判断；多角色按实际授权范围合并，不能角色分支扩权/漏权。教师限授课范围；知识审核不自动取得学生隐私；管理员不替代领域事实确认。撤权后每次请求重新判断，长任务交付前再次检查，审计保留原执行人。详情、列表、统计、搜索、导出、缓存、通知、错误响应全部适用。

### 20.4 实验会话与交接（BR-SESSION）

会话语义为准备、活动、结束、取消。创建原子检查身份、选课、任务开放状态/时间、发布包及设备可用性；一设备同时一个采集归属会话。多会话显式选定，不取最新。换学生新建；换设备保留历史及接续；重启只改变启动标识。

结束停止学生新操作，已提交回执可按授权查询，不借恢复消费新操作；结束不等于故障解决。设备交接先关闭旧使用权；上报优先携带可验证采集会话，A的离线积压不能进入B。无法归属保留受限检查，不展示学生。小组需明确主体、成员有效期、共享证据和个人反馈，不以共用账号代替。

### 20.5 数据可信度（BR-EVIDENCE）

证据保存来源、会话、发生/接收时间及时间可信度、测量语义、单位、真实/模拟/重放来源与测试标志。原文保留，规范化分开且有版本；接收时间不能冒充物理发生时间。同源重传只计一次，新UUID不使旧观察变新。

缺/空/显式单位分开，明确换算保留原值；数值有限且类型/范围有效。在线与新鲜度分开，缺测不全正常，冲突先于截取判断且不能择优丢弃。GPIO命令/实际电平/实际发光分开。真实硬件受控测试仍是测试，审批不能洗掉来源。认证、请求大小、条数、频率有边界，拒绝批次不留半批正式数据。归属未知不按今天绑定回填。

### 20.6 多问题诊断（BR-ISSUE）

目标一诊断可关联多个问题，分别有证据修订、指导、反馈及预算归因。范围为会话、设备、组件/接口或明确设备级、审核定义的版本化异常组、规则语义版本及测试性质；组件不明保持未知。合并由规则声明，不凭同时发生推断同根因。

主问题只决定展示顺序，顺序改变不得改变身份计数；A的新证据不增加B，A恢复不关闭B。旧单问题API须显式兼容，不把整份诊断resolved解释为全关闭。多目标操作明确列出目标，首版全成功或全冲突。每次诊断冻结证据、时间范围及版本；迟到形成新分析/历史补充，不覆盖旧诊断。未命中不自动正常，必需观测/覆盖/新鲜度齐备才给限定正常；不足、冲突保留unknown，ID有效仍需支持关系。

### 20.7 问题生命周期（BR-LIFECYCLE）

处理状态（处理中/待教师/结束）、结束原因、恢复验证程度、确认根因分别存储表达。学生、教师、规则恢复及工作流恢复经过同一生命周期服务。

| 事件 | 条件与效果 |
| --- | --- |
| 首次有效异常 | 范围和真实相关证据明确，建立问题 |
| 新相关异常 | 更新修订，一次诊断增一轮 |
| 刷新/重放旧证据 | 不增次、不重新计时 |
| 明确求助 | 同范围活动问题进入教师流程 |
| 学生报告解决 | 没有未查看的新相关异常则结束，标学生报告，不确认硬件 |
| 新采样满足恢复判据 | 保存恢复依据，结束对应问题 |
| 关闭工单 | 只更新处理记录；改变问题需显式动作、证据版本及统一服务 |
| 结束后新时期有效异常 | 新建问题并重新计数 |
| 关闭前记录迟到 | 历史补充，不按首次接收认定复发；挑战旧结论则追加待复核 |

离线、没数据、滑出窗口不等恢复；时序不可信要求新鲜采样/核验。旧问题反馈不得改变下一次新问题；会话结束不批量宣布恢复；NULL历史关联不猜测补造。

### 20.8 次数与时间（BR-COUNTERS）

采样失败数、新相关异常证据轮次、提示进度、幂等未解决反馈次数、学生报告的允许动作执行次数分开。点击未解决不证明执行，自述动作不证明硬件事实；累计与连续失败分开，缺完整序列不算连续。数据新鲜度、异常实际观测跨度、等待帮助时长分开；关页断流不证明连续异常，等待升级表达真实原因。现有门槛先保持；改变消费口径说明新旧差异，经教师确认版本化，不用同数字掩盖语义改变。

### 20.9 教学行动与复测（BR-TEACHING）

指导说明已知、缺失、下一步及区分作用、执行后如何验证。动作来自适用批准包/知识，带条件限制；提示等级和介入由确定性策略决定。多问题有明确行动焦点，避免冲突。继续解释用旧快照；重新检查获取新证据及新诊断，不暗示已经复测。展示/报告执行/验证成功分开；无适用动作保持未知并转教师；求助无需凑次数；实验完成另依课程判据。

### 20.10 教师工单（BR-INTERVENTION）

目标新数据同会话同活动问题最多一个活动工单，重复求助附加情况；旧逐诊断工单保留，不自动合并。认领明确责任人，转交检查接收人当前权限；撤权走移交，不能靠旧页面继续。处理完成/未确认/课程结束分别记录。学生解决反馈通知已认领工单，不代教师结案。关闭不等硬件恢复/根因确认；教师改变问题需明确目标、证据版本及统一服务。

私密默认不公开，学生摘要只取明确公开事件；撤回公开更新投影/缓存；通知、导出、AI同规则。

### 20.11 知识与实验包（BR-KNOWLEDGE）

实验记录→草稿→材料核验→审核生效→纳入适用实验包→使用。根因材料有确认人、时间、方法、来源、修复、修复后观察、版本和限制。未知可保留；候选外真实原因记录材料并提新包，不强迫选错，不让AI扩候选。润色只改允许表达，事实修订重新审核。状态+版本条件更新，审批与唯一来源正式记录同事务；等待模型不持锁，返回重验权限。已发布版本不覆盖，修订追加；撤回停新匹配，历史标记。测试来源不可洗掉。

全局案例批准不等进入会话锁定包。正常替代保持旧任务版本；安全撤回停止新/在途教学建议并转教师，采集/历史保留，不自动换包续跑。发布/运行检查引擎语义兼容及必需能力；工件已存不代表所有路径已使用。

### 20.12 AI与预算（BR-AI）

AI仅候选排序、解释、表达整理，不定异常/计数/状态/介入/发布。推理、解释、润色每次实际尝试统一检查开关、次数、长度、原子预算预留及外发许可，各自最小白名单并共用清洗。短字符串、单位、标签、反馈、嵌套文本无豁免；文本命令无指令权。引用同时满足路径、真实来源、允许值且相关；秘密冲突取消增强，不改证据ID。

关闭/清洗失败/超时/拒绝/超限/输出无效不阻断规则、反馈、求助。在途占额度，失败不等免费，未知费用保留待核对不自动退款重试。时区、币种、价目版本、范围明确；只有可靠最大成本预留可称硬金额上限，估算须如实命名。同请求仅记一次费用，多问题归因不重复扣账。返回重验权限、证据、版本，过时丢弃但计账；缓存重验范围、版本、撤回及测试边界。结构通过不等真实语义通过。

### 20.13 并发、重试与客户端（BR-RECOVERY）

变更绑定操作者、范围、目标、原状态/版本、请求身份及载荷。同身份同载荷返回回执或恢复未完成；不同载荷409。短事务内重读和变更，外部等待锁外，唯一约束补充条件更新。新异常先提交则旧解决冲突；解决先提交则有效新异常新建。提交成功响应丢失沿原身份恢复；GET/刷新/重开不新增反馈、调用、计数。

工作流完成、业务已应用、费用结算分别核对，不承诺跨外部系统恰好一次。旧会话不能恢复到新学生；关闭仅协调已发生操作。前端401重新认证、403停止并清除无权内容、409读取新状态并显式决定，不造新身份重试；超时标待确认；账号/会话隔离本地数据及迟到响应。

### 20.14 历史、统计和运维（BR-OPERATIONS）

历史列清单不猜归属、不重计数、不自动合并案例。归档/停用/物理删除分开；删除检查证据审核引用，级联不是政策。身份、证据、审计、AI台账按负责人批准的分类期限处理；未定不开放普通破坏性删除。课后历史独立本人授权。统计时间、分母、单位明确，反馈解决/复测恢复/教师核验分别统计，测试/未知归属不混正式。日志不默认输出隐私原文。

发布绑定代码、迁移、API/Schema、工作流/Prompt/验证器、包hash、配置及验收范围；隔离验证备份恢复、空库旧库迁移、重启、断网及版本不匹配。回滚代码不等数据库可降级。容量按真实课堂人数、设备数、周期、并发及负责人目标，不编造数值。

### 20.17 必须覆盖的组合反例

### 20.18 产品默认与未决事实

首期个人实验、已有项目账号、设备独占；小组及独立课后历史按真实需求扩展。审核权限语义分离，同人兼任分别记录。AI默认关闭，启用前确定费用硬度、币种及负责人。留存期、课堂容量、SLO、硬件阈值、课程判据不猜测；正式试运行限有真实材料的实验/版本/设备。未决外部事实不阻断独立软件建设，也不构成支付、部署、教师签署或硬件认证授权。

### 20.22 重新检查、固定输入与原请求恢复（BR-RECHECK，2026-09-20）

用户确认的边界：首次“检查当前数据”，之后“用最新数据重新检查”；“仍未解决”继续原诊断
指导。读取、刷新、查询回执不执行诊断、不推进提示、不调用模型。重新检查只分析服务端已收到的
数据，不控制硬件重新采样；相同数值的新采样仍是新证据，上传重传不是新证据。

- `services/diagnosis_checks.py` 是学生工作流启动的统一命令入口，旧工作流客户端未传身份时由
  服务端生成身份；这种旧客户端不能自行保证丢响应后的原请求重试。新客户端必须传 UUID。
- 同会话、同 `request_id`、同载荷恢复原命令；同身份不同载荷409。未决命令阻止另开检查。
  同输入的并发检查合并；指定的基准已过时且输入不同返回409。确定性旧诊断接口产生的当前
  结果也可用作基准，但不能把跨会话或归属不明历史记录当成基准。
- 先校验会话、固定包与参数，再在短 REPEATABLE READ 事务中读取截止时刻以内的完整输入，
  保存私有快照。图的上下文、规则和后续推理均使用它；迟到数据留给下一次显式检查。
  不向前端回执或 checkpoint 增加私有原始输入，不扩大模型外发白名单。
- 以真实来源ID、包/定义及规则与监测状态判断有无新依据；只有心跳流量且监测状态未变时不
  新建诊断。离线/缺测等监测状态变化可以产生新检查，但必须标为监测变化，不能说器件恢复。
- 会话级执行互斥覆盖命令恢复，等待后重新读取会话；模型等待不持有业务行锁或快照事务。
  工作流和命令关联同事务，证据生命周期继续由已有短事务锁管理。业务已提交、回执未保存时
  恢复原工作流，不创建第二份诊断；失败模型调用仍由既有治理入口记账。
- 对比按问题归属键及组件/接口范围展示，区分新异常、仍检测到、无新相关记录、未检测到但
  未证实恢复、满足既有恢复判据。新增正常读数但旧异常仍命中时，明确说明仍依据旧记录；
  解决后再次发生的问题使用新问题ID单列，不混作上一轮延续。处理状态单列；学生说解决、教师结案不等于硬件恢复。
  自动恢复仍要求既有完整正常判据，另要求基准每个相关范围具有新且时间可信的证据；未知
  范围、迟到/回退时间、心跳、窗口滑出和其他组件的新读数不能单独证明恢复。时间质量从服务端
  落库列保存，设备原始内容不能覆盖；该约束同时用于新一轮故障的时间判断。
- 等待教师期间允许新确定性检查，保留原工单和审核记录，不再次启动AI增强。
- 前端按设备和会话保存在途身份；网络结果未知保留原载荷，刷新只读。服务器发现未决请求时
  先恢复待确认入口，用户点击后才续跑。明确401/403/409/422不自动换身份重试。
  仪表盘诊断与工作流结果ID不一致时隐藏不匹配工作流，避免将两次结果拼成一次。

#### 教学内容与排查卡

正常实验内容须覆盖学习目标、前置知识、器材与接线、程序配置、操作步骤、预期观察、结果记录和课程验收要求。验收要求尚未确认时保留缺口，预期观察不得写成已经实测。

每张异常排查卡至少说明：现象及证据、目前能判断什么、尚不能确定什么、有限候选原因、允许的下一动作、动作要区分的问题、应留下的记录、如何用新证据判断进展，以及何时请求教师帮助。具体动作及前提须来自适用且经审核的材料；提示等级与升级继续由既有确定性策略控制。

读取失败不能直接写成接线错误或器件损坏；排查先后不等于原因概率。恢复需相关、独立且时间可信的新采样及适用判据，重复上传、旧异常离开窗口、学生报告解决和教师结案均不能替代。异常消失、确认根因和课程完成分别记录。

没有真实案例时正式案例可以留空；合成场景作为明确标记的测试材料保存，不为填满工件生成虚假教师经验。真实记录经事实核验和教师审核后才能按既有案例流程沉淀。
