# 芯鉴知微

**让嵌入式实验中的问题有据可查，让学生知道下一步该检查什么。**

芯鉴知微是面向高校嵌入式与物联网实验课程的辅助平台。学生做温湿度采集、LED 控制等实验时，平台收集开发板的状态、日志和读数，识别异常，给出排查方向，并支持教师介入。

目前项目已完成 V2 软件框架，正在准备真实硬件验证。DHT11 和 LED 资料包是 **`2.0.2` 测试草稿**，尚不能视为经过课堂和硬件验收的正式实验方案。当前进度与待确认事项见 [项目真实性看板](docs/project-truth-status.md)。

## 为什么做这个项目

实验出问题时，学生往往只能看到“读不到数据”或“灯没有亮”，却不知道从接线、代码还是器件开始检查。教师则需要反复了解现场、查看日志、指导排查。

我们希望把这个过程记录清楚：**发生了什么、有哪些可能原因、还缺什么信息、下一步怎么验证。** 学生能循着证据排查，教师也能看到已有记录，减少重复沟通。

平台提供辅助判断与教学建议。真实接线、器件状态和最终根因，仍需要实际观察、测量与教师确认。

## 学生和教师可以怎样使用

| 使用者 | 可以做什么 |
| --- | --- |
| 学生 | 查看设备是否在线、传感器读数和日志；阅读异常说明与分级提示；反馈是否解决，或请求教师帮助。 |
| 教师 | 查看所负责课堂的设备与异常情况，结合记录指导排查，处理学生求助并审核案例。 |
| 项目维护者 | 整理实验资料、配置运行预期和规则，检查数据来源与版本，维护哪些内容已验证、哪些仍待确认。 |

一次典型过程是：

1. 开发板向平台发送状态、日志和读数。
2. 平台按规则检查是否出现异常。
3. 若有异常，列出资料包中允许的候选原因与排查步骤。
4. 学生按提示检查并反馈；无法解决时交给教师。
5. 有记录、有验证、有教师审核的结果，才有机会成为以后可参考的正式案例。

## 我们怎样避免“看起来聪明，实际上猜错”

### 把看到的现象和故障原因分开

**证据 ≠ 异常 ≠ 根因。**

以 DHT11 为例：

| 层次 | 例子 | 含义 |
| --- | --- | --- |
| 证据 | 开发板报告了一次读取失败 | 记录设备报告了什么。 |
| 异常 | 诊断窗口内累计失败达到配置阈值 | 规则判断出现了需要关注的情况。 |
| 候选根因 | DATA 线断开、代码引脚不符、器件异常 | 只是需要进一步验证的可能原因。 |

不同故障可能产生相同日志。平台不能因为失败次数多，就断言一定是接线问题。资料不足时显示“未知／需要验证”，是正常且必要的结果。

### 不把程序命令当成真实效果

LED 实验中，这三件事需要分别看：

- **程序要求输出 HIGH**：说明程序发出了什么命令。
- **引脚实际为高电平**：需要有明确来源的电气观测。
- **LED 实际发光**：需要独立人工或光学观察。

仅有 `level=1` 的日志，不能证明灯已经亮了。当前真实固件中这个值来自哪里仍待确认，平台保留它的未知状态。

### 不把“没报错”当成“实验正常”

没有报错，可能只是没有收到数据。平台需要同时检查心跳、数据是否按预期到达、必需字段是否有效、实验预期是否满足，以及是否命中异常规则。

缺数据、缺周期参数或证据不够时，状态保持未知。即使这些检查都满足，也只表示上报数据符合已配置的监测条件，不代表已经验证所有硬件功能。

### AI 只在明确边界内辅助

规则负责识别异常；预先整理的故障树负责限定候选原因。AI 可在候选范围内辅助排序和解释，只能引用本次诊断中已经保存的证据，不能编造接线、教师经验或新根因。

AI 默认关闭，基础诊断仍可运行。当前不使用 RAG、向量检索、多智能体或自由规划 Agent。

## 为什么把每个实验做成“资料包”

不同实验需要不同接线、读数、规则和教学步骤。如果这些内容散落在程序里，就很难审阅来源，也难知道后来改过什么。

因此，每个实验用独立资料包保存：

| 内容 | 作用 |
| --- | --- |
| 实验介绍与硬件配置 | 说明实验对象、组件及当前配置。 |
| 证据映射与诊断规则 | 说明设备数据如何解释、什么情况算异常。 |
| 故障树与知识案例 | 明确候选原因、参考依据与审核状态。 |
| 教学步骤与分级提示 | 说明下一步可以怎样排查。 |
| 正常与异常测试样例 | 检查软件是否按设计处理输入。 |

资料包经过校验与审核后才能发布。历史诊断保留所用版本，避免资料更新后无法还原当时的判断依据。**有测试样例并不等于做过真实硬件实验。**

看板还保留了引擎兼容声明尚未执行版本检查、部分教学资料尚未被所有使用路径消费等已知缺口，具体见 [实现状态](docs/implementation-status.md)。

## 第一次体验

如已有部署好的环境，请向项目维护者获取访问地址及测试身份。学生从登录页查看设备与诊断，教师从教师登录页进入课堂视图。先查看“就绪状态”，了解当前环境哪些部分可用、哪些仍是测试资料。

如果需要在本机运行，请先准备 Docker 与 Docker Compose，参照 [部署说明](docs/deployment.md) 配置环境。首次配置时执行：

```bash
cp .env.example .env
docker compose up -d --build
docker compose ps
```

已有 `.env` 时保留现有配置，不重复覆盖。

默认访问地址：

- [前端首页](http://localhost:8080)
- [学生登录](http://localhost:8080/login)
- [教师登录](http://localhost:8080/teacher/login)
- [就绪状态](http://localhost:8080/readiness)
- [开发接口文档](http://localhost:8000/docs)

可创建一组测试身份与演示数据：

```bash
docker compose exec backend python -m app.cli.seed_demo --prefix demo-local-
```

按终端输出使用学生设备 ID/令牌和教师用户名/密码。凭据只显示一次；若此前已创建同名前缀，请按 [演示手册](docs/demo-runbook.md) 操作。演示数据用于体验软件流程，不代表真实硬件诊断结果，也不意味着新实验包已自动发布。

## 接下来最需要做什么

先取得准确的板卡与器件清单、原理图和课程指导书，再按 [硬件验证计划](docs/hardware-validation-plan.md) 做“正常—单因素故障—恢复”的对照，保存接线、原始日志、独立测量和实际操作记录。

硬件负责人确认实物与数据，教师确认教学判据和案例。未知项有了对应证据后再更新，不能靠 AI 或代码自动补全。
