# 芯鉴知微前端复杂度评估与成熟产品对照报告

日期：2026-09-21
性质：研究与设计建议，尚未实施。仅生成本报告，不修改应用代码、配置、数据库或现行开发规则。

## 1. 结论

**当前学生端和教师端确实存在信息组织过于繁杂的问题，值得优先处理。** 主要问题是多个栏目重复解释同一件事、不同角色和不同使用时机的信息同时展开，以及学生的操作链被日志、图表、解释和系统说明分隔。边框和留白修整改善了整齐程度，却没有解决这些问题。

上轮新增“现在该做什么”是有价值的，但新增入口后保留了原有全部说明栏目，实际增加了总展示量。这是前端设计上需要纠正的地方：今后每增加一块摘要，都要明确它替代或收纳哪部分旧内容，而不能长期叠加。

建议采用“按任务重组、分层展示”的中等幅度调整：学生围绕当前实验和当前问题操作，教师优先看到待处理事项，完整依据和历史仍可方便查看。暂不建议全站重写，也不建议靠缩小字体、隐藏真实性限制或再加一块 AI 摘要解决。

以下判断来自页面与代码审阅及官方产品资料；未开展真实学生/教师对比试验，因此没有“效率提高多少”“认知负担下降多少”的实测结论。

## 2. 评估范围与方法

本地证据包括本轮只读查看的学生页面、当前前端组件和样式，以及上一轮保存的五类页面截图。外部选取六款产品，覆盖教学、设备监测、故障调查和求助处理。它们分别与本项目的一部分任务相似，没有一款与本项目完全相同。

本次比较的是：用户进来先看什么、如何进入详情、操作放在哪里、哪些信息默认不展开，以及不确定性和角色差异怎样影响布局。没有用不同产品的宣传页与本项目真实工作台直接比较美观程度，也没有对产品打一个缺乏依据的综合分。

**证据边界：** 外部资料来自官方帮助文档、官方截图或产品公告，没有登录六款产品执行相同任务；文档展示的是其特定版本/配置下的结构，不保证所有账号的实时界面一致。本地截图采用模拟数据，不能证明真实课堂使用效果。

## 3. 当前界面的问题具体在哪里

| 发现 | 当前可观察的证据 | 对用户的影响 | 建议方向 |
| --- | --- | --- | --- |
| 同一判断反复出现 | 学生有“设备状态解释”“诊断解释”“辅助诊断进度／当前判断”，顶部又有下一步摘要 | 用户需要自行判断几个栏目是否有区别、哪个更新 | 当前结论只保留一份主展示；来源、解释与历史进入其详情 |
| 操作链被拆散 | 下一步在顶部，分层排查和反馈在底部，中间穿过概览、日志、图表、解释和证据 | 学生看完提示还要寻找操作；手机更明显 | 当前问题、允许的步骤、对应反馈放在连续区域 |
| 页面导航只定位，未减少同时展示的信息 | 概览、数据、诊断导航实际滚动到页面位置 | 看似分区，实际上仍是全部展开的长页 | 按使用目的切换内容，保留明确的数据入口 |
| 开发与运维概念进入日常操作面 | 学生出现 V2、故障树候选、AI 未启用等系统说明；教师常显 17 项工作流指标，含节点耗时、Token 和成本 | 主任务与技术解释争夺注意力 | 用户理解所需信息保留；维护信息移到已有权限内的详情 |
| 空状态占据过大空间 | 无日志、无读数仍各占一块；原因、提示为空也各有独立区；图表/日志高度配置为 310px | 数据越少并没有越简单，反而要跨过多个空区域 | 简短说明缺什么及下一步；仅在有数据或用户主动展开时呈现完整面板 |
| 相似卡片的视觉权重接近 | 多段标题、边线、说明框并列；主要诊断栏目统一有 72px 顶部间距 | 重点不突出，同时产生“东西很多、内容又很散”的感受 | 减少重复容器层级，建立重点、摘要、详情三层；不压缩正文可读性 |
| 教师的处置与分析混在一页 | 四项概览指标、四块图表/进度、异常表、设备日志、求助、AI 审核、审核历史、知识入口 | 教师找当前需要帮助的学生时，会经过与当前处置无关的统计 | 待处理事项优先；班级趋势和资料审核各有入口 |

这些是展示与任务组织问题，不能直接推导“后端结构要推倒重做”。当前项目已经有折叠技术详情、实验参考展开、问题选择和失败恢复等基础，可以在保留业务规则的前提下调整信息组织。

### 3.1 本轮实时页面还暴露了两个容易误解的组合

一是多个问题未选择时，顶部要求先选对象，而下方仍显示整次诊断的概括与建议，底部又显示暂无提示、反馈不可用。用户可能把整次诊断的建议误当成某个已选择问题的操作。建议在对象未选时以问题选择为主，下方明确标识“整体记录”，避免看上去已经进入某一问题的指导。

二是页面同时出现“AI 已增强”和“AI 增强未启用”。前者可以指保存的解释，后者可以指当前调用条件；二者并不必然构成业务错误，但缺少时间与对象说明时，用户容易认为系统矛盾。建议将“本条解释的来源”和“当前能否生成新解释”分开，来源放在结果旁，调用条件放在操作处。

这两点仅列为呈现风险，本轮没有复现或断言后台调用越权、数据损坏等代码错误。

| **Jira Service Management**：对应学生求助与教师处置 | 求助者看到 request，处理人员看到内部 work item；队列先展示摘要、状态等信息，用于查看、分流和指派。[角色视图区分](https://support.atlassian.com/jira-service-management-cloud/docs/what-are-issues-and-requests/)、[队列说明](https://support.atlassian.com/jira-service-management-cloud/docs/check-out-your-queues/) | 同一工单按角色展示不同信息；教师首页优先“当前有什么要处理”，学生只看与自己有关的处理状态 | 我们不是完整 IT 服务台，不必引入 SLA、复杂请求类型和跨部门流程。工单结案仍不能等同硬件恢复或案例审核通过 |

**对照后的判断：**这六款产品没有证明“页面越短越好”。它们提供的共同启发是：入口围绕任务组织，详情围绕具体对象组织，完整资料不必全部常驻。成熟工具的专业详情可以很密集；我们应让这种密度出现在用户主动进入的调查层，而不是要求初学学生一进来就承担。

外部资料核验说明：Arduino 与 Labster 的正文由本轮直接打开复核；Canvas、ThingsBoard 和 Atlassian 依据官方指南。Sentry 正文直接打开受到内容类型限制，采用搜索工具返回的官方页面正文，其抓取时间较早，因此只采用摘要/动作/事件详情的结构性观察，不据此断言当前像素布局。没有把未成功读取的外部原图当作已目视验证的截图。

## 5. 建议保留多少，收起多少，移走什么

### 5.1 学生端：让当前实验成为主线

建议先在现有页面范围内建立三个清楚的内容入口，具体名称待原型验证：

| 入口 | 默认内容 | 点开后可看 |
| --- | --- | --- |
| **当前实验／排查** | 实验与设备身份、数据时效、当前现象；异常时展示所选问题、适用步骤和反馈 | 该问题相关依据、候选原因、步骤旁的教学参考 |
| **数据记录** | 读数、趋势和日志，带时间范围、单位和测试标记 | 原始记录、详细证据和技术信息 |
| **实验参考** | 本次实验已有且获授权的资料入口 | 现有知识说明、实验步骤及来源版本；缺资料明确说明，不创建不存在的内容 |

这不是要求立即新建三个路由。第一版可先做同页内容切换，复用已有组件。需要避免把“查一个依据”变成跳到另一页再找回当前问题；相关证据和教学参考仍应能在当前排查区就地展开。

主工作区建议按下面的连续顺序安排：

1. **上下文**：正在做哪个实验、哪台设备、记录是否新鲜、是否为测试数据。
2. **当前情况**：已观察到什么、尚不能确认什么；多问题时先选择，明确还有其他问题待处理。
3. **接下来操作**：当前提示等级允许的步骤、必要前提和观察目标；旁边有教学参考。
4. **操作结果**：对这个问题反馈、求助，或明确检查新的上传记录。

“当前情况”只有一个主摘要来源。不能把规则判断、AI 保存的解释、工作流历史和不同问题的文本任意拼成一个结果；必须保持同一诊断、同一对象、同一时间范围。

**不同状态应有不同重点：**

| 状态 | 页面首先帮助用户完成什么 | 简化时不能丢失什么 |
| --- | --- | --- |
| 刚进入，还没有数据 | 确认实验与设备，理解缺哪些记录 | “没有收到数据”不能改成“正常” |
| 正常观察实验数据 | 查看本实验有关的读数与趋势 | 数据时效、单位、缺失/不可信说明；不要为了突出诊断把有用图表一律藏掉 |
| 一个异常待处理 | 看现象、按允许步骤检查、反馈 | 待确认事项与动作前提 |
| 多个问题 | 先选本次处理对象，再看相关步骤 | 其他活动问题的存在、每次反馈的作用范围 |
| 等待教师 | 看谁在处理、下一步是否需要补充记录 | 原工单状态；有新数据仍按现有规则允许明确重查 |
| 反馈已解决或工单关闭 | 看处理结果和是否有恢复证据 | “处理结束”和“硬件恢复”保持独立 |
| 请求结果未知／断网 | 先确认原请求或恢复读取 | 原请求身份、旧数据只读、会话失效；不能折进详情 |

不建议强制用户按网页按钮逐步解锁排查动作，也不增加“点击下一步就累计一次尝试”的规则。当前等级已允许的步骤不能为了画面简洁任意删减；可以清楚排序或分组，不能暗中改变教学阈值。

### 5.2 内容去向清单

| 现有内容 | 建议处理 | 保留尺度 |
| --- | --- | --- |
| 顶部下一步、状态解释、诊断解释、当前判断 | 组织成一个主结果区；重复正文不再全部常显 | 解释来源可查；不同事实层次不能混写 |
| 原始日志和完整曲线 | 放入数据记录；相关片段可就地展开 | 正常实验需要观察的读数仍可在主区出现 |
| 本次检查时间、是否有新依据 | 压成结果旁的简短摘要 | “无新数据”“时间不可信”等会影响判断的状态直接显示 |
| 完整检查对比与历史 | 默认收起，可明确展开 | 历史时间、对象、版本和归属不变 |
| 候选名次、支持分进度条 | 学生首先看到可能原因与证据局限；数值解释放依据详情 | 不把支持分表现成正确概率，也不删数据库证据 |
| AI 开关、V2、节点/版本等技术说明 | 与主任务分层；保留简明来源标识和可查询详情 | 不把 AI 文本伪装成测量事实，不隐瞒关键限制 |
| 测试、过期、冲突和操作前提 | 保留在结果或动作附近 | 避免全页反复同一句；局部查看时仍能知道这些限制 |
| 尚无数据/暂无提示/任务未配置 | 合并重复空态，告诉用户缺什么和可做什么 | 原因不明时说未知，不能臆测是网络、设备或用户错误 |
| 教学知识与实验参考 | 继续贴着相关步骤按需阅读 | 不能将教学价值全部藏到深层管理页 |

### 5.3 教师端：先处理课堂事项，再看统计

建议将“课堂处置”“课堂概览”“资料与审核”分成清楚的工作入口，保留现有权限控制。

课堂处置首先显示当前班级/任务范围，以及学生求助、需关注问题和待审核数量。列表只给足够决定“先打开谁”的信息：学生或设备、问题摘要、处理状态、时间。点开后再看学生明确报告执行过的步骤（如果已有记录）、相关依据、反馈历史和允许的操作。没有动作执行记录时明确显示未记录；展示过提示或点击“仍未解决”不能当成执行过某步骤的证据。

学生工单、诊断审核和正式案例审核必须保留各自身份、条件和状态。它们可以共用入口分组，不应合并成一个含义不明的“处理完成”按钮。排序先采用已有明确状态和时间，不凭空加入 AI 紧急程度或新的教学优先级规则。

设备数量、错误趋势和班级总体情况放在课堂概览。现有 17 项工作流指标中，节点耗时、Token、成本等进入获授权人员的系统详情；不能因为移了页面就默认授予所有教师新的运维权限。已解决诊断比例仍不能叫课堂通过率。

移动端适合“列表→单项详情→返回原列表”，桌面可考虑列表与详情并列。不要照搬工业大屏的一排图表，也不要为一个课堂引入大型服务台的多层筛选和流程设置。

## 6. 可选方案与投入尺度

| 方案 | 做什么 | 预期收益与代价 | 判断 |

## 7. 怎么证明改完更好用

先制作不连接真实提交操作的布局原型，覆盖“正常看数、单异常、多问题、等待教师、结果未知”几种代表状态，再让参与者比较。建议邀请 5—8 名未参与开发的学生和 2—3 名教师作小规模形成性试用；样本用于发现卡点，不用于推断全体用户或宣称统计显著。

旧版与原型使用难度相当的任务，轮换体验顺序，减少先看一版带来的学习影响。让用户自己尝试，记录首次找到正确操作的时间、是否选错对象、是否寻求帮助、能否解释当前结论的限制。不要只问“好不好看”。

| 任务 | 必须观察的结果 |
| --- | --- |
| 学生正常观察实验数据 | 找到本实验读数与趋势，辨认单位、采样时间和缺失/过期状态，不必先进入故障流程 |
| 学生指出本次异常与下一步 | 不必通读全页，就能找到对应操作；能说出尚未确认什么 |
| 学生查看一条相关证据 | 清楚属于哪个问题、哪个时间范围，并能回到当前步骤 |
| 学生在两个问题之间切换 | 不把一次解决反馈作用到全部问题，不把另一组件的步骤混用 |
| 学生检查新数据／继续旧指导 | 能区分二者，不因按钮变少而误触提交 |
| 断网、结果未知、权限失效 | 找到正确恢复动作；不把旧数据当实时，不创建新的身份重复提交 |
| 教师找到并处理一条求助 | 不必先阅读全部统计；能区分明确报告执行过的步骤与未记录项，并看到真实处理状态 |
| 判断“反馈解决”是否代表硬件正常 | 能明确区分处理结束、恢复证据和课堂验收 |

建议验收顺序是：**先保证关键语义与操作不退化，再比较找到操作的时间和求助次数，最后看主观阅读感受。** 如果新布局更短，却让更多人误解“已解决”或找不到证据，不能通过。

技术验收需要补充各状态、不同权限、桌面/手机、键盘操作和展开/返回行为的检查。边框和无横向溢出测试继续保留，但它们不能代替真人任务结果。本轮未执行这些未来验收，也不复用上一轮测试通过数证明新方案有效。
